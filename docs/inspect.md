# 검수 (바코드 스캔)

> 코드 `assets/js/pages/inspect.js` · 라우트 `#/inspect/:orderId` · [공통 규약](common.md) · [CLAUDE.md](../CLAUDE.md)
> 진입 경로는 [당일상차리스트](loading.md)의 `검수` 버튼

파렛트 바코드를 스캔해 상차 전 검수를 처리하는 화면.
**휴대폰 카메라 사용을 전제로 만들었다.** 사이드바 메뉴에는 없는 하위 화면이다.

> 📱 **모바일 앱에는 이 화면이 별도로 없다.** 상차검수는 앱의 `#/load/:id` 세그 `상차검수`로
> 흡수되었다 ([docs/mobile.md](mobile.md#3-5-상차작업-load--리스트--검수--완료--로케이션-) 참고).
> 이 문서(`assets/js/pages/inspect.js`, 웹 셸 하위 화면)는 6단계(웹 코드 정리)에서 삭제 예정이며
> 그 전까지는 유효한 기존 경로다. 웹의 `app.html#/inspect/:id` 링크는 앱에서는
> `m.html#/load/:id` 로 매핑된다(웹 inspect 는 상차검수 화면이라 이름이 같은 앱의
> `#/inspect`(검수작업 탭)와 다른 화면임에 주의).

## 화면 구성

### 상단 — 검수 대상 요약 (진한 남색 헤더)

```
R-2609-001  [대표] [3건]          ← 대표주문번호가 있으면 그 번호가 크게 나온다
올리브영 물류센터 · 용차 · 출고 2026-08-29
묶인 주문 3건이 함께 검수되고, 각 주문의 검수내역은 대표에 그대로 집계됩니다.
[PO-24080101 2/2] [PO-24080102 0/3] [PO-24080103 파렛트 없음]   ← 주문별 검수 진행
┌─────────┬───────────┬────────┐
│ 총 파렛트 │ 검수 파렛트 │ 진행률 │
│    6    │     2     │  33%   │
└─────────┴───────────┴────────┘
[■■■■□□□□□□□□]
```

진행률 100%면 막대가 초록색으로 바뀐다.

### 본문

1. `📷 카메라 스캔 시작` 버튼 — 다시 누르면 정지
2. `<video>` — 시작 전에는 숨김
3. 바코드 직접 입력 + `검수 등록` 버튼
4. 파렛트 목록 — `파렛트 N / 총수` 로 표시한다. 검수된 항목은 초록 배경 + ✅
   (라벨 바코드가 모두 같아 바코드 문자열 대신 순번을 보여준다)
   **묶음이면 차수 배지 옆에 그 파렛트가 어느 주문의 것인지 주문번호가 함께 나온다**
   (`.pallet__order`)
5. `상차완료 처리` 버튼 — **검수 상태일 때만 노출** (`hidden` 속성 제어)

`검수 초기화` 버튼은 카드 헤더 우측에 있다.

## 핵심 로직

### 바코드 규칙 🔑

주문의 `pallet_count` 만큼 자동 생성한다 (`mock-data.js` 의 `makePallets`).

```
{주문번호}-P01, {주문번호}-P02, ...   예: PO-24080101-P01
```

⚠️ **임시 규칙이다.** 실제 용마물류 파렛트 라벨 체계가 확정되면 교체한다.
`pallet_count` 가 0이면 바코드가 하나도 없어 검수할 수 없다.

`pallet_count` 는 두 곳에서 정해진다. 어느 쪽이든 **바코드가 전부 재생성되고
검수가 초기화된다.** 검수 중이던 건은 처음부터 다시 스캔해야 한다.

| 경로 | 함수 |
|---|---|
| 출고주문처리 검수작업 탭의 **총 파렛트수 입력** (주 경로) | `db.setInspectDone()` |
| 주문정보등록에서 주문 수정 | `db.updateOrder()` |

### 스캔 처리 — `db.scanPallet()` 🔑

**상차 묶음을 한 번에 검수한다 🔑** — 상차 단계는 대표주문번호로 묶인 주문과
추가주문 차수를 **모두** 하나로 본다 (`db.groupKeyOf`). 이 두 가지가 한 화면에 나오고
(`db.getLoadGroup()`), 총 파렛트수도 묶음 합계다. 헤더에는 `N건` 배지와 함께
**주문별 검수 진행(`PO-1 2/3`)** 이 배지로 나열되어, 각 주문의 검수내역이 대표에
집계된다는 것이 바로 보인다 (전량 검수된 주문은 초록). 파렛트 목록에는 `1차` `2차`
차수 배지와 **주문번호**가 함께 표시된다.
전량 검수되면 묶인 주문이 모두 `검수` 상태가 되어 상차완료 버튼이 나타난다.
⚠️ **완료 조건은 종전과 같다** — 묶음 전체가 검수돼야 상차완료할 수 있다.

⚠️ **묶음에는 두 종류가 있고 파렛트가 있는 곳이 다르다** ([orders.md](orders.md) 참고).
등록 시 묶은 묶음은 **파렛트가 묶음 대표에만** 있고(나머지는 0파렛트),
**검수 후 합친 묶음은 주문마다 자기 파렛트**를 갖는다. 총 파렛트수는 어느 쪽이든
**멤버 `pallet_count` 의 합**이다 (파렛트 행 수와 항상 같다).
두 종류를 가르는 판정은 **`db.hasSplitPallets(rows)` 한 곳**에만 있고,
모집단(상차 묶음 / 대표주문번호 묶음)은 부르는 화면이 정한다.
🔑 그래서 주문별 진행 배지에서 **파렛트가 0개인 멤버는 `0/0` 이 아니라 `파렛트 없음`**
(파란 태그)으로 적는다. `0/0` 회색 태그는 미검수로 오인되는데, 이 멤버는 애초에
검수할 파렛트가 없는 것이 정상이다.

**스캔 대상은 상차라벨의 주문번호 바코드다.**
([주문처리현황](status.md)에서 출력한 라벨이 파렛트마다 붙어 있다)

#### 채우는 범위 🔑 — 주문별 라벨은 각각 전량 스캔한다

스캔한 코드가 **어느 주문의 라벨인지** 보고 채울 범위를 가른다.

| 입력 | 채우는 범위 |
|---|---|
| **멤버의 주문번호** (그 주문이 자기 파렛트를 가짐) | **그 주문의** 미검수 파렛트 1개 |
| **대표주문번호** · 파렛트가 없는 멤버의 번호 | 묶음 전체의 미검수 파렛트 1개 |
| `{주문번호}-P01` (파렛트 개별 바코드) | 그 파렛트를 검수한다 — 도입 전 방식, 계속 인식한다 |

🔑 **검수 후에 합친 묶음은 주문마다 자기 라벨이 이미 출력돼 있다**
([orders.md](orders.md) 주문합치기 참고). 묶음 전체에서 아무거나 채우면
**A 라벨만 계속 읽어도 B 파렛트가 채워져** 실물과 어긋난다. 그래서 주문번호 라벨은
그 주문의 몫만 채운다. 화면에도 **「주문마다 출력된 상차라벨을 각각 그 수량만큼
스캔하세요」** 안내가 나온다 (파렛트를 가진 주문이 2건 이상일 때).

🔑 **등록 시 묶은 묶음은 종전 동작 그대로다.** 파렛트가 대표에만 있어
대표주문번호 라벨 1종을 총량만큼 읽으면 된다. 추가주문 차수도 원래부터 차수마다
자기 라벨(`a11111` / `a11111-1`, 라벨 오른쪽 위에 `추가건 - N차수`)을 쓴다.

| 상황 | 결과 |
|---|---|
| 파렛트가 하나도 없음 | ❌ "검수할 파렛트가 없습니다. …파렛트수를 입력하세요." |
| 다른 주문의 바코드 | ❌ "해당 주문의 바코드가 아닙니다." |
| **그 주문만** 전량 검수됨 | ❌ "PO-1 주문은 전량 검수되었습니다. (2/2) 남은 주문: PO-2 3장" |
| 묶음 전체가 전량 검수됨 | ❌ "이미 전량 검수되었습니다. (4/4)" |
| 이미 검수된 개별 파렛트 | ❌ "이미 검수된 파렛트입니다." |
| 정상 (단독 주문) | ✅ "검수 완료 (3/6)" |
| 정상 (묶음) | ✅ "검수 완료 (3/6) · PO-1 2/2" — 묶음 진행 + 그 주문 진행 |

🔑 **주문별 문구는 「다른 주문의 파렛트도 있을 때」만 붙는다** (`ours.length !== mine.length`).
등록 시 묶은 묶음은 대표가 파렛트를 전부 갖고 있어 대표번호를 읽는 것이 곧 묶음 전체를
읽는 것과 같으므로, 종전 문구(`검수 완료 (3/6)`)를 그대로 쓴다.

#### 상차검수 통과 판정 🔑 (`db.js` 의 `scanDone`)

| 주문 | 통과 조건 |
|---|---|
| 파렛트가 있는 주문 | **전량 스캔** (`inspected >= pallet_count`) |
| **0파렛트 멤버** (혼적 · 등록 시 묶음의 멤버) | **`inspect_done_at` 이 있을 때만** |

⚠️ `inspected >= pallet_count` 만 보면 0파렛트 멤버는 `0 >= 0` 이 늘 참이라,
**검수작업도 끝나지 않은 주문이 남의 라벨 스캔만으로** 상차검수를 통과해
상차완료·마감까지 올라간다. 상차완료 취소(`cancelLoading`)도 **같은 함수**를 쓴다
([loading.md](loading.md) 참고).

- 라벨은 주문마다 같은 번호라 **몇 번 스캔했는지가 곧 검수한 파렛트 수**다
- ⚠️ **카메라는 같은 코드를 2.5초 이내에 다시 읽지 않는다** (`scanner.js`).
  라벨을 옮겨가며 스캔하면 문제없지만, 한 라벨을 계속 비춰도 카운트가
  올라가지 않는다. 이 쿨다운이 중복 카운트를 막는 장치다
- 직접 입력에는 쿨다운이 없어 연속 등록할 수 있다 (블루투스 스캐너 포함)
- **대소문자를 구분하지 않는다.** 앞뒤 공백도 제거한다
- **다른 주문의 바코드는 거부한다.** 주문 간 오검수를 막는 핵심 장치다
- 성공 시 `navigator.vibrate(60)` — 현장에서 화면을 못 볼 때의 피드백

### 전량 검수 시 자동 전환 🔑

```js
if (o.inspected >= o.pallet_count && o.load_status === LOAD_STATUS.WAIT) {
    o.load_status = LOAD_STATUS.INSPECTED;   // 대기 → 검수
}
```

전량 스캔되면 상태가 **자동으로** `검수` 로 바뀐다. 별도 완료 버튼이 없다.
동시에 카메라가 꺼지고 상차완료 버튼이 나타난다.

### 카메라 스캔

브라우저 내장 **`BarcodeDetector`** 를 쓴다. 외부 라이브러리 의존이 없다.

| 항목 | 값 |
|---|---|
| 인식 포맷 | `code_128` `code_39` `ean_13` `qr_code` `codabar` `itf` |
| 카메라 | `facingMode: 'environment'` (후면 우선) |
| 인식 주기 | 400ms |
| 중복 방지 | 같은 코드는 **2.5초 이내 재인식 무시** |

**카메라 버튼이 아예 보이지 않는다면 접속 방식 문제다.** `navigator.mediaDevices` 는
HTTPS 또는 localhost 에서만 존재하므로, 휴대폰에서 `http://192.168.x.x:5173` 으로 열면
버튼이 숨겨지고 그 이유를 `#cam-note` 안내로 띄운다. `npm run dev:https` 로 띄운
주소로 접속하면 카메라가 켜진다. ([docs/testing.md](testing.md) 참고)

스캔 중에는 버튼이 `■ 스캔 중지` 로 바뀐다. 전량 검수·상차완료로 카메라가 자동으로
꺼질 때도 `syncCamBtn()` 이 표시를 되돌린다.

미지원 브라우저(주로 iOS Safari)에서는 BarcodeDetector 대신 ZXing 을 내려받아 쓴다.
그마저 안 되면 **직접 입력으로 처리한다.**
### 연속 스캔 🔑

직접 입력란은 **블루투스(모바일 연결) 바코드 스캐너**와 함께 쓰는 것을 전제로 한다.
스캐너는 코드를 타이핑하고 `Enter` 를 보내므로, 한 건을 처리한 뒤에도
**커서가 입력창에 남아 있어야** 다음 파렛트를 이어서 찍을 수 있다.

```js
manual.value = '';          // 다음 코드가 이어붙지 않게 먼저 비운다
keepFocus = true;
await submit(code);         // 목록을 다시 그린다
keepFocus = false;
manual.focus();
manual.select();
```

- `refresh()` 가 목록을 다시 그리는 동안에도 `keepFocus` 로 커서를 되돌린다
- 처리 결과를 기다린 뒤(`await`) 포커스를 주므로 순서가 어긋나지 않는다

### 자원 정리 🔑

```js
return () => {
    stopCamera();     // 타이머 + MediaStream 트랙 정지
    unsubscribe();    // 폴링 해제
};
```

**정리 함수를 반드시 반환한다.** 반환하지 않으면 화면을 떠난 뒤에도
카메라 LED 가 켜져 있고 배터리를 소모한다.
`stopCamera()` 는 상태가 `대기` 가 아니게 되면 `refresh()` 안에서도 호출된다.

### 검수 초기화

`db.resetInspection()` — 모든 파렛트의 `scanned_at` 을 비우고 상태를 `대기` 로 되돌린다.
이력에 `검수: <이전 상태> → 대기` 로 기록된다. 확인 대화상자를 거친다.

🔑 **상차완료된 묶음은 초기화할 수 없다.** 당일상차리스트 상세의 `상차완료 취소` 로
상차를 먼저 되돌려야 한다 ([loading.md](loading.md) 참고). 거부되면 토스트로 알린다.

> ⚠️ 예전에는 이 검사가 없어서 **상차완료 뒤에도 초기화가 됐다.** 그러면 `loaded_at` 은
> 남은 채 상차 상태만 `대기` 로 돌아가, 화면에는 상차 전으로 보이는데 취소·수정·적치취소는
> `상차완료된 주문입니다` 로 거부되는 앞뒤 안 맞는 상태가 됐다.
> 적치취소 → 검수취소와 같은 **되돌리는 순서 규칙**을 여기에도 맞췄다.

### 상차완료

`db.completeLoading()` 호출 후 `#/loading` 으로 돌아간다.
검수 상태가 아니면 데이터 계층에서 거부한다 ([loading.md](loading.md) 참고).

## 실시간 갱신

`db.subscribe(refresh, 8000)` — **8초 간격.**
다른 화면(5초)보다 길게 둔 이유는 스캔 중 화면이 자주 다시 그려지면
작업에 방해가 되기 때문이다.

## 수정 시 주의

- **정리 함수에서 카메라를 반드시 끈다.** 가장 흔한 실수다
- 바코드 비교는 대문자 정규화 후 수행한다. 규칙을 바꿔도 이 처리는 유지한다
- `BarcodeDetector` 미지원 환경 대비 직접 입력 경로를 **절대 제거하지 않는다.**
  iOS 에서는 이것이 유일한 수단이다
- 실기기 확인 권장: `npm run dev` 의 `Network:` 주소로 휴대폰에서 접속.
  **카메라 API 는 HTTPS 또는 localhost 에서만 동작한다.** 폰에서 http 로 접속하면
  카메라가 차단되므로, 실기기 카메라 테스트에는 HTTPS 터널이 필요하다
- 스캔 성공/실패는 항상 `toast()` 로 알린다. 현장에서는 화면을 자세히 보지 않는다
