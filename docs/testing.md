# 모바일 테스트 방법

> [CLAUDE.md](../CLAUDE.md) · 대상 화면: [출고주문처리](shipping.md), [검수](inspect.md)

바코드 스캔은 웹 브라우저만으로 확인하기 어렵다. 상황에 맞는 방법을 골라 쓴다.

---

## 요약

| 방법 | 카메라 스캔 | 준비 | 언제 쓰나 |
|---|:---:|---|---|
| 1. 수기 입력 | ❌ | 없음 | 업무 흐름만 빠르게 확인할 때 |
| 2. 브라우저 반응형 모드 | ✅ (PC 웹캠) | 없음 | 개발 중 대부분의 확인 |
| 3. 실기기 + HTTPS | ✅ (폰 카메라) | `npm run dev:https` | 현장과 같은 조건으로 확인할 때 |
| 4. 블루투스 스캐너 | — | 스캐너 | 실제 운영 장비로 확인할 때 |

**카메라는 HTTPS 또는 localhost 에서만 동작한다.**
휴대폰에서 `http://192.168.x.x:5173` 으로 접속하면 카메라가 차단된다.

---

## 0. 테스트용 바코드 준비

`barcodes.html` 에 **로그인한 계정이 볼 수 있는 주문**의 바코드가 자동으로 만들어진다.

⚠️ **이 페이지는 개발 전용이라 배포되지 않는다** (`vite.config.js` 의 빌드 entry 에서 제외).
개발 서버에서만 열린다.

```
http://localhost:5173/barcodes.html
```

- **주문번호** - 출고주문처리의 세 탭에서 스캔.
  **상차리스트 → 검수 화면에서도 같은 바코드를 파렛트 수만큼 스캔한다**
  (주문처리현황에서 출력하는 상차라벨의 바코드와 같다)
- **파렛트 바코드** - 상차라벨 도입 전 방식. 검수 화면에서 그대로 인식된다
- `인쇄` 버튼으로 종이에 뽑아 쓸 수 있다
- 외부 라이브러리 없이 `assets/js/barcode.js` 가 Code128 SVG 를 직접 그린다

두 번째 화면(또는 다른 기기)에 이 페이지를 띄워두고 스캔하면 편하다.

---

## 1. 수기 입력 (가장 간단)

스캔 없이도 모든 기능을 확인할 수 있다. 각 화면의 입력칸에 주문번호나 바코드를 직접 넣는다.

- 출고주문처리: `주문번호 (바코드 스캔 또는 직접 입력)` 칸
- 검수 화면: `바코드 직접 입력` 칸

스캔이 안 되는 상황에서도 항상 열려 있는 경로다.

---

## 2. 브라우저 반응형 모드 + PC 웹캠 (권장)

가장 빠르고 준비물이 없다.

1. `npm run dev` 후 크롬에서 `http://localhost:5173/app.html` 접속
2. **창 너비를 860px 이하로 줄인다** → 모바일 화면으로 자동 전환된다
   (개발자도구 F12 → 기기 툴바 Ctrl+Shift+M 도 동일)
3. `📷 스캔` 을 누르면 **노트북 웹캠**이 켜진다
4. 다른 창이나 휴대폰에 `barcodes.html` 을 띄워 웹캠에 비춘다

`localhost` 는 안전한 출처로 취급되므로 HTTPS 없이도 카메라가 동작한다.

---

## 3. 실기기(휴대폰) + HTTPS

현장과 같은 조건으로 확인할 때 쓴다.

```
npm run dev:https
```

출력되는 `Network: https://192.168.x.x:5173/` 주소를 휴대폰에서 연다.

- 자체 서명 인증서라 **경고 화면이 뜬다 → `고급` → `계속 진행`** 을 누른다
- 그 뒤에는 HTTPS 이므로 카메라가 정상 동작한다
- PC 와 휴대폰이 **같은 와이파이**에 있어야 한다
- 안드로이드·아이폰 모두 동작한다 (아래 지원 표 참고)

홈화면에 추가하면 PWA(앱처럼 전체화면)로도 확인할 수 있다.

---

## 4. 블루투스 바코드 스캐너

현장에서 실제로 쓰는 장비다. 스캐너는 **키보드처럼 동작**하므로 별도 연동이 필요 없다.

1. 입력칸에 커서를 둔다
2. 스캔하면 값이 입력되고 Enter 가 함께 전송되어 바로 조회된다

카메라 스캔이 안 되는 기기에서도 이 방법은 그대로 동작한다.

---

## 샘플 데이터 초기화

⚠️ **샘플 데이터는 제거했다.** 더미 계정·주문이 운영 배포본에 함께 실리기 때문이다.
`mock` 모드는 이제 **빈 상태로 시작하므로 로그인할 계정도 없다.**
화면 확인은 Supabase 모드로 한다.

아래 초기화는 **mock 모드에서 남은 데이터를 비울 때만** 쓴다.

```js
const db = await import('/assets/js/db.js');
await db.resetDb();
location.reload();
```

Supabase 모드(`VITE_DATA_SOURCE=supabase`)는 실제 서버 데이터라 이 방법이 막혀 있다.
정리가 필요하면 Supabase SQL Editor 에서 직접 지운다.
서버 없이 화면만 확인하려면 `.env.local` 의 `VITE_DATA_SOURCE` 를 `mock` 으로 바꾼다.

## 참고: 브라우저별 카메라 스캔 🔑

| 환경 | 카메라 스캔 | 인식 방식 |
|---|:---:|---|
| 안드로이드 크롬 | ✅ | 내장 `BarcodeDetector` |
| 데스크톱 크롬 / 엣지 | ✅ | 내장 `BarcodeDetector` |
| **iOS 사파리 · 크롬** | ✅ | **ZXing** (내려받아 처리) |
| 파이어폭스 | ✅ | ZXing |

### iOS 는 크롬을 써도 내장 인식기가 없다

**아이폰은 크롬·엣지·파이어폭스도 전부 애플의 WebKit 엔진을 쓴다.**
겉모습만 다를 뿐 사파리와 같은 엔진이라, 크롬으로 바꿔도 `BarcodeDetector` 는 없다.

그래서 `assets/js/scanner.js` 는 인식기를 두 갈래로 만든다.

```js
if (hasNativeDetector()) { /* 내장 BarcodeDetector */ }
else { const { BrowserMultiFormatReader } = await import('@zxing/browser'); }
```

- ZXing 은 **내장 기능이 없을 때만 동적으로 내려받는다** (약 470KB, 별도 청크)
  안드로이드·데스크톱 크롬 사용자는 이 파일을 받지 않는다
- 카메라 자체(`getUserMedia`)는 iOS 사파리·크롬 모두 지원하므로 스캔이 동작한다
- **여전히 HTTPS 는 필요하다.** `npm run dev:https` 로 접속한다

## 카메라 인식률 🔑

`assets/js/scanner.js` 맨 위 **`TUNE` 한 곳**에 인식률에 관계된 값이 모여 있다.
현장에서 잘 안 읽히면 이 상수만 조정하고, 문제가 생기면 그대로 되돌린다.

| 값 | 기본 | 뜻 · 조정 방향 |
|---|---|---|
| `nativeSize` | **2560×1440** | 내장 인식기용 요청 해상도. **작은 라벨을 살리는 가장 큰 수단**이다. 발열이 심하면 1920×1080 으로 낮춘다 |
| `zxingSize` | **1920×1080** | iOS 등 ZXing 경로 해상도. ROI 로 잘라 넘기므로 총 비용은 크게 늘지 않는다 |
| `downSize` | 1280×720 | 예산을 2회 연속 넘기는 기기가 자동으로 내려가는 해상도 (**되돌리지 않는다**) |
| `roiNative` / `roiZxing` | 아래 ROI 계획 | 한 프레임에서 순서대로 볼 영역. **첫 성공에 멈춘다** |
| `budgetNativeMs` / `budgetZxingMs` | 120 / 260 | 프레임당 디코딩 예산. 넘기면 다음 ROI 를 열지 않고 다음 프레임으로 넘어간다 |
| `zoomSteps` | [1, 2, 3] | 줌 버튼 배율. 기기가 주는 `zoom.max` 로 잘리고, **줌이 없으면 버튼이 숨는다** |
| `zoomSettleMs` | 300 | 줌을 바꾼 뒤 연속 오토포커스를 다시 걸기까지 기다리는 시간 |
| `preMissN` | 3 | 연속 미검출이 이만큼 쌓이면 ROI 순서를 돌리고 ZXing 에 전처리를 붙인다 |
| `consensus` | 1 (꺼짐) | 같은 값을 몇 프레임 **연속** 봐야 받는지 (미검출이 끼면 처음부터 다시 센다). **오인식 신고가 오면 2로 올린다** — 잘 안 읽히는 기기에서는 그만큼 느려진다 |
| `minGapMs` | 60 | 찾는 중의 프레임 간격. 발열이 심하면 100~120 으로 올린다 |
| `idleGapMs` / `idleAfterMs` | 180 / 2000 | **2초간 아무것도 안 잡히면** 간격을 늘려 발열·배터리를 아낀다 |
| `repeatMs` / `reArmMs` / `reArmFrames` / `costCapMs` | 2500 / 1500 / 5 / 500 | 같은 라벨을 다시 받는 조건 (아래 참고). 🔑 **인식 강화와 무관하게 그대로 둔다** |
| `selfTestText` | `SELFTEST-128` | 시작할 때 내장 인식기에 먹여 보는 자가 진단 바코드 값 (아래 [내장 인식기 폴백](#내장-인식기-폴백-2026-09-19-)) |
| `shadowAfterMs` | 4000 | 내장이 이만큼 아무것도 못 잡으면 같은 프레임을 ZXing 으로도 본다 |
| `shadowEveryN` | 6 | 그림자 디코딩 주기 (미검출 6회마다 1번). 발열이 심하면 올린다 |
| `shadowSwitchHits` | 2 | ZXing 만 읽은 일이 이만큼 쌓이면 내장을 버린다. 오판이 걱정되면 3으로 올린다 |

**ROI 계획** — ⚠️ **가로를 0.72 아래로 자르지 않는다.** Code128 은 좌우 여백(quiet zone)이
잘리면 디코딩이 실패한다. 1D 는 스캔라인 하나면 되므로 **세로를 줄인다**
(`scan-calc.js` 의 `ROI_MIN_W` · `npm run check:scan` 의 S7 이 강제한다).

| 순서 | 내장 경로 | ZXing 경로 | 포맷 |
|---|---|---|---|
| 1 | 전체 `1.00 × 1.00` | 밴드 `1.00 × 0.45` | **CODE_128 전용** (빠르고 오인식이 적다) |
| 2 | 밴드 `1.00 × 0.45` | 좁은 밴드 `1.00 × 0.22` | 전 포맷 |
| 3 | 사각 `0.80 × 0.60` | 사각 `0.80 × 0.60` | 전 포맷 |
| 4 | — | 전체 `1.00 × 1.00` | 전 포맷 |

미검출이 `preMissN`(3)회 쌓일 때마다 **순서를 한 칸씩 돌려** 같은 자리만 보지 않게 하고,
ZXing 경로에는 **그레이 + 대비 스트레치** 전처리를 붙인다 (잘 읽히는 동안에는 붙이지 않는다).

- **해상도는 `ideal` 로만 요청한다.** 못 맞추는 기기도 거절하지 않고 가장 가까운 값을 준다
- **프레임 예산을 2회 연속 넘기면**(ROI 1회조차 예산을 넘는 기기) 해상도를 `downSize` 로
  낮춘다. 되돌리지 않는다 — 올렸다 내렸다 하면 화면이 계속 깜빡이고 초점이 다시 잡힌다
- **줌은 안드로이드에서만 대부분 동작한다.** `track.getCapabilities().zoom` 이 없는 기기
  (iOS·대부분의 PC 웹캠)에서는 **버튼 자체가 나오지 않는다.** 핀치 줌도 같은 조건이다
- **연속 오토포커스**(`focusMode: 'continuous'`)는 기기가 지원할 때만 적용한다
- **플래시 버튼**은 프리뷰 오른쪽 위에 뜨고, **토치를 지원하는 기기에서만** 나타난다
  (대개 안드로이드 후면 카메라. iOS 사파리는 지원하지 않아 버튼이 없다)
- 화면에 바코드가 여러 개 잡히면 **조준 밴드 가운데에 가장 가까운 것**을 고른다

### 같은 라벨을 연달아 스캔할 때 🔑

상차검수는 **같은 주문번호 라벨을 파렛트 수만큼** 찍는다. 그래서 같은 값이 다시 들어오는 것이
정상이고, 판정을 어느 쪽으로 틀리든 사고가 난다.

| 너무 엄격하면 | 너무 느슨하면 |
|---|---|
| 빨리 찍는 사람에게 "안 읽힌다" 로 보인다 | **한 파렛트가 2건으로 세어진다** |
| 직접 입력으로 우회 가능 | 실물은 남았는데 진행률 100% → 파렛트 누락 출고 |

오른쪽이 훨씬 위험하므로 **보수적으로** 잡았다.

- 라벨을 계속 비추고 있으면 **2.5초**(`repeatMs`) 동안 다시 세지 않는다
- 다음 1건으로 세려면 **라벨이 그만큼 비어 있어야** 한다 —
  `reArmMs`(1.5초)와 `reArmFrames × 디코딩 1회 소요시간`(5배) 중 **큰 쪽**
- 두 번째 조건이 있는 이유: iOS·ZXing 은 디코딩 1회가 100~400ms 라, 라벨을 든 채
  초점 재조정·손떨림으로 몇 번 실패하면 **"라벨을 치웠다" 로 오해**해 두 번 세어진다.
  기기가 느릴수록 문턱이 자동으로 커진다 (400ms × 5 = 2초)
- 실사용에서 파렛트를 옮기는 간격은 1초를 넘으므로 누락 부작용은 거의 없다.
  그래도 못 세면 **직접 입력**으로 넣는다 (쿨다운이 없다)

### 실기기에서 확인할 것

`npm run dev:https` 로 폰에서 접속해 `m.html#/load` 상차검수·`#/stow` 로케이션에서 본다.

1. 프리뷰에 **점선 밴드**가 보이고, 밴드 가운데 빨간 선에 바코드를 맞추면 읽히는가
2. 파렛트 라벨을 **연속으로 3~4장** 찍을 때 **찍은 수와 카운트가 정확히 같은가**
   (같은 번호여도 된다. **라벨을 한 장씩 떼었다 대는** 방식으로 확인한다)
   - ⚠️ **찍은 수보다 카운트가 많으면 즉시 보고** — 실물은 안 찍힌 파렛트가 남았는데
     진행률이 100% 가 되어 **파렛트 누락 출고**로 이어진다. `TUNE.reArmMs` 를 올려야 한다
   - 🔑 **한 장을 떼지 않고 계속 비추면 2.5초마다 1건씩 오르는 것이 정상이다**
     (`TUNE.repeatMs` · 구버전부터 같다). 이걸 결함으로 보고하지 않는다 —
     상차검수는 같은 번호 라벨을 파렛트 수만큼 찍는 업무라 계속 비추는 것을 영구히
     막으면 정상 작업이 멈춘다
3. 어두운 곳에서 **플래시 버튼**이 보이는가 (안드로이드) · 눌러 켜지는가
4. 화면을 떠나거나 `중지` 를 누르면 **프리뷰와 플래시가 함께 꺼지는가**
5. 앱을 백그라운드로 보냈다 돌아오면 프리뷰가 멈춰 있지 않은가
6. 카메라를 켠 직후(1~3초 안에) **세그를 바꾸거나 화면을 떠나도** 폰이 계속 뜨거나
   느려지지 않는가 (준비 중 이탈 시 루프가 남지 않아야 한다)
7. 5분 이상 켜 둔 채 작업할 때 발열이 견딜 만한가 — 심하면 `minGapMs` 를 100~120,
   `nativeSize` 를 1920×1080 으로 낮춘다 (인식률보다 발열이 먼저 문제라면 이 순서)
8. **줌 버튼(1x·2x·3x)이 안드로이드에서 보이는가** · 2x·3x 에서 3m 거리 라벨이 읽히는가
9. **iOS 에서 줌 버튼이 숨겨지는가** (없는 기능을 눌러 실패하지 않아야 한다)
10. `barcodes.html` 의 **소형 카드(모듈 1px)** 를 20cm 에서 읽는가 ·
    **원거리 카드(×0.35)** 를 줌 2x 로 읽는가
11. 🔴 **줌·해상도를 올린 뒤에도 「찍은 수 = 카운트」가 유지되는가** (가장 중요 · 2번과 같은 방법)
12. 5분 연속 스캔에서 **해상도 강등이 실제로 걸리는가** (콘솔에 `해상도를 1280×720 로
    낮췄습니다` 경고가 뜬다) · 강등 뒤 인식이 계속 되는가
13. 가이드 박스(점선)가 **비디오 안에서 ROI 자리와 맞는가** · 인식되는 순간 **초록으로
    번쩍이는가** · 핀치로 확대·축소가 되는가 (줌 지원 기기)

### 그래도 안 될 때

- **줌 버튼(2x·3x)을 눌러 본다.** 거리가 있는 라벨은 크롭이 아니라 **줌만 효과가 있다**
  (크롭은 픽셀을 잘라낼 뿐 모듈 픽셀 수를 늘리지 못한다). 버튼이 없으면 그 기기에는
  줌이 없는 것이므로 **라벨에 더 가까이 간다**
- **가이드 박스(점선) 안에 라벨을 채운다.** 박스는 디코더가 실제로 보는 영역이고,
  좌우 여백까지 들어와야 읽힌다 (바코드를 화면 끝까지 붙이면 오히려 실패한다)
- 어두우면 **플래시**를 켠다 (안드로이드) · 라벨이 접히거나 젖었으면 펴서 댄다
- HTTPS 로 접속했는지 확인한다 (`http://` 면 카메라가 차단된다)
- 카메라 권한을 허용했는지 확인한다 (설정 → 사파리/크롬 → 카메라)
- 🔑 **프리뷰 좌하단의 엔진 태그가 `내장` 인데 안 읽히면** 계정 화면(`#/account`) →
  **`스캔 엔진 재검사`** 를 누르고 다시 켠다. 안드로이드는 Google Play 의 바코드 모듈이
  없으면 내장 인식기가 **만들어지기는 하는데 아무것도 못 읽는다.** 보통은 자가 진단이
  걸러내지만, 진단을 통과한 뒤 고장난 기기는 이 버튼으로 다시 판정하게 한다
  (태그가 `ZXing` 으로 바뀌면 그 기기는 앞으로 ZXing 으로 돈다)
- 지원 문의를 받을 때는 **엔진 태그(`내장`/`ZXing`)를 먼저 묻는다.** 어느 경로에서
  못 읽는지에 따라 볼 곳이 다르다
- 안 되면 **수기 입력**이나 **블루투스 스캐너**를 쓴다. 두 경로는 항상 열려 있다

### 0. 먼저 정리한 전제 — 무엇이 인식률을 결정하는가

바코드 1D 디코딩은 **바코드의 최소 모듈(가장 가는 바)이 이미지에서 몇 픽셀인가**로
거의 결정된다. 경험칙은 **모듈당 2px 이상**이다. 그래서 대책은 셋뿐이다.

| 상황 | 모듈 픽셀을 늘리는 수단 | 크롭(ROI)이 도움이 되는가 |
|---|---|---|
| **먼 거리** | **줌**(`track.zoom`) — 유일하게 결정적 | ❌ 잘라도 모듈 픽셀은 그대로다 |
| **작은 라벨을 가까이** | **센서 해상도 상향** + 근접 초점 | 🔺 간접적 (잡음 제거·속도) |
| 라벨이 화면에서 작게 보임 | 위 둘 | 🔺 디코더가 후보를 덜 놓친다 |

🔑 **크롭은 확대가 아니다.** 원본 픽셀을 그대로 잘라내므로 모듈 픽셀 수는 변하지 않는다.
크롭의 이득은 ① 처리 픽셀이 줄어 프레임을 더 많이 볼 수 있고 ② 주변 잡음(다른 라벨·
글자·격자)이 빠져 1D 스캔라인이 붙는 것이다. **크롭을 줌이라고 부르지 않는다.**

### 2. 학습로그 규칙(2026-09-17)과의 정합 🔑 — 가장 중요한 한 가지

인식률을 올리면 **중복 계수 위험이 자동으로 커지는 역설**이 있다. 지금
`reArmGap = max(reArmMs, reArmFrames × cost)` 의 `cost` 는 **성공·실패 프레임을 섞어**
잰 이동평균이다. ROI 계획이 들어오면 성공 프레임은 첫 ROI 에서 끝나 **싸지고**,
평균이 내려가 `reArmGap` 이 짧아진다 → **한 파렛트가 2건으로 세어질 여지가 커진다.**

```
잘 읽히게 만든다 → 성공 프레임이 싸다 → cost ↓ → reArmGap ↓ → 중복 계수 ↑   ← 막아야 한다
```

**규칙 (설계 불변식)**

1. `cost` 는 **미검출로 끝난 tick 의 소요시간만** 이동평균한다. 성공 프레임은 넣지 않는다.
   (`cost` 의 뜻 = "라벨을 든 채 한 번 실패하는 데 걸리는 시간")
2. 한 tick 은 예산(`budgetMs`) 안에서 ROI 를 순서대로 시도하고 **첫 성공에서 멈춘다.**
   미검출 tick 은 예산에 수렴하므로 `cost ≈ budgetMs` 로 **안정된다.**
3. `reArmMs`(1.5초) 하한은 **절대 낮추지 않는다.** 어떤 적응도 이 아래로 내려가지 않는다.
4. 위 두 식은 **여전히 한 식**(`max(시간, 프레임수 × 1회 비용)`)이다. 상수를 나란히 두지 않는다.
5. 줌·해상도·ROI 계획을 바꾸는 손잡이는 **`accepts()` 를 건드리지 않는다.** 중복 판정과
   인식 강화는 서로 독립이어야 한다.


`checkflow.js` + `tools/checkflow-check.js` 와 같은 꼴이다. 순수 함수라 브라우저 없이
가짜 디코더로 루프를 모사해 셀 수 있다.

**구현** — 설계와 다른 곳은 둘이다.
① 순수 함수가 **`tune` 을 인자로 받는다.** 조정값이 두 파일에 흩어지면 현장에서 어느 쪽을

② 설계에 없던 `clampZoom` · `nextOverrun` · `shouldDowngrade` · `aimRect` 를 순수 함수로
빼냈다 — 전부 **검사기가 세야 하는 판정**이라 DOM 쪽에 두면 검사할 수 없다.

| `minGapMs` | 60 | 60 (유지) | tick 이 무거워져 실질 간격은 자연히 늘어난다 |
| `repeatMs` `reArmMs` `reArmFrames` `costCapMs` | 2500 / 1500 / 5 / 500 | **전부 유지** | 🔑 중복 판정은 이번 변경에서 건드리지 않는다 |

**ROI 계획** — ⚠️ **가로를 0.72 아래로 자르지 않는다.** Code128 은 좌우 여백(quiet zone,
모듈 10개)이 없으면 디코딩이 실패한다. 1D 는 스캔라인 하나면 되므로 **세로를 좁힌다.**

| 순서 | 내장 경로 | ZXing 경로 | 뜻 |
|---|---|---|---|
| 1 | 전체 `1.00 × 1.00` | 밴드 `1.00 × 0.45` | 기본 |
| 2 | 밴드 `1.00 × 0.45` | 좁은 밴드 `1.00 × 0.22` | 잡음 제거·가장 빠름 |
| 3 | 사각 `0.80 × 0.60` | 사각 `0.80 × 0.60` | 라벨이 밴드를 벗어났을 때 |
| 4 | — | 전체 `1.00 × 1.00` | 마지막 수단 |

미검출이 쌓이면(3회) 뒤 순서를 앞으로 당기고, 전처리(ZXing)를 1단계 붙인다.

### 6. 검증 (구현 결과)

1. **가짜 디코더 루프 모사** — `tools/scan-check.js` · `npm run check:scan`
   가짜 시계·가짜 카메라·가짜 `BarcodeDetector` 를 끼워 **`scanner.js` 를 그대로** 돌린다.
   | 항목 | 세는 것 |
   |---|---|
   | S1 | 같은 값을 계속 검출해도 `repeatMs` 주기보다 자주 세지 않는다 |
   | **S2** | **실패가 섞인 채 한 장을 들고 있어도 2건이 되지 않는다** (핵심) + 떼었다 대면 그 수만큼 |
   | S3 | 성공 프레임이 싸져도 `reArmGap` 이 짧아지지 않는다 (`cost` 는 미검출만) |
   | S4 | 한 tick 의 디코딩 총시간 ≤ 예산 + 1회분 |
   | S5 | `stop()` 이 어느 `await` 사이에 와도 콜백·디코딩·타이머가 남지 않는다 |
   | S6 | 강등이 진동하지 않는다 (2회 연속 초과에서 1번 · 복귀 없음) |
   | S7 | ROI 계획 — 가로 ≥ 0.72 · 계획은 순열 · 1순위만 CODE_128 전용 |
   | S8 | 줌 — 쓸 수 있는 단계가 2개 미만이면 빈 배열(버튼을 숨긴다) · 범위 클램프 ·
          **안정화 대기 중에 멈춰도 `setZoomRaw` 가 끝난다**(UI 의 `zoomBusy` 가 풀린다) |
   | S9 | 합의(`consensus`)는 **연속** 프레임을 뜻한다 — 미검출이 끼면 처음부터 다시 센다 |

   | **S11** | 내장이 **늘 빈 결과**면 그림자 디코딩으로 읽고 갈아탄다 (라벨 수보다 많이 세지 않는다) + 느린 그림자에서 **문턱이 함께 커진다**(1.6초 공백을 2건으로 세지 않는다) |

   🔑 **중지 판정은 「코드가 더 들어왔나」 가 아니라 「다음 프레임을 예약했나」 로 센다.**
   예약된 프레임은 `running` 이 false 라 아무 일도 하지 않고 스스로 죽으므로, 결과만
   보면 좀비 루프가 보이지 않는다 (실제로 `throw-stop` 변이가 이 때문에 잡히지 않았다).

   🔑 **검사기는 변이로 검증했다.** `npm run check:scan -- --mutate=<이름>` 은 원본을
   건드리지 않고 임시 폴더에 고친 사본을 만들어 돌린다 (`--mutate=list` 로 목록).
   12가지 변이(`cost-hit` `rearm-short` `roi-narrow` `zoom-always` `budget-off`
   `leak-stop` `throw-stop` `settle-hang` `consensus-keep` `downgrade-again`
   `no-fallback` `shadow-count`)가 **각각 대응하는 항목을** 올리는 것을 확인했다.
   🔑 **ZXing 은 가짜로 갈아끼운다** — 실제 패키지는 브라우저 전용이라 노드에서 돌지
   않는다. 사본을 만들 때 `@zxing/*` **임포트 지정자 두 줄만** 가짜 모듈로 바꾼다.
   ⚠️ 시작 **자가 진단은 검사기가 세지 못한다** (`Image`·`Blob`·캔버스가 필요하다) —
   브라우저에서 확인한다. 검사기에서는 `barcode.js` 를 못 찾아 진단을 건너뛴다.
   ⚠️ `throw-stop` 은 이제 **재확인 두 곳을 함께** 뺀다 (catch 머리 + 전환 `await` 뒤).
   하나만 빼면 나머지가 막아 주어 결함이 드러나지 않는다.
   ⚠️ `zoom-always` 는 처음에 잡히지 않았다 — 난수 `caps.min` 이 3 미만이라
   **「쓸 수 있는 단계가 1개」인 입력이 한 번도 만들어지지 않았다.** 커버리지 카운터를
   보고 입력 범위를 넓혀 잡았다 (0건이 「없어서 0」인지 확인해야 하는 이유).

### 6-1. 내장 인식기 폴백 (2026-09-19) 🔑

> 현장 보고: **안드로이드 휴대폰에서 우리 앱만 바코드가 전혀 안 읽힌다**
> (다른 스캐너 앱·전용 스캐너는 잘 읽힘).

**원인** — `nativeReader()` 가 `new BarcodeDetector()` **생성 성공**을 곧 동작 가능으로 보고
그대로 썼다. 안드로이드 크롬은 Google Play 의 바코드 모듈이 깔려 있지 않으면 생성은
성공하는데 `detect()` 가 매번 던지거나(`NotSupportedError: Barcode detection service
unavailable`) **늘 빈 배열**을 준다. `tick()` 의 catch 는 `바코드 인식 실패` 만 찍고 **같은
인식기로 계속 돌아** 영원히 미검출이었다 (ZXing 경로는 「내장이 없는 기기」에서만 열렸다).

**대책은 셋이고, 셋 다 필요하다.** 기기가 고장을 알려주는 방식이 세 가지이기 때문이다.

| # | 언제 | 무엇을 하는가 | 코드 |
|---|---|---|---|
| ① 시작 자가 진단 | 인식기를 만든 직후 | `code128Svg('SELFTEST-128')` 를 캔버스에 그려 `detect()` 를 **한 번** 돌린다. 예외 또는 결과에 값이 없으면 내장을 버린다 | `selfTest` `selfTestCanvas` |
| ② 런타임 전환 | `detect()` 가 **던졌을 때** | 그 자리에서 `readerP` 를 ZXing 으로 바꾼다 (한 세션 1회 · 세대 토큰 확인) | `swapEngine` |
| ③ 그림자 디코딩 | 내장이 `shadowAfterMs`(4초) 이상 **조용할 때** | `shadowEveryN`(6) 프레임마다 **같은 프레임**을 ZXing 으로도 디코딩한다. ZXing 만 읽은 일이 `shadowSwitchHits`(2)회 쌓이면 내장을 버린다 | `shadowDue` + `tick` |

- ③이 따로 필요한 이유 🔑 — **예외도 안 던지고 늘 빈 결과**인 기기는 전환 신호가 없다.
  「한참 못 잡는 것」 자체를 신호로 본다. 그림자가 잡은 코드는 **곧바로 채택**한다
  (사용자 입장에서는 그냥 읽힌 것이다)
- ⚠️ **진단 자체의 실패(이미지를 못 그림)로는 폴백을 걸지 않는다.** 그림 실패와 인식기
  고장은 다르고, 잘못 버리면 멀쩡한 기기가 470KB 를 내려받는다. `console.warn` 만 남기고
  내장을 쓴다
- 자가 진단은 `start()` 의 **세대 토큰 뒤에서** 돌고, 각 `await` 마다 취소를 확인한다.
  `barcode.js` 는 **지연 로드**라 내장 인식기가 없는 기기는 진단 코드를 받지 않는다

**`cost` 규칙과의 정합** 🔴 — 2절의 규칙은 그대로다.
그림자 디코딩에 든 시간은 **그 tick 의 소요시간(`used`)에 포함**하되,
`cost` 이동평균에는 **여전히 미검출 tick 만** 들어간다. 그림자는 **예산이 남았을 때만**
붙여 「한 tick ≤ 예산 + 1회분」(S4)도 깨지 않는다.
🔑 그림자 시간을 빼면 느린 디코더의 문턱(`reArmGap`)이 짧아져 **한 파렛트가 2건**이 된다
(변이 `shadow-count` 가 이것을 재현하고 S11 이 잡는다).

**기억** — ①·②·③ 중 하나라도 일어나면 `localStorage.tpl_scan_engine = 'zxing'` 을 적어
**다음 실행부터 진단 없이 ZXing 을 쓴다.** 지우는 곳은 앱 **계정 화면의 `스캔 엔진 재검사`**
하나뿐이다 ([docs/mobile.md](mobile.md)).

**엔진 표시** — 프리뷰 좌하단에 `내장` / `ZXing` 태그가 뜬다 (전환 즉시 갱신).
스캐너 API 의 `engine()` · `onEngine(cb)` 가 값을 준다. 지원 문의 때 이 값으로 기기를 가른다.
