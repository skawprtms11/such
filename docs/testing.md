# 모바일 테스트 방법

> [CLAUDE.md](../CLAUDE.md) · 대상 화면: [출고주문처리](shipping.md), [검수](inspect.md)

바코드 스캔은 웹 브라우저만으로 확인하기 어렵다. 상황에 맞는 방법을 골라 쓴다.

---

## 요약

| 방법 | 카메라 스캔 | 준비 | 언제 쓰나 |
|---|:---:|---|---|
| 1. 수기 입력 | ❌ | 없음 | 업무 흐름만 빠르게 확인할 때 |
| 2. 브라우저 반응형 모드 | ✅ (PC 웹캠) | 없음 | 개발 중 대부분의 확인 |
| 3. 실기기 + HTTPS | ✅ (폰 카메라) | `npm run dev:https` | 현장과 같은 조건으로 확인할 때 |
| 4. 블루투스 스캐너 | — | 스캐너 | 실제 운영 장비로 확인할 때 |

**카메라는 HTTPS 또는 localhost 에서만 동작한다.**
휴대폰에서 `http://192.168.x.x:5173` 으로 접속하면 카메라가 차단된다.

---

## 0. 테스트용 바코드 준비

`barcodes.html` 에 **로그인한 계정이 볼 수 있는 주문**의 바코드가 자동으로 만들어진다.

⚠️ **이 페이지는 개발 전용이라 배포되지 않는다** (`vite.config.js` 의 빌드 entry 에서 제외).
개발 서버에서만 열린다.

```
http://localhost:5173/barcodes.html
```

- **주문번호** - 출고주문처리의 세 탭에서 스캔.
  **상차리스트 → 검수 화면에서도 같은 바코드를 파렛트 수만큼 스캔한다**
  (주문처리현황에서 출력하는 상차라벨의 바코드와 같다)
- **파렛트 바코드** - 상차라벨 도입 전 방식. 검수 화면에서 그대로 인식된다
- `인쇄` 버튼으로 종이에 뽑아 쓸 수 있다
- 외부 라이브러리 없이 `assets/js/barcode.js` 가 Code128 SVG 를 직접 그린다

두 번째 화면(또는 다른 기기)에 이 페이지를 띄워두고 스캔하면 편하다.

---

## 1. 수기 입력 (가장 간단)

스캔 없이도 모든 기능을 확인할 수 있다. 각 화면의 입력칸에 주문번호나 바코드를 직접 넣는다.

- 출고주문처리: `주문번호 (바코드 스캔 또는 직접 입력)` 칸
- 검수 화면: `바코드 직접 입력` 칸

스캔이 안 되는 상황에서도 항상 열려 있는 경로다.

---

## 2. 브라우저 반응형 모드 + PC 웹캠 (권장)

가장 빠르고 준비물이 없다.

1. `npm run dev` 후 크롬에서 `http://localhost:5173/app.html` 접속
2. **창 너비를 860px 이하로 줄인다** → 모바일 화면으로 자동 전환된다
   (개발자도구 F12 → 기기 툴바 Ctrl+Shift+M 도 동일)
3. `📷 스캔` 을 누르면 **노트북 웹캠**이 켜진다
4. 다른 창이나 휴대폰에 `barcodes.html` 을 띄워 웹캠에 비춘다

`localhost` 는 안전한 출처로 취급되므로 HTTPS 없이도 카메라가 동작한다.

---

## 3. 실기기(휴대폰) + HTTPS

현장과 같은 조건으로 확인할 때 쓴다.

```
npm run dev:https
```

출력되는 `Network: https://192.168.x.x:5173/` 주소를 휴대폰에서 연다.

- 자체 서명 인증서라 **경고 화면이 뜬다 → `고급` → `계속 진행`** 을 누른다
- 그 뒤에는 HTTPS 이므로 카메라가 정상 동작한다
- PC 와 휴대폰이 **같은 와이파이**에 있어야 한다
- 안드로이드·아이폰 모두 동작한다 (아래 지원 표 참고)

홈화면에 추가하면 PWA(앱처럼 전체화면)로도 확인할 수 있다.

---

## 4. 블루투스 바코드 스캐너

현장에서 실제로 쓰는 장비다. 스캐너는 **키보드처럼 동작**하므로 별도 연동이 필요 없다.

1. 입력칸에 커서를 둔다
2. 스캔하면 값이 입력되고 Enter 가 함께 전송되어 바로 조회된다

카메라 스캔이 안 되는 기기에서도 이 방법은 그대로 동작한다.

---

## 샘플 데이터 초기화

⚠️ **샘플 데이터는 제거했다.** 더미 계정·주문이 운영 배포본에 함께 실리기 때문이다.
`mock` 모드는 이제 **빈 상태로 시작하므로 로그인할 계정도 없다.**
화면 확인은 Supabase 모드로 한다.

아래 초기화는 **mock 모드에서 남은 데이터를 비울 때만** 쓴다.

```js
const db = await import('/assets/js/db.js');
await db.resetDb();
location.reload();
```

Supabase 모드(`VITE_DATA_SOURCE=supabase`)는 실제 서버 데이터라 이 방법이 막혀 있다.
정리가 필요하면 Supabase SQL Editor 에서 직접 지운다.
서버 없이 화면만 확인하려면 `.env.local` 의 `VITE_DATA_SOURCE` 를 `mock` 으로 바꾼다.

## 참고: 브라우저별 카메라 스캔 🔑

| 환경 | 카메라 스캔 | 인식 방식 |
|---|:---:|---|
| 안드로이드 크롬 | ✅ | 내장 `BarcodeDetector` |
| 데스크톱 크롬 / 엣지 | ✅ | 내장 `BarcodeDetector` |
| **iOS 사파리 · 크롬** | ✅ | **ZXing** (내려받아 처리) |
| 파이어폭스 | ✅ | ZXing |

### iOS 는 크롬을 써도 내장 인식기가 없다

**아이폰은 크롬·엣지·파이어폭스도 전부 애플의 WebKit 엔진을 쓴다.**
겉모습만 다를 뿐 사파리와 같은 엔진이라, 크롬으로 바꿔도 `BarcodeDetector` 는 없다.

그래서 `assets/js/scanner.js` 는 인식기를 두 갈래로 만든다.

```js
if (hasNativeDetector()) { /* 내장 BarcodeDetector */ }
else { const { BrowserMultiFormatReader } = await import('@zxing/browser'); }
```

- ZXing 은 **내장 기능이 없을 때만 동적으로 내려받는다** (약 470KB, 별도 청크)
  안드로이드·데스크톱 크롬 사용자는 이 파일을 받지 않는다
- 카메라 자체(`getUserMedia`)는 iOS 사파리·크롬 모두 지원하므로 스캔이 동작한다
- **여전히 HTTPS 는 필요하다.** `npm run dev:https` 로 접속한다

## 카메라 인식률 🔑

`assets/js/scanner.js` 맨 위 **`TUNE` 한 곳**에 인식률에 관계된 값이 모여 있다.
현장에서 잘 안 읽히면 이 상수만 조정하고, 문제가 생기면 그대로 되돌린다.

| 값 | 기본 | 뜻 · 조정 방향 |
|---|---|---|
| `nativeSize` | 1920×1080 | 내장 인식기용 요청 해상도. 기기가 느리면 1280×720 으로 낮춘다 |
| `zxingSize` | 1280×720 | iOS 등 ZXing 경로 해상도. 더 낮추면 빨라지지만 가는 바가 뭉개진다 |
| `roi` | 세로 45% | 조준 밴드 - **ZXing 경로만** 이 안쪽을 잘라 디코딩한다 |
| `fullFrameEvery` | 4 | 밴드에서 4번 연속 실패하면 한 번은 전체 화면으로도 본다 |
| `minGapMs` | 60 | 찾는 중의 프레임 간격(≈16회/초). 발열이 심하면 100~120 으로 올린다 |
| `idleGapMs` / `idleAfterMs` | 180 / 2000 | **2초간 아무것도 안 잡히면** 간격을 늘려 발열·배터리를 아낀다 |
| `repeatMs` / `reArmMs` / `reArmFrames` | 2500 / 1500 / 5 | 같은 라벨을 다시 받는 조건 (아래 참고) |

- **해상도는 `ideal` 로만 요청한다.** 못 맞추는 기기도 거절하지 않고 가장 가까운 값을 준다
- **연속 오토포커스**(`focusMode: 'continuous'`)는 기기가 지원할 때만 적용한다
- **플래시 버튼**은 프리뷰 오른쪽 위에 뜨고, **토치를 지원하는 기기에서만** 나타난다
  (대개 안드로이드 후면 카메라. iOS 사파리는 지원하지 않아 버튼이 없다)
- 화면에 바코드가 여러 개 잡히면 **조준 밴드 가운데에 가장 가까운 것**을 고른다

### 같은 라벨을 연달아 스캔할 때 🔑

상차검수는 **같은 주문번호 라벨을 파렛트 수만큼** 찍는다. 그래서 같은 값이 다시 들어오는 것이
정상이고, 판정을 어느 쪽으로 틀리든 사고가 난다.

| 너무 엄격하면 | 너무 느슨하면 |
|---|---|
| 빨리 찍는 사람에게 "안 읽힌다" 로 보인다 | **한 파렛트가 2건으로 세어진다** |
| 직접 입력으로 우회 가능 | 실물은 남았는데 진행률 100% → 파렛트 누락 출고 |

오른쪽이 훨씬 위험하므로 **보수적으로** 잡았다.

- 라벨을 계속 비추고 있으면 **2.5초**(`repeatMs`) 동안 다시 세지 않는다
- 다음 1건으로 세려면 **라벨이 그만큼 비어 있어야** 한다 —
  `reArmMs`(1.5초)와 `reArmFrames × 디코딩 1회 소요시간`(5배) 중 **큰 쪽**
- 두 번째 조건이 있는 이유: iOS·ZXing 은 디코딩 1회가 100~400ms 라, 라벨을 든 채
  초점 재조정·손떨림으로 몇 번 실패하면 **"라벨을 치웠다" 로 오해**해 두 번 세어진다.
  기기가 느릴수록 문턱이 자동으로 커진다 (400ms × 5 = 2초)
- 실사용에서 파렛트를 옮기는 간격은 1초를 넘으므로 누락 부작용은 거의 없다.
  그래도 못 세면 **직접 입력**으로 넣는다 (쿨다운이 없다)

### 실기기에서 확인할 것

`npm run dev:https` 로 폰에서 접속해 `m.html#/load` 상차검수·`#/stow` 로케이션에서 본다.

1. 프리뷰에 **점선 밴드**가 보이고, 밴드 가운데 빨간 선에 바코드를 맞추면 읽히는가
2. 파렛트 라벨을 **연속으로 3~4장** 찍을 때 **찍은 수와 카운트가 정확히 같은가**
   (같은 번호여도 된다. **라벨을 한 장씩 떼었다 대는** 방식으로 확인한다)
   - ⚠️ **찍은 수보다 카운트가 많으면 즉시 보고** — 실물은 안 찍힌 파렛트가 남았는데
     진행률이 100% 가 되어 **파렛트 누락 출고**로 이어진다. `TUNE.reArmMs` 를 올려야 한다
   - 🔑 **한 장을 떼지 않고 계속 비추면 2.5초마다 1건씩 오르는 것이 정상이다**
     (`TUNE.repeatMs` · 구버전부터 같다). 이걸 결함으로 보고하지 않는다 —
     상차검수는 같은 번호 라벨을 파렛트 수만큼 찍는 업무라 계속 비추는 것을 영구히
     막으면 정상 작업이 멈춘다
3. 어두운 곳에서 **플래시 버튼**이 보이는가 (안드로이드) · 눌러 켜지는가
4. 화면을 떠나거나 `중지` 를 누르면 **프리뷰와 플래시가 함께 꺼지는가**
5. 앱을 백그라운드로 보냈다 돌아오면 프리뷰가 멈춰 있지 않은가
6. 카메라를 켠 직후(1~3초 안에) **세그를 바꾸거나 화면을 떠나도** 폰이 계속 뜨거나
   느려지지 않는가 (준비 중 이탈 시 루프가 남지 않아야 한다)
7. 5분 이상 켜 둔 채 작업할 때 발열이 견딜 만한가 — 심하면 `minGapMs` 를 100~120,
   `nativeSize` 를 1280×720 으로 낮춘다 (인식률보다 발열이 먼저 문제라면 이 순서)

### 그래도 안 될 때

- HTTPS 로 접속했는지 확인한다 (`http://` 면 카메라가 차단된다)
- 카메라 권한을 허용했는지 확인한다 (설정 → 사파리/크롬 → 카메라)
- 안 되면 **수기 입력**이나 **블루투스 스캐너**를 쓴다. 두 경로는 항상 열려 있다
