# 사용자관리

> 코드 `assets/js/pages/users.js` · 라우트 `#/users` · [공통 규약](common.md) · [CLAUDE.md](../CLAUDE.md)

계정의 권한과 사용 여부를 관리하는 화면. **관리자 전용**이다.

---

## 접근 권한

**관리자만 진입할 수 있다.** 다른 역할에게는 메뉴 자체가 보이지 않는다.

```js
// config.js — 메뉴 정의
{ key: 'users', path: '#/users', label: '사용자관리', icon: '👥', adminOnly: true }
```

`app.js` 가 두 겹으로 막는다.

1. `MENUS` 필터 — 관리자가 아니면 사이드바·탭바에 그리지 않는다
2. 라우팅 시 재확인 — URL 을 직접 입력해도 "접근 권한이 없습니다" 를 표시한다

이 화면은 다른 화면과 달리 `render(root)` 만 받는다. `user` 인자를 쓰지 않는다
(진입 자체가 관리자로 제한되므로 화면 안에서 다시 판정할 필요가 없다).

⚠️ 현재는 화면단 차단일 뿐이다. **실제 차단은 Supabase RLS 의
`profiles_update` 정책**(`current_role() = 'admin'`)이 담당한다.

## 핵심 로직

### 권한 변경 🔑

select 를 바꾸는 **즉시** `db.updateUserRole()` 이 호출된다.
저장 버튼이 없고 확인 대화상자도 없다.

```js
el.addEventListener('change', async () => {
    await db.updateUserRole(el.dataset.role, el.value);
    toast('권한이 변경되었습니다.', 'success');
    reload();
});
```

⚠️ **자기 자신의 권한도 바꿀 수 있다.** 관리자가 스스로를 다른 역할로 내리면
이 화면에 다시 들어올 수 없게 된다. 현재 이를 막는 장치가 없다.

변경 사항은 대상 사용자의 **다음 화면 조회**부터 적용된다.
이미 로그인된 세션의 사용자 객체는 즉시 갱신되지 않는다 (화면 하단 안내 문구 참고).

### 사용여부 토글

`db.toggleUserActive()` — 확인 대화상자를 거친다.
`중지` 상태일 때 버튼이 빨간 테두리(`.btn--danger`)로 바뀐다.

**중지된 계정은 로그인이 차단된다.**

```js
// auth.js — signIn()
if (!user.active) throw new Error('사용이 중지된 계정입니다. 관리자에게 문의하세요.');
```

단, **이미 로그인된 세션은 끊기지 않는다.** 계정을 중지해도 그 사용자가
브라우저를 닫기 전까지는 계속 사용할 수 있다.

### 사용자 추가

| 항목 | 필드 | 필수 | 비고 |
|---|---|:---:|---|
| 이름 | `name` | ✅ | |
| 이메일 | `email` | ✅ | `type=email` 검증 |
| 소속 | `company` | ✅ | 기본값 `더퓨어랩` |
| 연락처 | `phone` | | |
| 권한 | `role` | ✅ | |

`active: true` 로 생성된다. **비밀번호 항목이 없다.**

### 정보 수정 · 삭제 · 비밀번호 초기화 🔑

| 기능 | 동작 |
|---|---|
| **수정** | 이름 · 이메일 · 소속 · 연락처 · 권한을 고친다. 이메일은 로그인 ID 라 `auth.users` 까지 함께 바뀐다 |
| **삭제** | 로그인 계정까지 지운다. ⚠️ **등록한 주문이 남아 있으면 거부된다** — 이력이 끊기기 때문이다. 본인 계정도 삭제할 수 없다 |
| **비밀번호 초기화** | `config.js` 의 `INITIAL_PASSWORD`(`1318`) 로 되돌리고, 그 값을 팝업으로 알려준다 |

세 기능 모두 **관리자 전용 서버 함수**(`admin_update_user` · `admin_delete_user` ·
`admin_reset_password`)를 거친다. 로그인 계정(`auth.users`)은 anon 키로 건드릴 수 없어
`security definer` 함수로 처리하며, **함수 안에서 호출자가 관리자인지 다시 확인한다.**

- 초기화한 비밀번호는 본인에게 알려주고 **로그인 후 바꾸도록** 안내한다
- 잠시 막아둘 목적이면 삭제 대신 **사용여부 중지**를 쓴다

⚠️ **Supabase 모드에서는 이 화면으로 사용자를 만들 수 없다** (`db.createUser()` 가 막는다).
로그인 계정(`auth.users`)이 함께 있어야 하기 때문이다. 다음 순서로 만든다.

1. Supabase 대시보드 → Authentication → Users → `Add user` (이메일·비밀번호 입력)
2. SQL Editor 에서 `profiles` 행 추가 — 만든 계정의 `id` 를 그대로 쓴다

```sql
insert into public.profiles (id, name, email, company, role, phone)
values ('<auth 에서 만든 uuid>', '홍길동', 'hong@example.com', '고객사', 'shipper_sales', '');
```

권한·소속 변경과 사용중지는 이 화면에서 그대로 할 수 있다.
초대 메일 발송 방식은 서버(Edge Function)가 필요해 아직 붙이지 않았다.

## 역할 정의

`config.js` 의 `ROLE` / `ROLE_LABEL` / `PERMISSION` 세 곳이 한 벌이다.
역할을 추가하려면 **세 곳을 모두** 수정하고, 배지 색상(`.role--*`)도 CSS 에 추가한다.

| 코드 | 표시 | 배지 색 |
|---|---|---|
| `admin` | 관리자 | 보라 |
| `yongma` | 용마담당자 | 파랑 |
| `shipper_admin` | 화주관리자 | 초록 |
| `shipper_sales` | 화주영업팀 | 주황 |

권한 매트릭스는 [CLAUDE.md](../CLAUDE.md#4-권한) 참고.

## 수정 시 주의

- **연번이 정순이다.** 다른 화면(역순)과 다르니 통일하려 하기 전에 의도를 확인한다
- 권한 변경에 확인 절차가 없다. 실수 방지 장치를 넣는다면 자기 자신의 권한 강등을
  먼저 막는 것이 효과적이다
- 역할 추가 시 `ROLE` `ROLE_LABEL` `PERMISSION` + CSS `.role--*` 네 곳을 함께 고친다
- Supabase 연동 시 이 화면은 `profiles` 테이블을 다루게 되며,
  계정 생성은 `auth.users` 초대 흐름과 연결되어야 한다
