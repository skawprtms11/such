### 2026-09-04 — [개발팀] 묶음 키 하나로 모든 단계를 묶어 데드락을 만들었다

**상황**: 대표주문번호(`rep_no`) 도입 시 `groupKeyOf = rep_no > base_no > order_no`
묶음 키 하나로 접수·출고작업·검수·상차를 **전부** 일괄 처리하도록 구현.
**실수/오판**: 추가주문 차수(`base_no`)까지 일괄 처리 범위에 넣었다.
그 결과 `setShipWorkDone` 의 `rows.some(r => r.inspect_done_at)` 가드가
**1차수 검수 완료 후 등록된 추가주문의 출고완료를 영구 차단**했다 (데드락).
**원인**: "함께 배송되니 함께 처리하면 된다" 고 업무 흐름을 단순화했다.
상차는 함께여도 **작업 진행 시점은 차수마다 다르다**는 점을 놓쳤다.
**교훈**:
  1. 묶음(그룹) 개념을 도입할 때 **단계별로 적용 범위를 표로 먼저 그린다.**
     하나의 키로 모든 단계를 묶지 않는다.
  2. 일괄 처리는 항상 `rows.filter(미완료)` 를 대상으로 한다.
     `rows.some(...)` 전체 가드는 나중에 합류한 멤버를 영구 차단한다.
  3. 목록의 완료 판정도 대표(head)가 아니라 `rows.every(...)` 로 본다.
**파일**: `assets/js/db.js` (`groupFor` · `setShipWorkDone`) ·
`assets/js/pages/shipping.js` (`rowDone`) · `CLAUDE.md` 3-1 절

### 2026-09-16 — [dev-team] 새 동작을 넓게 열어 두고 화면부터 만들었다

**무엇**: 「주문합치기」 1차 구현이 합치기 허용 조건을 사실상 두지 않았다.
같은 거래처·등록자만 보고 **진행 단계 · 기존 묶음 소속 · 차수 형제 · 출고요청일**을 모두 열어 둬,
코드리뷰팀·DB팀이 🔴 4건을 잡았다.

**왜 위험했나**
- 총 파렛트·박스는 **묶음 대표에만** 실린다. 대표인 주문이 다른 묶음으로 빠지면 남은 묶음이
  0파렛트가 되어 당일상차리스트에는 뜨는데 검수·상차완료가 막히는 **교착**이 된다
- 진행 단계가 다른 주문을 합치면 파렛트 0건 멤버가 상차검수에서 자동 통과 판정을 받아
  **검수·적치를 건너뛴 채 상차완료·마감**까지 올라간다
- 차수 형제를 합치면 접수·출고·검수가 통째로 묶여 2026-09-04 항목과 같은 경로로 들어간다

**배운 것**
  1. **상태를 바꾸는 새 동작은 허용 조건부터 좁게 못 박고 시작한다.** 넓게 열어 두면
     기존 불변식(«총량은 대표에만», «차수는 따로 처리»)이 어디서 깨지는지 보이지 않는다
  2. 이미 있는 묶음·상태 개념에 **새 진입 경로**를 만들 때는, 그 개념이 **빠져나가는**
     경우(이탈·해제)를 반드시 함께 설계한다. 들어오는 길만 만들면 데이터가 고아가 된다
  3. 선재 결함이 새 기능으로 **도달 가능해지는지** 확인한다. 이번 `listLoading` 의
     묶음 재확장은 원래 있던 결함이지만 합치기가 한 번의 클릭으로 그 상태에 넣었다
  4. 도메인 감사팀(DB팀)을 코드리뷰와 **병렬로** 붙인 것이 🔴 2건을 잡았다.
     묶음·정산·단계 전이를 건드리는 작업에는 코드리뷰만으로 부족하다

**파일**: `assets/js/db.js`(`mergeOrders` `listMergeTargets` `listLoading`) · `docs/orders.md`

### 2026-09-16 — [dev-team] 같은 판정을 화면마다 다시 짜서 모집단이 갈렸다

**무엇**: 「주문합치기」 2차 구현에서 «주문마다 자기 파렛트를 가진 묶음인가» 를
`status.js` `inspect.js` `shipping.js` `mobile/inspect.js` **네 곳이 제각각** 판정했다.
기준도(파렛트 행 수 vs `pallet_count`) 모집단도(상차 묶음 vs 대표주문번호 묶음) 달라,
같은 데이터에서 화면마다 다른 결론이 났다 (🔴 3건).

**왜 위험했나**
- `status.js` 는 `loadGroups`(rep ∪ 차수)로 판정하면서 표 행은 `repGroups` 로 그렸다.
  모집단이 어긋나 **대표번호 라벨 경로가 사라지고** 같은 출력 버튼이 두 행에 생겼다
- 총량 수정 대상이 **저장 함수 안에서 조용히 뒤집혀**, 화면에 보이는 값과 고쳐지는 값이
  달라졌다 (모바일은 멤버 값을 보여주고 대표에 저장)
- `inspected >= pallet_count` 가 0파렛트 멤버에서 `0 >= 0` 으로 늘 참이라,
  **검수도 안 끝난 주문이 남의 라벨 스캔만으로** 상차완료·마감까지 올라갔다

**배운 것**
  1. **판정 함수는 db.js 에 하나만 둔다.** 화면이 같은 뜻의 조건을 다시 쓰는 순간
     기준이 갈린다 (2026-09-05 항목의 재발이다)
  2. 묶음 판정 함수에는 **모집단을 JSDoc 에 못 박는다.** «어느 묶음을 넘겨야 하는가» 가
     함수 이름에 안 드러나면 호출자가 손에 든 것을 그냥 넘긴다
  3. **대상이 데이터 상태에 따라 뒤집히는 로직을 저장 함수 안에 넣지 않는다.**
     «대상을 알려주는 조회 함수» + «넘긴 것을 그대로 고치는 저장 함수» 로 나누면
     보이는 값과 고쳐지는 값이 항상 같다
  4. `a >= b` 형태의 완료 판정은 **`b === 0` 일 때 무조건 참**이 된다.
     0건이 정상인 대상(혼적·0파렛트)이 있으면 그 분기를 따로 적는다
  5. 상태를 쓰는 함수(`completeLoading`)는 **쓰기 직전에 전제를 다시 확인**한다.
     목록 조회에서 걸렀다는 것만 믿으면, 묶음을 다시 펼치는 경로로 뚫린다

**파일**: `assets/js/db.js`(`hasSplitPallets` `countTarget` `scanDone` `completeLoading`
`listLoading` `stepGapReason`) · `assets/js/pages/status.js`(`repGroupMap`) ·
`docs/orders.md` `docs/loading.md` `docs/shipping.md`

### 2026-09-17 — [dev-team] 도식 불변식을 문서에만 적고 코드로 강제하지 않았다

**무엇**: 업무프로세스 도식을 세로로 바꾸면서 무교차 근거(V1~V6)를 문서에 적어 두고
코드에는 서로 모르는 상수 둘로 남겼다. ① `gapX 40` < 들여쓰기 상한 `48` 이라 2단
들여쓴 카드가 옆 열 카드와 8px 겹쳤다(V2 위반 · 랜덤 4000트리 중 98건). ② 형제 사슬의
`spineTail` 이 갈래 부모에 `null` 을 주는데 호출부가 `?? prev` 로 **부모 카드에서 곧장**
내려 갈래 첫 카드를 관통했다(1401건). SVG 가 카드 뒤에 깔려 화면에서는 「부모 → 갈래
첫 카드 → 다음 형제」 로 **잘못 읽히기만 하고 티가 나지 않았다**.
**원인**: 순차(seq) 판만 고쳐 놓고 같은 원리의 갈래(fork) 판을 빠뜨렸다. 검증도
손으로 만든 예시 트리로만 했는데 그 예시가 전부 합류(`join`)라 비합류 경로를 비켜갔다.
**교훈**:
  1. **두 상수가 서로를 알아야 하는 관계면 한쪽을 다른 쪽에서 파생시킨다.**
     여기서는 `colGap() = max(gapX, 들여쓰기*2 + 8)` 한 곳으로 모아 레인 폭 계산과
     좌표 계산이 같은 값을 쓰게 했다. 문서에 적은 불변식은 강제 수단이 아니다.
  2. **「A 일 때 고쳤다」 면 A 의 대칭 경우(fork ↔ join · null 이 나오는 다른 경로)를
     같이 센다.** `spineTail` 은 갈래 부모뿐 아니라 **마지막 하위가 갈래인 순차 부모**
     에서도 `null` 이라 같은 버그가 한 겹 더 있었다.
  3. **순수 함수는 랜덤 입력으로 불변식을 센다.** 예시 트리로는 높이·깊이·갈래 조합이
     몇 가지 안 나온다. `tools/checkflow-check.js` (P1~P7)를 남겼다 —
     배치 코드를 건드리면 `npm run check:flow`.
  4. 검사기 자체도 검증한다. 처음 만든 교차 판정이 **폭 0 인 세로선을 못 잡아**
     수정 전 코드에서도 P2 가 0건으로 나왔다. **옛 코드에 돌려 결함이 재현되는지**
     먼저 확인하고 나서 통과를 믿는다.
**파일**: `assets/js/checkflow.js`(`colGap` `blockNextEdge` `spineTail`) ·

### 2026-09-17 — [dev-team] 스캔 루프를 빠르게 만들면서 "중복 판정"의 위험 방향을 거꾸로 봤다

**무엇**: 카메라 인식률을 올리려고 프레임 주기를 400ms → 40ms 로 줄이고, 같은 라벨을
다시 받는 조건을 「2프레임 이상 미검출 + 0.6초」로 완화했다. 그런데 40ms 주기에서
0.6초는 이미 15프레임이라 **프레임 조건이 아무 것도 막지 않았고**, 실질 조건이
「0.6초 디코딩 공백」 하나만 남았다. iOS·ZXing 은 디코딩 1회가 100~400ms 라 라벨을
**든 채로** 2~3회 실패하면 조건이 충족되어 **한 파렛트가 2건으로 계수**된다
(진행률 100% → 상차완료 → 파렛트 누락 출고). 같이 넣은 세 가지도 검수에서 걸렸다 —
`start()` 의 await 구간(최대 3초) 중 `stop()` 이 오면 루프가 살아나는 좀비,
`await read()` 뒤 `running` 재확인 누락으로 중지 후 1건 유출, 문서 3개 값 불일치.
**원인**:
  1. 인식률(못 읽힘)만 실패로 보고 **과다 인식**을 실패로 세지 않았다. 두 방향의
     피해 크기가 다른데(누락은 즉시 보이고 재스캔하면 끝, 과다는 조용히 데이터가 틀림)
     완화 쪽으로만 값을 잡았다.
  2. **시간 상수와 프레임 수 상수를 나란히 놓고 "둘 다 만족" 이라고 안심했다.**
     서로 단위가 달라 한쪽이 항상 먼저 충족되면 그 조건은 없는 것과 같다.
  3. 비동기 시작 절차에 **세대 토큰이 없었다.** `if (stream)` 같은 플래그는 await 뒤에야
     채워지므로 준비 중 이탈·연타를 막지 못한다.
**교훈**:
  1. **양방향 실패를 먼저 적고 값을 정한다.** "안 읽힘 / 두 번 읽힘" 중 어느 쪽이
     데이터를 조용히 망가뜨리는지 보고 그 반대쪽으로 보수적으로 잡는다.
  2. **조건 둘의 단위가 다르면 하나를 다른 하나로 환산해 한 식으로 만든다.**
     여기서는 `max(reArmMs, reArmFrames × 디코딩 1회 소요시간)` 으로 합쳐, 느린 기기에서
     자동으로 더 엄격해지게 했다. 상수를 나란히 두면 같은 실수가 재발한다.
  3. **`await` 가 있는 start/stop 쌍에는 세대 토큰을 둔다.** await 마다 뒤에서
     `if (취소) 정리하고 반환`, 콜백 직전에 `if (!running) return`.
  4. **실기기가 없어도 루프는 모사해 센다.** 가짜 디코더(소요시간·검출 패턴 지정)로
     이중 카운트·좀비 루프·중지 후 유출을 스크립트로 재현해 확인했다.
**파일**: `assets/js/scanner.js`(`TUNE` `reArmGap` `accepts` `start` `stop` `tick`) ·
`docs/inspect.md` · `docs/mobile.md` · `docs/testing.md`

### 2026-09-17 — [dev-team] 간선 하나만 다른 기준을 쓰게 두었다 (선이 허공에서 시작)

**무엇**: 갈래 카드 관통(D2)을 고치면서 `blockNextEdge` 의 출발점을 **서브트리 바닥**
(`bottomOf`)으로 바꿨다. 그런데 바닥 카드는 갈래로 벌어진 **다른 열**일 수 있어, 부모 열의
그 높이에는 카드가 없다 — 관통은 없어졌지만 **선이 허공에서 시작**했다
(랜덤 4000트리에서 `blockNextEdge` 3378회 중 1391회 = 41%). 다른 모든 간선(부모→첫 하위 ·
`forkEdges` · `joinEdges`)은 카드 바닥에서 출발하는데 **이 하나만 규칙에서 벗어났고**,
검사기에 그 규칙(V7 간선 부착)이 없어 P1~P7 이 전부 0건으로 통과했다.
**원인**:
  1. 「카드를 지나지 않는다」 만 목표로 잡고 **「카드에 붙는다」 는 목표를 적지 않았다.**
     두 조건을 함께 적으면 `bottomOf` 는 후보가 되지 못한다.
  2. 고칠 때 **다른 간선들이 쓰는 기준을 확인하지 않았다.** 같은 종류의 출력(간선)에
     기준이 둘이면 반드시 한쪽이 틀린다.
  3. 검사기가 **개수(P7)와 관통(P2)만** 보고 있었다. 개수는 오배선을, 관통은 미부착을
     못 본다 — 둘 다 「0건」 이라 안심했다.
**교훈**:
  1. **결함을 고칠 때 「하면 안 되는 것」과 「반드시 해야 하는 것」을 함께 적는다.**
     여기서는 「어떤 카드도 지나지 않는다 + 카드 경계에서 출발한다」 두 조건을 동시에
     만족하는 유일한 점이 **같은 열의 가장 아래 카드 바닥**(`colTail`)이었다.
     갈래 첫 하위가 부모와 같은 열에 놓이므로 그 카드는 언제나 있다.
  2. **같은 종류의 출력은 기준을 하나로 통일하고, 그 기준을 검사기에 넣는다.**
     P8(부착) · P9(화살촉) · P10(연결 상대)을 추가했다. 규칙을 문서에만 적으면 다음 수정이
     또 벗어난다.
  3. **검사기의 파서는 모르는 입력을 조용히 넘기면 안 된다.** `points()` 가 `M`·`V` 외
     모든 명령을 `H` 로 읽어, 곡선(`C`)이나 상대좌표(`l`)를 쓰면 엉뚱한 좌표로 전부
     통과했다. 지금은 실패로 센다.
  4. **검사기는 변이로 검증한다.** 곡선 도입 · 화살촉 규격/위치 깨기 · 옛 D2 버그 부활 ·
     부모→첫 하위 간선을 둘째에 붙이기 — 네 가지를 넣어 해당 항목이 올라오는 것을 보고
     「0건」 을 믿었다.
  5. **순수 함수 검사는 치수도 바꿔가며 돌린다.** 기본값으로만 돌리면 `colGap()` 파생
     (들여쓰기 > `gapX`)과 `laneWidth` 의 간격 인자 누락이 드러나지 않는다.
**파일**: `assets/js/checkflow.js`(`colTail` `blockNextEdge` `laneWidth`) ·
`tools/checkflow-check.js`(P8~P10 · `points` · 치수 5조합) · `docs/checklist.md`

### 2026-09-19 — [code-review-team] 되돌릴 수 없는 값의 저장 실패에서 캐시를 버리지 않았다

**무엇**: 유통가공 작업지시서 채번(`issueProcessDoc`)이 `unique(doc_no)` 충돌만 재시도하고,
그 밖의 저장 실패(네트워크·RLS)는 `invalidate()` 없이 다시 던졌다. `db` 는 `store.js` 의
캐시와 같은 객체라 실패한 문서번호가 메모리에 남고, 0.7초 안의 다른 저장이 `pushChanges` 로
그 번호를 서버에 밀어 넣을 수 있었다. 같이 잡힌 것 — 수정 팝업은 스냅샷(`qty_per`)으로,
저장은 현재 마스터로 필요수량을 계산해 마스터가 바뀌면 화면은 「합계 맞음」 인데 저장은 거부.
**원인**:
  1. 재시도 분기만 생각하고 **실패의 나머지 경우**를 적지 않았다. 되돌릴 수 없는 값
     (문서번호)은 실패 경로마다 캐시가 어떻게 남는지 봐야 한다.
  2. 같은 계산(필요수량)을 화면 3곳에 인라인으로 복제했고, 정작 `db.js` 의 export 는
     쓰이지 않았다 (2026-09-16 「같은 계산을 화면마다 다시 짜서 갈렸다」 재발 자리).
**교훈**:
  1. **되돌릴 수 없는 값을 쓰는 함수는 모든 실패 경로에서 `invalidate()`** — 재시도 여부와
     무관하게 캐시를 버리고 다시 읽는다.
  2. **화면이 보여 주는 검증과 저장이 거부하는 검증은 같은 입력을 봐야 한다.** 스냅샷과
     현재 마스터 중 하나로 통일하고, 순수 함수(`needQty`) 한 곳을 쓴다.
  3. 화면이 항상 보내는 값이라도 **db 는 「빠진 경우」를 조용히 채우지 않는다**
     (제품 LOT 줄 누락 → 거부). 조용한 기본값은 화면 버그를 정상 저장으로 바꾼다.
**파일**: `assets/js/db.js`(`issueProcessDoc` `buildJobItems` `updateProcessJob`) ·
`assets/js/pages/processing/jobform.js` · `assets/js/processing-calc.js`(`needQty`) ·
`docs/processing.md`

### 2026-09-19 — [db-guard-team] 새 역할에 권한을 주면서 기존 테이블의 UPDATE 정책을 안 봤다

**무엇**: 모바일 검수 권한을 `updateStatus`(현장작업자 포함)로 정하고 새 테이블·버킷 정책은
전부 그렇게 맞췄는데, **상태를 찍는 대상인 `process_jobs` 의 UPDATE 정책**은 이전 판의
`can_manage_processing()` 그대로였다. 현장작업자가 검수를 끝내면 사진은 올라가고
`pre_check_at` UPDATE 는 RLS 로 0행이 되는데, PostgREST 는 오류를 주지 않아 앱은
성공 토스트를 띄웠다. mock 모드는 RLS 를 타지 않아 브라우저 29항목이 전부 통과했다.
**원인**:
  1. 권한 축을 하나 늘리면서 「새로 만드는 것」만 맞추고 「이미 있는 것 중 그 역할이
     건드려야 하는 것」을 열거하지 않았다.
  2. `store.js` 가 update 결과 행 수를 보지 않아 RLS 무음 실패가 성공으로 보였다.
**교훈**:
  1. **역할이 새 동작을 얻으면 그 동작이 쓰는 모든 테이블의 정책을 표로 적고 대조한다.**
     insert 하는 테이블뿐 아니라 update 하는 테이블(상태 컬럼이 있는 부모)까지.
  2. **쓰기 결과는 되읽는다.** `pushChanges` 가 `.select('id')` 로 반영 행 수를 확인하고
     0행이면 예외를 던진다 (select 정책이 좁은 테이블은 `scopedSelect` 로 예외 표시).
  3. **RLS 위의 동작은 mock 으로 증명되지 않는다.** 적용 후 실 계정으로 확인할 항목을
     문서에 적어 둔다 (`docs/processing.md` §17-8).
**파일**: `supabase/schema.sql`(`process_jobs_update` `enforce_process_check_cols`) ·
`assets/js/store.js`(`pushChanges` `scopedSelect`) · `docs/processing.md`
