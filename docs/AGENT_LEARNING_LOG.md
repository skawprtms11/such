> 모든 팀(부장·dev-team·감사팀·검수팀·consultant)이 공유하는 실수·교훈 기록.
> **세션 시작 시 필독.** 새 항목은 하단에 append (시간 역순 X — 추가 순서 보존).

## 📐 형식

```markdown
### YYYY-MM-DD — [팀명] 한 줄 제목

**상황**: 무엇을 하다가 발생했는지 1~2줄
**실수/오판**: 무엇이 잘못됐는지
**원인**: 왜 그렇게 됐는지 (구조적·인지적)
**교훈**: 다음에 어떻게 다르게 할 것인지
**파일**: 관련 파일:라인 (있으면)
```

### 2026-08-31 — [부장] 하네스 부장 시스템 도입

**상황**: 본 프로젝트에 하네스 부장 다중 에이전트 시스템 도입.
**원인**: 코드 작업이 단일 에이전트로는 검수가 약하고, 톡방 가시성 없이는 "어디서 막혔는지" 파악이 어려움.
**교훈**: 작업마다 `harness_messages` INSERT를 빠뜨리지 말 것. 모든 단계가 톡방에 보여야 대표님이 진행 파악 가능.
**파일**: `.claude/agents/*.md` · 톡방: `bujang chat`

### 2026-09-04 — [개발팀] 묶음 키 하나로 모든 단계를 묶어 데드락을 만들었다

**상황**: 대표주문번호(`rep_no`) 도입 시 `groupKeyOf = rep_no > base_no > order_no`
묶음 키 하나로 접수·출고작업·검수·상차를 **전부** 일괄 처리하도록 구현.
**실수/오판**: 추가주문 차수(`base_no`)까지 일괄 처리 범위에 넣었다.
그 결과 `setShipWorkDone` 의 `rows.some(r => r.inspect_done_at)` 가드가
**1차수 검수 완료 후 등록된 추가주문의 출고완료를 영구 차단**했다 (데드락).
**원인**: "함께 배송되니 함께 처리하면 된다" 고 업무 흐름을 단순화했다.
상차는 함께여도 **작업 진행 시점은 차수마다 다르다**는 점을 놓쳤다.
**교훈**:
  1. 묶음(그룹) 개념을 도입할 때 **단계별로 적용 범위를 표로 먼저 그린다.**
     하나의 키로 모든 단계를 묶지 않는다.
  2. 일괄 처리는 항상 `rows.filter(미완료)` 를 대상으로 한다.
     `rows.some(...)` 전체 가드는 나중에 합류한 멤버를 영구 차단한다.
  3. 목록의 완료 판정도 대표(head)가 아니라 `rows.every(...)` 로 본다.
**파일**: `assets/js/db.js` (`groupFor` · `setShipWorkDone`) ·
`assets/js/pages/shipping.js` (`rowDone`) · `CLAUDE.md` 3-1 절

### 2026-09-05 — [dev-team/code-review-team] 모바일 앱 분리(A안) 7단계 진행 중 리뷰 반복 지적

**상황**: `feat/mobile-app` 브랜치에서 `db.js` 에 모바일 전용 조회 함수(`listStowWaiting` 등)를
추가하고, 문서(`docs/mobile.md` `docs/common.md` 등)를 여러 세션이 동시에 편집.
**실수/오판**:
  1. 새 조회 함수가 상차완료 판정을 자체 계산하려다 `steps.js` 의 `loadDone()` 단일 판정
     규칙을 깰 뻔했다(코드리뷰에서 반복 지적) — `loaded_at` 과 `load_status` 를 함께 보는
     기존 규칙을 우회하면 화면마다 상차완료 표시가 어긋난다.
  2. `docs/common.md` `docs/shipping.md` 처럼 여러 팀이 동시에 손댈 수 있는 공유 문서를
     소유 팀 구분 없이 편집해 병합 충돌·중복 서술이 생겼다.
  3. 세션 한도로 dev-team 에이전트가 단계 중간에 끊겨 완료 기준 미확인 상태로 다음
     단계가 시작될 뻔했다.
**교훈**:
  1. 상차완료·검수완료 등 **기존에 단일 판정 함수가 있는 값은 새 조회 함수도 반드시
     그 함수(`loadDone()` 등)를 재사용한다.** 직접 재계산하지 않는다.
  2. 공유 문서(`CLAUDE.md` `docs/common.md` 등)를 여러 팀이 동시에 건드릴 작업이면
     **소유 팀을 한 팀(doc-sync-team)으로 고정**하고 나머지는 변경 요청만 전달한다.
  3. 세션 한도로 에이전트가 중단되면 **완료 기준(체크리스트) 충족 여부를 확인한 뒤에만
     다음 단계로 넘기고**, 미확인이면 같은 단계로 재디스패치한다.
**파일**: `assets/js/db.js`(`listStowWaiting` 등) · `docs/mobile.md` `docs/common.md`

## 🎯 자주 반복되는 카테고리 (주의 영역)

이 카테고리에 해당하는 실수는 **재발 시 즉시 본 로그 + 해당 팀 에이전트 파일 둘 다 갱신**:

- DB 스키마 판단 — 마이그레이션 파일 vs prod 실태 불일치
- 줄글 보고 — 톡방에 마크다운 없이 한 줄 줄글 INSERT
- 톡방 INSERT 누락 — 작업 단계 진행했는데 기록 안 함
- 검수 누락 — verifier-team 거치지 않고 "완료" 보고
- 감사팀 누락 — 결제·DB·법적 문구 등 도메인 작업에 해당 감사팀 호출 안 함
- 묶음/그룹 처리 — 단계별 적용 범위를 구분하지 않고 키 하나로 묶기
