# 당일상차리스트

> 코드 `assets/js/pages/loading.js` · 라우트 `#/loading` · [공통 규약](common.md) · [CLAUDE.md](../CLAUDE.md)
> 검수 화면은 [inspect.md](inspect.md) 참고

해당 출고일의 상차 대상을 확인하고, 검수와 상차완료를 처리하는 화면.
**현장에서 휴대폰으로 쓰는 것을 전제로 만들었다.** PC 는 부차적이다.

---

## 접근 권한

| 역할 | 조회 범위 | 검수·상차완료 | 다운로드 |
|---|---|:---:|:---:|
| 관리자 | 전체 | ✅ | ✅ |
| 용마담당자 | 전체 | ✅ | ✅ |
| 화주관리자 | 전체 | ❌ 조회만 | ✅ |
| 화주영업팀 | **본인 등록건만** | ❌ 조회만 | ✅ |

조회 범위 필터는 `db.listLoading()` 이 출고일 기준으로만 조회하므로
**결과를 받은 뒤에** 건다.

```js
rows = await db.listLoading(filter.date);
if (!can(user, 'viewAll')) rows = rows.filter((o) => o.created_by === user.id);
```

## 조회 대상 🔑

```js
db.orders.filter((o) => o.ship_req_date === shipDate
    && !o.canceled_at
    && readyToLoad(o, hasExtraTask))
```

**출고일이 일치하고, 상차작업을 제외한 모든 단계가 끝난 주문만** 나온다
(`steps.js` 의 `readyToLoad`). 취소된 주문은 제외한다.

즉 [출고주문처리](shipping.md)에서 출고작업·검수작업(요청작업 포함)을 끝내야 하고,
추가작업 요청이 있는 주문이라면 추가작업까지 완료해야 이 목록에 나타난다.
목록이 비어 있으면 대개 앞 단계가 안 끝난 것이다 (빈 화면 안내 문구가 그 점을 알려준다).

정렬은 묶음 번호(대표주문번호 · 없으면 대표 주문번호) 오름차순이다.

## 화면 구성

### 상단 — 요약 (4칸)

| 카드 | 계산 |
|---|---|
| 출고건수 | 행 수 |
| 파렛트수 | `pallet_count` 합 (PLT) |
| 상차완료 | `load_status === '완료'` 인 행 수 |
| 진행률 | 상차완료 / 전체 — 막대 그래프 포함 |

### 날짜 이동

`출고일자` 날짜 입력 + `전일` `오늘` `익일` 버튼.
현장에서 한 손으로 날짜를 넘길 수 있도록 버튼을 뒀다. 기본값은 오늘이다.

### 본문 — 화면 크기에 따라 두 형태

**두 마크업을 모두 그려두고 CSS 로 하나만 보인다.** (기준 860px)

| | PC (`.load-table`) | 모바일 (`.load-list`) |
|---|---|---|
| 형태 | 표 | 카드 |
| 그리는 함수 | `drawTable()` | `drawCards()` |

⚠️ **한쪽만 고치면 다른 화면에서 반영되지 않는다.** 컬럼을 추가하면 양쪽 다 손봐야 한다.
버튼 동작은 `bindActions()` 가 공통으로 처리하므로 한 번만 고치면 된다.

#### PC 표 컬럼

출고일자 · 주문번호 · 거래처명 · 차량구분 · 파렛트수 · **박스수** · **적치로케이션** · 검수 · 상태 · 상차

#### 모바일 카드

주문번호 + 상태 배지 / 거래처명 / 출고일·차량·파렛트(검수/전체)·박스 / 버튼 행

| 상태 | 버튼 행 |
|---|---|
| 상차 전 | `적치로케이션` · **`상차검수`** (검수가 끝나면 `상차완료` 가 붙는다) |

버튼은 `flex: 1 1 0; min-width: 0` 으로 **가로 폭을 같게** 맞춘다.
(`min-width` 를 풀지 않으면 글자 수에 따라 폭이 달라진다)
| 상차완료 | **`상차완료` 버튼 하나만 크게.** 누르면 상차 상세가 열린다 |

- 상차완료된 건은 적치로케이션 버튼도 사라진다. 로케이션은 상세 팝업 안에서 본다
- 상세(`openLoadedDetail`)는 거래처·출고일·차량·파렛트·박스·검수와
  **검수완료 · 출고적치 · 상차완료 시각**, 파렛트별 로케이션을 보여준다

#### 상차완료 취소 🔑

잘못 찍은 상차는 **상세 팝업 최하단의 `상차완료 취소`** 로 되돌린다 (`db.cancelLoading()`).

- 확인 대화상자에서 **묶인 주문 몇 건이 함께 되돌아가는지** 알려주고, 취소 뒤 토스트로 결과를 알린다
- 묶음 전체의 `loaded_at` 을 비운다. **상차검수는 그대로 두므로 바로 다시 상차완료할 수 있다**
- 🔑 **되돌아가는 상태는 실제 스캔 수를 보고 정한다** — 묶음에 스캔된 파렛트가 있고
  전량 검수돼 있으면 `검수`, 아니면 `대기`.
  (예전에는 `검수` 로 고정해서 스캔이 0인데 `검수` 로 남는 경우가 있었다.
  0파렛트 멤버는 스캔할 파렛트가 없으므로 `scanPallet` 과 같은 기준으로 `검수` 로 둔다 —
  그러지 않으면 `대기` 로 남아 재상차가 막힌다)
- 취소 이력이 `상차작업: 완료 → 취소` 로 남는다
- 🔑 **`loaded_at` 이 있으면 상차 상태가 무엇이든 이 상세로 들어갈 수 있다** (PC 표·모바일 카드 공통).
  상태만 어긋난 건도 화면에서 되돌릴 수 있어야 하기 때문이다
  ([inspect.md](inspect.md) 의 검수 초기화 주의 참고)
- ⚠️ **완료처리(마감)된 주문은 거부된다.** 주문처리현황에서 완료처리를 먼저 취소해야 한다
- 처리 권한(`updateStatus`)이 없으면 버튼이 나오지 않는다
- PC 표는 검수 버튼과 적치로케이션 버튼을 그대로 두고,
  마지막 칸의 `상차완료` 버튼으로 상세를 연다

### 모바일 필터 🔑

앱 화면은 한 행에 **검색(좌) + 출고일자(우)** 만 둔다 (`drawFilters`).

| | 웹 | 모바일(앱) |
|---|---|---|
| 출고일자 | 좌측 | **우측** |
| 주문번호 / 거래처명 검색 | 없음 | **있다** (입력 즉시 걸린다) |
| `전일` `오늘` `익일` | 있다 | **없다** |
| 다운로드 | 있다 | **없다** |

검색은 조회된 목록에서 주문번호·거래처명을 부분 일치로 거른다.

## 핵심 로직 — 상태 전이 🔑

```
대기 ──(상차라벨 바코드를 파렛트 수만큼 스캔)──▶ 검수 ──(상차완료 버튼)──▶ 완료
```

| 상태 | 배지 색 | 의미 |
|---|---|---|
| `대기` | 회색 | 검수 전이거나 검수 중 |
| `검수` | 파랑 | 파렛트 전량 검수 완료. **상차완료 버튼이 나타난다** |
| `완료` | 초록 | 상차 종료 |

상태값은 `config.js` 의 `LOAD_STATUS` 를 쓴다.

### 검수 버튼

```
검수 3/6      ← 검수완료 파렛트 / 전체 파렛트
```

**상태와 무관하게 항상 표시된다.** 누르면 `#/inspect/{주문ID}` 로 이동한다
([검수 화면](inspect.md)). 조회 권한만 있는 사용자도 진입할 수 있으며,
그 경우 검수 화면이 조회 전용으로 열린다.

### 상차완료 버튼

**표시 조건**: `o.load_status === '검수' && editable`

즉 **검수가 끝나야만 나타난다.** 대기 상태에서는 `-` 만 보인다.
확인 대화상자를 거쳐 `db.completeLoading()` 을 호출한다.

```js
if (o.load_status !== LOAD_STATUS.INSPECTED) {
    throw new Error('검수가 완료된 건만 상차완료 처리할 수 있습니다.');
}
o.load_status = LOAD_STATUS.DONE;
o.loaded_at = new Date().toISOString();   // 처리현황의 상차작업 단계가 완료된다
```

화면 버튼을 우회해 호출하더라도 데이터 계층에서 한 번 더 막는다.
**상차완료는 처리현황의 상차작업 단계(`loaded_at`)도 함께 채운다.** 두 화면이 여기서 다시 만난다.

## 묶음 (대표주문번호 · 차수) 🔑

대표주문번호로 묶인 주문과 추가주문 차수는 함께 실리므로 **하나로 묶어** 다룬다
(`db.listLoading()` 이 대표 1건만 돌려주고 `group_no` `group_nos` `group_count`
`group_pallets` `group_inspected` 를 붙인다).

```js
db.groupKeyOf(o)   // rep_no(대표주문번호) > base_no(차수 기준번호) > order_no
```

🔑 **차수까지 묶는 것은 상차 단계뿐이다.** 접수·출고작업·검수작업은 대표주문번호
묶음에만 일괄 적용되고, 추가주문 차수는 각각 따로 처리한다
([shipping.md](shipping.md) 참고).

- 목록에는 대표만 나오고 옆에 `+2건` 배지가 붙는다.
  주문번호 칸은 **대표주문번호가 있으면 그 번호(굵게)** 이고, 묶인 주문번호는 툴팁으로 본다
- 파렛트수·검수 수는 **묶음 합계**다
- **상차검수는 묶음 전체를 한 화면에서 한다.** 대표주문번호(또는 묶인 주문번호) 바코드를
  합계 수만큼 스캔한다 ([검수 화면](inspect.md) 참고)
- **상차완료는 묶음 전체가 검수돼야** 누를 수 있고, 누르면 묶인 주문이 함께 상차완료된다
  (`db.completeLoading()`)
- 검수 초기화도 묶음 전체에 적용된다
- 검색(주문번호/거래처명)은 대표주문번호도 함께 본다

## 적치 로케이션 확인 · 파렛트 내리기 🔑

각 주문의 `적치로케이션`(모바일) · `확인`(PC) 버튼으로 팝업을 연다
(`openLocationModal`).

- 파렛트별 **로케이션과 체크박스**가 나온다. 상단에 `내림 1/4` 로 진행 수를 보여준다
- 로케이션은 `IF-01-03-01` 형식으로 보여준다
  ([출고적치](shipping.md#로케이션-형식-) 참고)
- 파렛트마다 앞에 `1차` `2차` 차수가 표시된다 (추가주문 파렛트 구분)
- 🔑 **로케이션 순으로 정렬한다** — 구역 → 행 → 열 → 단 오름차순 (`compareLocation()`).
  창고를 도는 순서대로 내리기 위해서다. 로케이션이 없는 파렛트는 맨 뒤로 간다
- ⚠️ 정렬해도 **파렛트 번호는 원래 번호를 유지한다.** 이름을 붙인 뒤 정렬하기 때문이다
  (`sortByLocation()`). 상차완료 상세의 목록도 같은 순서다
- **한 파렛트씩 내리면서 체크한다.** 체크하면 `pallets.picked_at` 이 기록되고
  그 줄이 초록으로 바뀐다 (`db.setPalletPicked()`)
- 체크를 풀면 기록도 지워진다
- 다음 경우에는 체크할 수 없다
  - 처리 권한이 없는 사용자 (`can(user, 'updateStatus')`)
  - **상차완료된 주문** — 안내 문구가 뜬다
  - 적치 로케이션이 없는 파렛트
- 상차완료된 건도 로케이션은 열어볼 수 있다 (읽기 전용)

⚠️ 파렛트를 다 내렸는지는 **상차완료 조건에 넣지 않았다.** 상차완료는 지금처럼
바코드 전량 검수(`load_status` 가 `검수`)로만 판단한다.

## 출고적치를 마쳐야 나온다 🔑

`readyToLoad` 는 상차작업을 제외한 **모든 단계**가 끝났는지를 본다.
2026-08 에 추가된 **출고적치**도 그 대상이므로, 파렛트 로케이션이 전량 입력되지 않은
주문은 이 화면에 나오지 않는다. 적치는 [출고주문처리](shipping.md#출고적치-탭-)의
출고적치 탭에서 한다.

## 알려진 제약

**`pallet_count` 가 0이면 검수가 불가능하다.** 다만 출고주문처리의 **검수작업 탭에서
검수완료 시 총 파렛트수를 수기로 입력**하면 그 수만큼 바코드가 생성된다
([docs/shipping.md](shipping.md) 참고). 검수를 거치지 않은 주문은 여전히 0이다.

`박스수`(`box_count`) 도 같은 화면에서 입력된 실측값이다. 입력 전에는 `-` 로 표시한다.

## 수정 시 주의

- **모바일 우선이다.** 변경 후 반드시 좁은 화면(390px 등)에서 확인한다.
  하단 탭바에 가리지 않도록 `.view` 하단 패딩이 잡혀 있다
- 표와 카드 **양쪽**을 고친다. 한쪽만 고치면 다른 기기에서 안 보인다
- 상차완료 조건(`검수` 상태)을 화면에서만 풀지 않는다. `db.completeLoading()` 이 막는다
- 진입 조건은 `steps.js` 의 `readyToLoad()` 하나로 관리한다.
  단계를 바꾸려면 `config.js` 의 `WORK_STEPS` 를 고친다
