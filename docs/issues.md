# 이슈등록

> 코드 `assets/js/pages/issues.js` · 라우트 `#/issues` · [공통 규약](common.md) · [CLAUDE.md](../CLAUDE.md)

주문 처리 과정에서 발생한 문제를 게시판 형태로 등록하고 처리 상태를 관리하는 화면.
화주와 물류사 사이의 소통 창구다.

---

## 접근 권한

| 역할 | 조회 범위 | 등록 | 이슈접수·종결요청 | 종결승인 | 다운로드 |
|---|---|:---:|:---:|:---:|:---:|
| 관리자 | 전체 | ✅ | ✅ | ✅ | ✅ |
| 용마담당자 | 전체 | ✅ | ✅ | 등록자 본인이면 | ✅ |
| 화주관리자 | 전체 | ✅ | ❌ | 고객사 소속이면 ✅ | ✅ |
| 화주영업팀 | **본인 등록건만** | ✅ | ❌ | 등록자 본인이면 | ✅ |

**등록은 모든 역할이 할 수 있다.** 다른 화면과 달리 `createOrder` 권한을 보지 않는다.
누구나 문제를 제기할 수 있어야 하기 때문이다.

이슈접수 버튼 노출 조건:

```js
(can(user, 'updateStatus') && can(user, 'createIssue')) || can(user, 'manageUsers')
```

→ 실질적으로 **관리자와 용마담당자**만 접수한다.
문제를 접수하고 해결하는 주체가 물류사이기 때문이다.
담당자확인·종결요청·종결승인의 주체는 아래 상태 전이 표를 따른다.

---

## 화면 구성

### 탭 🔑

화면 맨 위의 탭 3개가 목록의 범위를 가른다. 화면 구성(요약·필터·표·팝업)은 같다.

| 탭 | 표시 대상 | 필터 | 상태 컬럼 |
|---|---|---|---|
| 이슈등록 및 확인 | 진행중 (종결완료·확인취소 **제외**) | 상태 + 검색어 | 절차(단계 칩) |
| 완료 | `종결완료` 건만 | **년도·월(종결일자 기준)** + 검색어 | `종결완료` 초록 배지 하나 |
| 취소 | `확인취소` 건만 | **년도·월(취소일자 기준)** + 검색어 | `확인취소` 빨강 배지 하나 |

년도 목록은 데이터에 있는 년도로 채워진다 (`fillYearOptions`). 기본값은 전체.

### 상단 — 요약

전체 이슈 + 상태별 건수. 조회된 행 기준이다.
메인 탭은 진행 단계 4칸(접수대기~종결요청)이 붙어 5칸(`.summary--5`),
완료·취소 탭은 해당 상태 1칸만 붙는다.

### 표 (웹)

| 컬럼 | 폭 | 비고 |
|---|---|---|
| 연번 | 44px | 역순 |
| 등록일자 | 88px | **날짜만** (`YYYY-MM-DD`) — 시각은 상세 팝업에서 본다 |
| 업무유형 | 76px | 태그 (`work_type`, 등록 시 선택) / `-` |
| 업무구분 | 88px | 태그 (`type`, `tag--lg` — 문구가 잘 보이게 키움) |
| 관련주문번호 | 110px | `order_no` / `-` (자동등록 건은 조정요청의 주문번호가 자동 입력) |
| 제목 | **남는 폭 전부** | 클릭 시 상세 모달 |
| 등록자 | 96px | 등록자 이름 (`creator_name` — `db.listIssues()` 가 붙여준다) |
| 상태 | 420px(메인) / 96px | 메인은 절차 칩, 완료·취소는 배지 하나 |
| 종결일자 | 88px | 완료·메인 탭은 `closed_at`, **취소 탭은 `취소일자`(`canceled_at`)** |

확인요청일 컬럼은 없다 (상세 팝업에서만 본다).
상태 변경은 표에서 하지 않고 **상세 팝업의 버튼**으로 한다 (아래 상세 모달 참고).

### 모바일 표 (860px 이하) 🔑

앱 화면의 **표는 조회 전용**이라 컬럼 4개만 둔다. 처리는 웹과 동일하게
상세 팝업의 버튼으로 할 수 있다 (권한·주체 조건도 동일 — 현장작업자는 버튼이 없다).

```
연번 · 등록일자(월/일) · 업무구분 · 제목
```

- **행 어디를 눌러도 상세 팝업이 열린다** (`bindDetail`). 확인요청일·상태·본문은 상세에서 본다
- 등록일자는 `08/31` 형식으로 줄인다 (`monthDay()`)
- **상단의 `다운로드` · `이슈 등록` 버튼은 나오지 않는다** (`drawHeadActions`)
- 필터는 한 행에 `상태`(110px 고정) · `제목/주문번호`(남는 폭) · `조회` 를 넣는다
- 창 크기가 기준점을 넘나들면 상단 버튼과 표를 다시 그린다

## 등록 폼

| 항목 | 필드 | 필수 | 비고 |
|---|---|:---:|---|
| 업무유형 | `work_type` | ✅ | `입고` `출고` `반품` `배송` `배차` `기타` |
| 업무구분 | `type` | ✅ | `오류확인` `긴급작업` `정보확인` `자료요청` `작업요청` `기타업무` |
| 확인요청일 | `due_date` | ✅ | **기본값 내일** |
| 관련 주문번호 | `order_no` | | 선택 입력. 자유 텍스트 |
| 제목 | `title` | ✅ | |
| 내용 | `content` | ✅ | textarea |

업무구분 목록은 `config.js` 의 `ISSUE_TYPES`, 업무유형 목록은 `ISSUE_WORK_TYPES` 가
유일한 출처다. ⚠️ **업무구분의 `작업요청` 은 출고주문처리의 추가작업 요청 연동**
(`EXTRA_TASK_TYPE`)에 쓰이므로 목록에서 빼지 않는다.
업무유형이 도입되기 전의 이슈는 `work_type` 이 비어 있고 화면에 `-` 로 나온다.

### 자동등록 (조정요청 연동) 🔑

주문정보등록에서 **조정요청을 등록하면 이슈가 자동으로 함께 등록된다**
(`db.createRestore()` — 업무구분 `작업요청`, 업무유형 `출고`, `auto_created: true`).

- 목록의 제목 앞에 **`자동등록`** 주황 태그가 붙는다
- 상세 팝업 최상단에 *"해당 건은 주문정보등록에서 조정요청으로 접수하여
  자동등록 된 건입니다"* 안내 배너(`issue-auto-note`)가 표시된다
- ⚠️ **`auto_created` 건은 추가작업 요청 연동에서 제외된다**
  (`extraTaskNoSet` · `listRequestTasks`). 원본 조정요청이 이미 조정작업 단계를
  만들기 때문에, 포함하면 같은 요청이 요청작업·추가작업 단계로 이중 표시된다

등록 시 상태는 항상 `접수대기` 로 시작한다 (`db.createIssue()` 의 기본값).
확인담당자를 지정하는 **이슈접수**를 거쳐야 `접수완료` 가 된다.

⚠️ **`order_no` 는 주문 테이블과 연결되어 있지 않다.** 단순 문자열이다.
오타가 나도 검증하지 않으며, 주문 화면에서 관련 이슈를 역으로 조회할 수 없다.
연결이 필요하면 별도 작업이 필요하다.

## 핵심 로직 — 상태 전이 🔑

**단계마다 처리 주체가 다르다.** 물류사가 접수·처리하고, 등록자(화주) 쪽이 종결을 승인한다.

```
접수대기 ──(이슈접수)──▶ 접수완료 ──(담당자확인)──▶ 확인중 ──(종결요청)──▶ 종결요청 ──(종결승인)──▶ 종결완료
                            └──────────(종결요청: 확인중 생략 가능)──────────┘
```

| 전이 | 버튼 | 처리 주체 | db.js |
|---|---|---|---|
| 접수대기 → 접수완료 | `이슈접수` | 관리자·용마담당자 — 확인담당자 지정 | `acceptIssue()` |
| 접수완료 → 확인중 | `담당자확인` | **선정된 확인담당자 본인** 또는 관리자 | `confirmIssueAssignee()` |
| 접수완료·확인중 → 종결요청 | `종결요청` | 선정된 담당자 또는 관리자 | `requestIssueClose()` |
| 종결요청 → 종결완료 | `종결승인` | **등록자**, 고객사 소속 화주관리자, 관리자 | `approveIssueClose()` |
| 접수대기~확인중 → **확인취소** | `이슈취소` | **등록자 본인** 또는 관리자 (종결요청 전까지) | `cancelIssue()` |

`확인취소` 는 절차가 아니라 이탈 상태다 (`ISSUE_STATUS` 절차 목록에 없다).
취소하면 `canceled_at`(취소일자)이 기록되고 취소 탭에서만 보인다.

- **이슈접수** : 확인담당자를 **소속 용마로지스 + 권한 용마담당자인 활성 사용자** 중에서
  고른다 (`db.listIssueAssignees()`, 본인 포함 — 기본 선택은 본인).
  지정되면 `assignee_id` `assignee_name` 이 저장된다
- **종결승인** 시에만 `closed_at`(종결일자)이 기록된다
- 버튼 노출과 실제 처리는 같은 판정 함수를 쓴다
  (`db.canConfirmAssignee()` `canRequestClose()` `canApproveClose()`)
- 뒤로 되돌리는 버튼은 없다. 상태 변경 이력도 남지 않는다
  (주문의 `order_history` 같은 장치가 이슈에는 없다)
- 서버 RLS: 화주관리자가 남이 등록한 이슈를 종결승인해야 하므로
  `issues_update` 정책에 `shipper_admin` 이 포함되어 있다 (`schema.sql`)

상태값은 `config.js` 의 `ISSUE_STATE` / `ISSUE_STATUS` 를 쓴다.

### 상태 컬럼의 절차 표시

표의 상태 컬럼과 팝업의 상태 행은 배지 하나가 아니라 **5단계 칩 절차**로 그린다
(`issueFlow()`, 주문처리현황의 `.steps--flow` 스타일 재사용 + `.issue-flow` 로 글자 확대).

- **지나온 단계** : 초록 (`is-done`)
- **현재 진행·요청중인 단계** : 노랑 (`is-current`)
- 종결완료에 도달하면 다섯 칸 모두 초록이 된다

### 상세 모달

제목 클릭 시 업무유형 · 업무구분 · 주문번호 · 확인요청일 · 상태(절차) · 확인담당자 ·
등록자 · 등록일시 · 종결일자와 본문을 보여준다. 본문은 `white-space: pre-wrap` 으로 줄바꿈을 살린다.
팝업은 `openModal(..., { xl: true })` 로 크게(최대 1120px) 띄운다.

하단 처리 버튼은 위 전이 표의 주체에게만 보인다. 예컨대 `접수완료` 상태에서
선정된 담당자가 아닌 용마담당자에게는 아무 버튼도 나오지 않는다.

### 댓글

상세 팝업 맨 아래에 댓글 영역이 있다 (`issue_comments` 테이블, `initComments()`).

- **누구나 등록**할 수 있다 (조회 가능한 이슈에 한함 — RLS 도 동일 판정)
- `답글` 로 **대댓글을 깊이 제한 없이** 이어 달 수 있다 (`parent_id`, 화면은 깊이만큼
  들여쓰되 5단계까지만 들여쓴다)
- **수정·삭제는 작성자 본인만** 보이고 가능하다 (서버 RLS 도 본인만 허용)
- 수정하면 `updated_at` 이 남아 **(수정됨)** 으로 표시된다
- 답글이 달린 댓글을 삭제하면 스레드를 지키기 위해 **"삭제된 댓글입니다"** 로 남고
  (soft delete), 답글이 없으면 행 자체가 지워진다

## 실시간 갱신

`db.subscribe(reload)` — 5초 폴링.
화주가 이슈를 올리면 용마담당자 화면에 5초 안에 나타난다.

## 수정 시 주의

- 유형·상태 목록은 `config.js` 에서만 바꾼다. 화면에 문자열로 쓰지 않는다
- 등록 권한을 좁히지 않는다. 모든 역할이 이슈를 올릴 수 있어야 한다
- 확인요청일 기본값이 **내일**이다. 오늘로 바꾸면 당일 처리 압박이 생긴다
- 이슈에는 이력 기능이 없다. 필요해지면 주문의 `addHistory()` 방식을 참고한다
