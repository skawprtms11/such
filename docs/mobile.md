# 모바일 앱 셸 (m.html)

> 코드 `m.html` · `assets/js/shell.js` · `assets/js/mobile/app.js` · `assets/js/mobile/ui.js` ·
> `assets/js/mobile/screens/*.js` · `assets/css/mobile.css` · [공통 규약](common.md) · [CLAUDE.md](../CLAUDE.md)
> 관련 문서: [출고주문처리](shipping.md) · [상차리스트](loading.md) · [검수](inspect.md) · [이슈등록](issues.md)

**현장(협력사·용마담당자)이 휴대폰으로 쓰는 전용 셸.** 웹 셸(`app.html`)과 화면 코드를
공유하지 않고, `db.js` `steps.js` `auth.js` `config.js` `scanner.js` `util.js` `icons.js` 만
같이 쓴다. 업무 규칙(단계 판정·묶음·검증)은 전부 그 공유 모듈에 있고, 이 문서가 다루는
화면 층에는 새 규칙이 없다.

---

## 1. 진입 · 분기 · 탈출구

로그인은 `index.html` 하나다. 로그인 성공 직후·재방문 시 **`assets/js/shell.js` 의
`shellUrl(user)` 한 곳**이 어느 셸로 보낼지 정한다.

```
고정값(tpl_force_shell) → 화면 폭 860px → 협력사 소속(appOnlyCompany) 순서로 판정
```

| 조건 | 결과 |
|---|---|
| `localStorage.tpl_force_shell === 'web'` | `app.html` |
| `localStorage.tpl_force_shell === 'app'` | `m.html` |
| 화면 폭 860px 이하 **또는** 협력사(`COMPANY.PARTNER`) 소속 | `m.html` |
| 그 밖 | `app.html` |

- 🔑 **협력사는 기기와 무관하게 앱으로 간다.** PC 로 접속해도 `m.html` 이다.
- 두 셸은 **자기가 갈 곳이 상대 셸일 때만** 서로 넘긴다(백스톱). 판정 함수가
  `shellUrl()` 하나뿐이라 상호 배타적이고, 되튕기는 무한 루프가 생기지 않는다
  (`mobile/app.js` 는 `shellUrl(user) === WEB_SHELL` 이면 `app.html` 로,
  `app.js` 는 `shellUrl(user) === APP_SHELL` 이면 `m.html` 로 넘긴다).
- 옛 주소·설치된 PWA 의 해시는 `shell.js` 의 `appRoute()` 가 옮긴다.

```
app.html#/shipping        →  m.html#/ship
app.html#/loading         →  m.html#/load
app.html#/inspect/:id     →  m.html#/load/:id     ← 웹 inspect 는 상차검수라 앱의 load 로 간다
app.html#/processing      →  m.html#/pcheck       ← 웹은 등록·문서, 앱은 검수만 (docs/processing.md §17)
app.html#/status, #/issues →  그대로 유지 (뒷조각 보존)
app.html#/orders, #/users →  앱에 없는 메뉴 → 홈(빈 문자열, `#/ship`)
```

### 탈출구 🔑

`?shell=web` / `?shell=app` 쿼리로 들어오면 `shell.js` 의 `applyShellQuery()` 가
그 값을 `tpl_force_shell` 에 고정하고(로그인 여부와 무관하게 먼저 처리) 이후 그 셸로 고정된다.
화면 버튼도 양쪽에 하나씩 있다.

| 위치 | 버튼 |
|---|---|
| 앱 `계정`(`#/account`) 화면 | `웹 화면으로` |
| 웹 사이드바 하단 | `앱 화면으로` |

둘 다 `shell.js` 의 `forceShell()` 을 부른다. 태블릿을 쓰는 용마담당자가 웹 화면을
계속 봐야 할 때 쓰는 경로다.

### 롤백 1줄 🔑

`index.html` 의 `shellUrl()` 분기를 되돌리면(또는 `tpl_force_shell=web` 을 전원에 심으면)
즉시 예전 웹 전용 경로로 돌아간다. `m.html` 이 배포되어 있어도 아무도 가지 않으므로 무해하다.

### 알려진 제약

- ⚠️ **앱→웹 백스톱은 해시를 버리고 웹 홈으로 간다.** 웹 해시로 옮기는 역방향 표가 없다.
  앱에서 보던 화면을 웹에서 이어 보려면 웹 메뉴에서 다시 들어가야 한다.
- ⚠️ **설치된 PWA 는 셸을 바꾼 당일 첫 실행이 옛 캐시로 열릴 수 있다.** 서비스워커가
  새 셸을 받아오는 것은 그 실행 이후다. "앱을 껐다가 다시 열어 주세요" 로 안내한다
  (재설치는 필요 없다).
- 앱 안내에서는 **CSV 만 지원한다.** 인쇄는 웹에서 한다 — 대표님 결정 H.
  재고실사표 화면(`#/stock`)의 툴바 자리는 나중에 인쇄를 붙일 수 있게 비워 두었다.

## 2. 하단 탭 — 탭 세트 (`config.js` 의 `APP_TAB_SETS`)

🔑 **하단 탭바는 라우트에 따라 통째로 바뀐다** (대표님 지시 2026-09-19). 탭 세트는 둘이다.

| 세트 | 언제 | 담긴 탭 |
|---|---|---|
| `main` (= `APP_TABS`) | 기본 — 그 밖의 모든 화면 | 출고 · 검수 · 적치 · 조정 · 상차 |
| `pcheck` | `#/pcheck/*` 안에서만 | 작업전 · 완료 · 캘린더 · 가이드 |

- 세트 선택은 `config.js` 의 **`tabSetOf(key)` 한 곳**이다. 셸(`mobile/app.js`)은
  라우트 키가 바뀔 때 `renderTabbar(세트)` 로 다시 그리고, **세트가 그대로면 손대지 않는다**
- 🔑 세트·활성 탭 판정은 셸의 **`tabStateOf(key, params)` 함수 하나**다 (라우터와 뒤로가기가
  같은 것을 부른다). 돌려주는 `tab` 은 **두 값뿐** — 세그 세트가 아니면 `null`, 세그 세트면
  언제나 탭 하나다(없거나 틀린 세그는 첫 탭). 주소를 옮길지는 부른 쪽이
  `tab.seg !== params[0]` 로 본다. 「없는 값(`undefined`)」을 세 번째 뜻으로 쓰지 않는다
- 유통가공 세트 항목에는 **`seg`** 가 있고 경로가 `#/pcheck/<seg>` 다. 활성 탭·상단바 제목은
  `seg` 로 고르며(`main` 세트는 종전대로 `key`), 상세는 그 아래 `#/pcheck/<seg>/:id` 다.
  **세그가 없거나 틀리면 첫 탭으로 옮긴다** (`#/pcheck` → `#/pcheck/pre`)
- 세그 세트에서는 목록도 `params` 를 하나 쓰므로 **뒤로가기 화살표는 상세에서만** 나오고,
  누르면 그 세그의 목록(`#/pcheck/<seg>`)으로 간다 (완료 검수 상세에서 작업전 목록으로 새지 않는다)
- 🔑 **유통가공 세트에는 출고 탭이 없다.** 돌아오는 길로 서랍(≡) **첫 줄에 「출고작업」**
  항목을 두었다 (`APP_MENU`). 라우트가 `APP_TABS` 의 출고와 겹치지만 목적지가 같아 무해하다

### `main` 세트 (홈)

홈은 **출고작업**(첫 번째 탭)이다. 앱을 열면 바로 스캔할 수 있어야 한다.

| 탭 라벨 | 상단바 제목 | 라우트 | 담는 것 |
|---|---|---|---|
| 출고 | 출고작업 | `#/ship` · `#/ship/:id` | 스캔/목록 → 작업시작·완료·시작취소·완료취소, 작업지시 박스 |
| 검수 | 검수작업 | `#/inspect` · `#/inspect/:id` | 스캔/목록 → 요청작업 확인·패킹리스트·총 파렛트/박스 입력·검수완료·완료 후 수정/취소 |
| 적치 | 출고적치 | `#/stow` · `#/stow/:id` | 스캔/목록 → 파렛트별 로케이션 입력(하단 독) |
| 조정 | 조정요청 | `#/adjust` · `#/adjust/:id` | 접수된 요청 목록 → 상세 → 작업완료 |
| 상차 | 상차작업 | `#/load` · `#/load/:id` | 목록 → 상차검수(라벨 스캔) → 상차완료 → 로케이션(파렛트 내리기) |

- 🔑 **출고작업과 검수작업은 별도 탭이다.** 설계 초안(§)의 "한 탭 통합안"은 대표님 결정 A 에서
  버려졌다 — 현행 웹 출고주문처리의 탭 구조(출고작업/검수작업 분리)와 맞춘 것이다.
  각 탭에서 **다른 단계의 주문을 스캔하면 안내 + 해당 탭으로 이동하는 버튼**을 보여준다
  (헛걸음 제거. 예: 검수 탭에서 출고 미완료 주문을 스캔하면 `출고작업으로` 버튼).
- 탭 순서는 **처리 흐름 순**이다(출고 → 검수 → 적치 → 조정 → 상차).
- 🔑 **유통가공작업의 입구는 하단 탭이 아니라 상단바 메뉴(≡)다** (대표님 지시 2026-09-19).
  주문 흐름과 이어지지 않는 독립 업무라 `main` 세트에 6번째 탭을 만들지 않는다.
  대신 **들어가면 하단 탭이 유통가공 전용 4개로 바뀐다** (아래 세트 표 · [§3-8](#3-8-유통가공-pcheck)).
  처음 구현은 6번째 탭 「가공」이었으나 대표님 원문 「상단 헤더의 메뉴」를 잘못 읽은 것이라 옮겼고,
  그 다음에는 화면 안 세그 3개였으나 「아래에 표시」 지시로 하단 탭이 되었다.
- 탭 순서·라벨·아이콘은 `config.js` 의 `APP_TAB_SETS` 가 유일한 출처다. 화면에 문자열로 쓰지 않는다.
- 셸(`mobile/app.js`)은 탭·메뉴를 **조회 권한만** 보고 거른다(`viewPerm`). 처리 권한
  (`updateStatus`)은 각 화면이 따로 판단한다 — 화주 역할도 진행 상황을 앱에서 조회해야 하므로
  탭 자체를 막지 않는다.

### `pcheck` 세트 (유통가공 전용)

`#/pcheck/*` 안에서만 나온다. 주문 흐름 탭은 전부 숨는다 — 현장에서 섞이면 오작동이 난다.

| 탭 라벨 | 상단바 제목 | 라우트 | 담는 것 |
|---|---|---|---|
| 작업전 | 작업전 검수 | `#/pcheck/pre` · `#/pcheck/pre/:id` | 스캔/목록 → 구성품 줄마다 사진 1장 → 저장 → 검수완료 |
| 완료 | 완료 검수 | `#/pcheck/done` · `#/pcheck/done/:id` | 스캔/목록 → 완료 사진 3장 → 저장 → 완료처리 |
| 캘린더 | 작업캘린더 | `#/pcheck/cal` | 월 이동 + 상태색 막대 (막대 탭 → 요약 시트) |
| 가이드 | 작업가이드 | `#/pcheck/guide` · `#/pcheck/guide/:id` | 촬영 절차 3단계 + 작업지시서 목록 → **작업지시서 내용 보기(읽기 전용)** |

### 상단바 메뉴(`≡`, `config.js` 의 `APP_MENU`)

탭에 없는 조회·보조 화면과 **독립 업무(유통가공작업)** 는 상단바 오른쪽 서랍 메뉴에 둔다.

| 항목 | 라우트 | 내용 | 조회 조건 |

| 유통가공작업 | `#/pcheck` (→ `#/pcheck/pre`) | 들어가면 **하단 탭이 유통가공 4개로 바뀐다** (위 세트 표 · [§3-8](#3-8-유통가공-pcheck)). **처리 화면이지만 독립 업무라 서랍에 둔다** | 없음(모두) — 검수 처리는 `updateStatus` |

| 이슈등록 | `#/issues` | 탭 3개(등록·완료·취소) · 목록 · 상세 · 댓글 | 없음(모두) |

## 3. 화면별 구성

### 3-1. 출고작업 (`#/ship`)

스캔 또는 목록에서 주문을 연다. 접수(주문처리, `confirmed_at`)가 안 된 주문은
`작업시작` 버튼 대신 안내가 뜬다. 접수된 작업지시(`work_note`)가 있으면 상단에
노란 안내 박스로 보여준다.

| 상태 | 버튼 |
|---|---|
| 미착수 | `작업시작` |
| 작업중 | `작업완료` · `시작 취소` |
| 완료 | `완료 취소` |

- `db.startShipWork()` / `db.setShipWorkDone()` 을 그대로 쓴다.
- **검수작업이 완료된 주문은 출고작업을 취소할 수 없다.** 검수를 먼저 취소해야 한다.
- 처리는 **대표주문번호 묶음**(`db.getBatchGroup`) 단위다. 추가주문 차수는 여기서 묶지 않는다
  ([shipping.md](shipping.md#처리-단위는-대표주문번호-묶음이다-) 참고).

### 3-2. 검수작업 (`#/inspect`)

**출고작업이 완료된 주문만** 진행할 수 있다. 아니면 안내 + `출고작업으로` 버튼.

| 항목 | 언제 필수인가 |
|---|---|
| 요청작업 완료 확인 | 추가작업이 `있음`(`extra_yn`)일 때 |
| 패킹리스트 내용 작성 | 패킹리스트가 `있음`(`packing_yn`)일 때 |
| 총 파렛트수 · 총 박스수 | 항상 — **묶음 총량을 1회 입력** |

- 필수 항목이 하나라도 빠지면 `db.setInspectDone()` 이 거부한다. 화면은 검증을 복제하지 않는다.
- 0파렛트(혼적 추가건, `db.minPalletOf` — 2차수 이상은 0 허용)로 완료하면 확인 대화상자가
  한 번 더 뜬다.
- 완료 뒤에는 `수정`(`setPalletCount` / `setBoxCount`) · `완료 취소` 가 나온다.
  **완료 취소는 적치취소를 먼저 해야 한다** — 순서를 어기면 `db.setInspectDone(false)` 가
  거부한다 (검수 미완료·적치 완료라는 앞뒤 안 맞는 상태를 막기 위해서다).
- 자세한 규칙(필수 항목·수정 조건·파렛트수 변경 영향)은 [shipping.md 의 검수작업 탭](shipping.md#검수작업-탭)과 동일하다. 이 문서는 화면 배치만 다룬다.

### 3-3. 출고적치 (`#/stow`) — 하단 독 방식 🔑

검수가 끝나고 아직 상차되지 않은 주문의 파렛트를 로케이션에 넣는 화면.
`mobile/screens/stow.js` 가 담당하며, 설계서의 "상단 sticky 입력 패널" 대신
**화면 맨 아래 고정 독(dock)** 으로 재배치했다. 기능은 웹/구모바일과 100% 동일하다.

```
목록(스크롤) ─────────────────────────
대상 배너 (독 바로 위, 큰 글씨 — "지금 어디에 넣는가")
도구 줄  [평치] [일괄평치 N(미지정 2건 이상일 때만)] [카메라] [지우기(값 있을 때만)]
하단 독  [ 로케이션 입력칸 ] [ 저장 ]
설정 줄  연속이동|건별이동   구역 [자동|수기] [IF]
```

| 상태 | 독 표시 |
|---|---|
| 입력 전/중 | 입력칸 + `저장` |
| 전량 입력 완료 | 독 전체가 초록 `적치완료` 버튼 |
| 적치완료 후 | 독 없음. 상태 카드의 `···` 메뉴에 `적치취소` |

- **위험 조작(적치취소)은 독에 두지 않는다.** 상태 카드의 `···` 메뉴 + 확인 대화상자.
- 로케이션·구역코드는 **폰 키보드로 넣는다.** 앱 자판(계산기 배열)은 폰 자판과 겹쳐 둘로
  보여서 걷어냈다 — 대신 `inputmode` 로 어떤 자판이 뜰지 정한다 (§4 소프트키보드 규칙).
- **일괄평치**: 미지정 파렛트 전부를 한 번에 평치로 기록한다 (확인 대화상자 · 이미 넣은 로케이션은 유지 ·
  [shipping.md 의 평치 일괄이동](shipping.md#평치-일괄이동-앱-)). 앱에만 있는 버튼이다
- 연속이동/건별이동, 구역코드 자동/수기, 평치, 지우기, 중복 로케이션 거부(진동 3회),
  스캐너 이중발사 2.5초 무시, 최근 이동순 정렬, 로케이션 형식(`isValidLocation`/`formatLocation`)
  등 **입력 규칙은 전부 [shipping.md 의 출고적치 탭](shipping.md#출고적치-탭-)과 같다.**
  이 화면은 배치만 재설계했다.
- `db.getLoadGroup()` 으로 묶음(대표주문번호 + 추가주문 차수)을 본다 — 적치·상차는
  차수까지 묶는 쪽이다.
- 목록 진입 지원: `db.listStowTargets()` 가 스캔 없이도 적치 대상 목록을 보여준다
  (§4-2 참고). 검수 미완료 주문을 열면 안내 + `검수작업으로` 버튼.

### 3-5. 상차작업 (`#/load`) — 리스트 → 검수 → 완료 → 로케이션 🔑

`mobile/screens/load.js` 가 상차리스트·검수(구 `#/inspect/:id`)·상차완료·파렛트 내리기를
**한 화면 흐름**으로 합쳤다 (설계서 §4).

```
#/load  (목록, 날짜 이동 + 검색)
   │ 카드 탭
   ▼
#/load/:id  세그 [ 상차검수 | 로케이션 ]
   상차검수 : 큰 카운터 n/N → 카메라/직접입력 스캔 → 전량 시 독이 [상차완료]로 전환
   로케이션 : 파렛트 내리기 체크(로케이션 순 정렬)
```

| 기능 | 함수 | 비고 |
|---|---|---|
| 목록 | `db.listLoading()` | 출고일 기준으로 먼저 묶고 **묶음 전체**가 `readyToLoad` 인지 본다. 묶음 값(`group_*`)도 묶음 전체 기준이다. 준비되지 않은 묶음은 사라지지 않고 `blocked` · `block_reason` 이 붙어 **`당일상차 제외` 배지 + 회색 카드**로 나온다 (탭·상차검수·상차완료 차단, 로케이션 확인만 가능) |
| 묶음 | `db.getLoadGroup()` | 대표주문번호 + 추가주문 차수 전체를 한 화면에서 검수 |
| 스캔 | `db.scanPallet()` | 대표주문번호·묶음 안 아무 번호·개별 파렛트 바코드 모두 인식. 결과 메시지는 화면에서 새로 만들지 않고 그대로 쓴다 |
| 전량 검수 시 자동 전환 | (db 내부) | `대기 → 검수`. 카메라 자동 종료 |
| 상차완료 | `db.completeLoading()` | **`검수` 상태에서만** 성공 |
| 상차완료 취소 | `db.cancelLoading()` | `···` 메뉴. 완료처리(마감)된 건은 거부 |
| 검수 초기화 | `db.resetInspection()` | `···` 메뉴. **상차완료된 묶음은 거부** |
| 파렛트 내리기 | `db.setPalletPicked()` | 세그 `로케이션`, 로케이션 순 정렬 |

- 🔑 **박스수는 묶음 합계다.** 목록 카드는 `db.listLoading()` 의 `group_boxes`,
  상세 화면은 `getLoadGroup().rows` 의 `box_count` 합을 쓴다.
  예전에는 대표 1건의 `box_count` 만 보여 웹 [상차리스트](loading.md)와 값이 달랐다
- 상세 화면 진입 시 `db.loadProgress()` 류 진행 계산은 새 규칙이 아니라
  `getLoadGroup().pallets` 를 세는 조합이다.
- 카메라 중복 방지(같은 라벨을 계속 비추면 2.5초, 다음 1건은 1.5초 이상 비어 있을 때)와
  직접 입력 무쿨다운(블루투스 스캐너 연속 입력)은 [inspect.md](inspect.md)와 동일.
- 날짜 이동은 웹처럼 `◀ 오늘 ▶` 버튼을 앱에도 둔다(장갑 낀 손으로 date picker 는 어렵다).


### 3-6. 일일체크리스트 (`#/checklist`) — 상단바 메뉴

**오늘 내가 빠뜨리면 안 되는 것**을 훑고 체크하는 목록. 날짜(`◀ 오늘 ▶`)를 옮겨 가며 **본인이
담당(상속 포함)인 항목 + 공통 항목**을 체크한다. 담당자 필터는 없다 (앱은 늘 본인 것이다).

**등록 기준 3구획**으로 나뉜다 — `일별`(그 날) · `이번 주`(머리에 `9/14~9/20`) ·
`이번 달`(`9월`). 구획 머리마다 기간과 `done / total` 이 붙고, 위에 큰 진행 카운터가 있다.
🔑 **같은 주·같은 달 안에서는 어느 날 눌러도 기록 1건**이다 (`db.periodStart`).

- 카드 하나 = 항목 하나. **카드 전체가 터치 영역**(48px 이상)이라 장갑을 낀 채 눌러도 된다
- 체크해도 카드는 **사라지지 않는다** — 흐리게 + 「완료」 배지 + 체크한 시각·사람
- 직전 기간에 체크 기록이 없으면 붉은 「지난 기간 미체크」 꼬리표
- **특이사항**은 카드 안 입력칸에 바로 쓴다 (체크 전에도 된다 · `db.setCheckMemo`).
  입력칸을 눌렀을 때는 체크가 토글되지 않는다
- 체크 권한이 없는 줄은 흐리게 + 잠긴다

⚠️ 상황 발생 시트 · 완료 접기 · `일일 | 전체` 세그먼트는 **없앴다** (웹과 같다).
체크항목 등록은 웹 「체크리스트 등록」 탭에서만 한다.

### 3-7. 업무프로세스 (`#/process`) — 상단바 메뉴 · 보기 전용

현장에서 매뉴얼을 펼쳐 보는 화면. 업무구분·업무항목 세그먼트로 고르면 흐름을 **세로 스테퍼**로 그린다 —
시작 → 프로세스 박스(체크항목 목록) → 박스 아래 주황 블록 `⚠ 상황 발생 시`(대응 단계, `↩ 처리 후 다음 단계`) → 완료.
편집(업무프로세스 탭 편집 모드)은 **웹에만** 있다.

🔑 **웹 업무프로세스 탭은 좌표로 놓는 도식이지만 앱은 세로 스테퍼를 유지한다** (좁은 화면에서
가로 스크롤은 읽기 어렵다). 한 층에 단계가 둘 이상이면(= **갈래**) `4.1 국내` 머리가 붙은
하위 스테퍼(파란 점선 레일)로 편다 — 번호는 머리에만 적고 동글은 가운뎃점이다.
**합류**도 도식으로 그리지 않고 갈래 블록 끝에 `↩ 갈래가 다시 ④ 출고완료 로 모입니다`
캡션 한 줄만 붙인다. 🔑 **합류 판정은 `db.processFlow` 의 `joinTarget` 만 읽는다** — 앱이
「즉시 다음 단계」만 교집합하면 「갈래 A 는 3단계 뒤에 합류」 같은 흐름에서 캡션이 사라진다
([checklist.md](checklist.md) 참고).

🔑 **공유 경계는 번호와 층이다.** 층·층 내 순서·번호(`4.1`)의 유일한 출처는 `checkflow.js` 의
`flowNos` 이고, `db.processFlow` 가 그것을 써서 `layers` · `no` · `joinTarget` 을 내려 준다.
앱은 그 값만 읽는다 (층을 다시 묶지 않는다). **좌표(`layoutDag`)는 웹 도식 전용**이다.
화면 코드는 여전히 서로 import 하지 않는다.

기간·담당자 상속·상황 판정은 웹과 같은 `db.checklistBoard()` · `db.canCheckItem()` · `db.checklistTree()` 를 쓴다
([checklist.md](checklist.md) 참고).

### 3-8. 유통가공 (`#/pcheck`) — 하단 탭 4개 · 사진 검수 🔑

`mobile/screens/pcheck.js`. **업무 규칙은 [processing.md §17](processing.md#17-모바일-검수-pcheck-)**
에 있고 여기서는 화면 배치만 다룬다. 웹 「유통가공작업」(등록·문서생성·마스터)은 앱에 없다.

```
#/pcheck   →  #/pcheck/pre 로 옮긴다 (하단 탭 [ 작업전 | 완료 | 캘린더 | 가이드 ])
   │  작업전·완료  : 상단 스캔바(문서번호) + 하단 목록   ← 출고(#/ship)·검수(#/inspect) 와 같은 틀
   │  캘린더       : 월 이동 + 상태색 막대
   │  가이드       : 촬영 절차 3단계 + 작업지시서 목록 (완료건은 접어 둔다)
   ▼ 카드 탭 · 문서번호 입력 · 바코드 스캔
#/pcheck/pre/:id    구성품 줄마다 [촬영] → 썸네일 → [저장] → 독이 [검수완료] 로
#/pcheck/done/:id   3칸 촬영 → [저장] → 독이 [완료처리] 로
#/pcheck/guide/:id  작업지시서 내용 보기 (읽기 전용)
```

🔑 **하위 탭은 화면 안 세그가 아니라 하단 탭바다** (대표님 지시 2026-09-19 · [§2](#2-하단-탭--탭-세트-configjs-의-app_tab_sets)).
화면은 `params[0]`(세그)만 읽고 그리며, **세그 UI 를 직접 그리지 않는다.**
탭 정의·활성 표시·상단바 제목은 전부 셸(`config.js` 의 `APP_TAB_SETS` + `mobile/app.js`) 몫이다.

#### 작업가이드 탭 (`#/pcheck/guide`)

현장이 **무엇을 언제 찍는지**와 **작업지시서 내용**을 폰에서 확인하는 보기 전용 화면이다
(인쇄물을 들고 다니지 않아도 되게 한 것 — 인쇄는 웹에서 한다).

| 조각 | 내용 |
|---|---|
| 절차 카드 | 작업전 검수 → 유통가공 작업 → 완료 검수 3단계 + 촬영 규칙 한 줄씩 (`GUIDE_STEPS`) |

| 상세 | 문서번호·작업구분·제품코드·제품명·작업수량·시작예정일·완료요청일 · **구성품 표**(구분·코드·품명·필요·LOT·수량) · 진행상태 배지 · 검수자/시각 |

- 🔑 **다음에 할 검수가 무엇인지는 `db.nextCheckPhase(job)` 하나가 정한다** (없으면 `null`).

- 검색어(`state.keyword`)는 **작업전·완료·가이드 목록이 함께 쓴다.** 세 목록이 같은 필드
  (문서번호·제품코드·제품명)를 보므로 탭을 옮겨도 찾던 작업이 그대로 걸려 있게 한 것이다

  `pages/processing/common.js` 에 있던 함수를 **`processing-calc.js` 로 옮기고** 웹은 그것을
  다시 내보낸다 (앱 화면은 `pages/**` 를 import 하지 않는다는 규칙을 지키기 위해서다)

- **촬영은 `<input type="file" accept="image/*" capture="environment">` 하나뿐이다.**
  `scanner.js`(카메라 스트림)를 쓰지 않는다 — 사진 촬영은 OS 카메라 앱이 초점·노출·플래시를
  훨씬 잘 잡고, 스캔용 스트림과 동시에 띄우면 기기에 따라 카메라가 잠긴다
- 촬영 칸은 **미촬영(점선 + 카메라 아이콘) / 촬영됨(썸네일 + `재촬영`)** 두 모양이다.
  아이콘은 `icons.js` 의 `camera` — 이모지 금지
- **저장 전에는 화면을 떠나도 사진이 남는다** (IndexedDB 초안 · processing.md §17-4).
  다시 들어오면 그대로 복구되고, 저장에 성공하면 초안을 지운다
- 위험 조작(**작업전검수 취소 · 완료 취소**)은 독에 두지 않고 상단 `···` 메뉴 +
  확인 대화상자다 (`#/stow` 의 적치취소와 같은 관례)
- 캘린더 세그는 웹과 **같은 순수 함수**(`processing-calc.js` 의 `calendarLanes`)를 `maxLane = 2`
  로 부른다. 막대 색은 `PROCESS_STATUS_TONE`, 클래스는 `m-cal-bar--*` (앱 CSS 는 `m-` 접두)
- 정리 함수에서 **`release()`(사진 URL 해제)** 를 반드시 부른다 — 카메라·구독 해제와 같은 자리

#### 구현 시 바꾼 것 (설계안 대비)

| # | 바꾼 것 | 근거 |
|---|---|---|
| ① | 상세는 **전체 화면이되 세그 없이 단계 하나만** 그린다 (`#/pcheck/pre/:id` · `#/pcheck/done/:id`). 단계가 다른 건을 열면 안내 + 그 단계로 가는 버튼 | 설계 그대로다. 촬영 칸이 여러 개라 시트에 넣으면 스크롤이 두 겹이 된다 |
| ② | **상세에는 실시간 구독(`db.subscribe`)을 걸지 않는다** | 촬영 도중 폴링이 다시 그리면 초안 썸네일·파일 선택이 끊긴다. 저장·완료·취소 뒤에는 화면이 직접 다시 읽는다 (`refresh()`) |
| ③ | 「저장」과 「검수완료」가 **db 함수도 둘**이다 (`savePreCheck` → `completePreCheck`) | 커밋 지점이 둘인데 함수가 하나면 「저장」만 눌러도 상태가 바뀐다 ([processing.md §6](processing.md#6-dbjs-함수-시그니처)) |
| ④ | 저장이 실패하면 **초안을 지우지 않는다** (성공해야 지운다) | 경로가 결정적이라 다시 「저장」을 눌러도 중복이 생기지 않는다. 지워 버리면 실패한 사진을 다시 찍어야 한다 |
| ⑤ | 촬영 칸은 `<label>` 이 파일 선택 전체를 감싼다 (`.m-photo__box`) | 장갑 낀 손으로 작은 버튼을 겨누지 않게 칸 전체가 터치 영역이다 |
| ⑥ | **초안 저장소를 못 열어도 촬영·저장은 된다** (코드리뷰팀) | 사파리 프라이빗 모드 등에서 IndexedDB 가 막히면 상세 화면이 통째로 뜨지 않았다. 초안은 보조 장치라 실패는 안내만 하고 그대로 진행한다 |
| ⑦ | ~~세그 전환에 **세대 토큰**을 둔다~~ → **없앴다** (하단 탭 전환은 셸이 한다) | 세그가 하단 탭이 되면서 pane 을 화면 안에서 갈아 끼우지 않는다. 셸이 라우트를 바꿀 때 **이전 화면의 정리 함수를 먼저 부르고**(`mobile/app.js`) 늦게 끝난 `render` 는 `renderSeq` 로 걸러 스스로 정리한다 — 같은 보호가 셸 한 곳에 있다 (학습로그 2026-09-17 「await 가 있는 start/stop 쌍에는 세대 토큰」) |
| ⑧ | 하위 탭을 **하단 탭바**로 옮겼다 (대표님 지시 2026-09-19) | 세그는 화면 위쪽에 있어 장갑 낀 손이 닿기 어렵고, 유통가공 중에 주문 흐름 탭(출고·검수…)이 그대로 남아 있어 잘못 눌리는 자리였다 |

프레임워크가 없으므로 **"HTML 문자열을 만드는 함수 + 이벤트를 붙이는 함수"** 쌍으로 만든다.

### 카메라 프리뷰 규칙 🔑 (`scanPreview`)

- **가이드 박스는 CSS 퍼센트가 아니라 JS 가 크기를 넣는다.** 비디오는 `object-fit: cover`
  로 잘려 보이므로 화면 45% 와 프레임 45% 가 다르다. `scanner.aimRect(상자폭, 상자높이)`
  가 실제 배율을 계산해 **디코더가 보는 밴드와 같은 자리**에 그린다
- **줌 버튼(1x·2x·3x)은 `scanner.canZoom()` 이 true 일 때만 그린다.** 기기가 줌을
  못 주면(iOS·대부분의 PC 웹캠) 버튼을 **아예 만들지 않는다** — 없는 기능을 눌러
  실패하는 것이 가장 나쁘다. 핀치 줌도 같은 조건이고, 상자는 `touch-action: pan-y`
  라 세로 스크롤은 그대로 두고 브라우저 확대만 막는다
- **인식 순간에는 `flash()`** 로 초록 하이라이트를 준다 (`scanBar` 가 자동으로 부른다.
  `scanPreview` 를 직접 쓰는 화면 — `#/stow` 로케이션 — 은 제출 지점에서 직접 부른다)
- 🔑 **`scanBar` 시그니처는 바뀌지 않았다.** 줌·가이드는 전부 `scanPreview` 안에서
  끝나므로 `mountScan` 을 쓰는 화면(ship·inspect)과 `scanBar` 를 직접 쓰는 화면
  (load·stow·pcheck)이 **고칠 것 없이** 함께 받는다

### 소프트키보드 규칙 🔑

- **스캔 바 입력칸은 기본 `inputmode="none"` 이다.** 탭에 들어오면 포커스는 잡되(블루투스
  스캐너 입력 유지) 폰 키보드는 뜨지 않는다. 손으로 칠 때만 독의 `자판` 버튼으로
  `inputmode="text"` + 포커스로 열고, 제출하거나 화면을 떠나면 다시 `none` 으로 돌아간다
  (입력칸을 눌러도 키보드가 안 뜨는 것은 의도된 동작이라 placeholder 에 `· 자판 버튼` 을 붙인다).
- **출고적치의 입력은 폰 키보드로 하고, `inputmode` 로 자판 종류만 가른다.** 로케이션
  입력칸은 구역코드 자동이면 `numeric`(숫자 자판), 수기면 `text`. 구역코드 입력칸은 영문
  2자리만 받으므로 `text` + `autocapitalize="characters"` 다. 앱 자판(계산기 배열)은
  폰 자판과 겹쳐 두 개로 보여 제거했다 — `inputmode` 는 `dock` 한 곳만 소유한다.

### 규약 (변경 없음)

- `render(root, { user, params })` → **정리 함수 반환** (카메라 정지·`db.subscribe` 해제·
  `VisualViewport` 리스너 해제)
- 🔑 **클릭 위임은 `root` 가 아니라 화면이 만든 컨테이너에 건다.** `root`(셸의 `#view`)는
  화면이 바뀌어도 살아남아, 거기 건 핸들러는 정리 함수로 지우지 않으면 **다음 화면의 탭까지
  가로챈다** (`innerHTML` 로 갈아 끼우는 것은 자식뿐이다 · 코드리뷰팀 2026-09-19)
- 사용자 입력은 전부 `esc()`
- 아이콘은 `icons.js` 단색 SVG. 이모지 금지
- 문자열 상수는 `config.js` (`APP_TABS` `APP_MENU` `PALLET_SCAN_STATUS` 등)
- CSS 는 `assets/css/mobile.css` 에만 쓰고 클래스는 **`m-` 접두**를 붙인다.
  `app.css` 의 클래스(`.pallet` `.work-head` `.stow-*` `.steps` 등)를 재사용하지 않는다 —
  6단계(웹 코드 정리)에서 그 클래스를 지워도 앱이 깨지지 않게 하기 위해서다.

## 5. 권한 (역할 × 화면)

역할명을 직접 비교하지 않는다. `can(user, ...)` / `allow()` 로만 판정한다.

| 역할 | 조회(탭·메뉴) | 처리(작업시작/완료 등) | 유통가공 검수 (`#/pcheck`) | 재고실사표 | 이슈 등록·댓글 |
|---|:---:|:---:|:---:|:---:|:---:|
| 관리자 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 용마담당자 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 화주관리자 | ✅ | ❌ 조회만 | ❌ 조회만 | ✅ | ✅ |
| 화주영업팀 | ✅ (본인 등록건만, `viewAll` false) | ❌ 조회만 | ❌ 조회만 | ✅ | ✅ |
| 현장작업자 | ✅ | ✅ | ✅ | ❌ (`download` 없음) | 등록·댓글만, 접수/승인 불가 |

- **조회는 모두 가능하다.** 셸(`mobile/app.js`)은 탭·메뉴를 `viewPerm` 으로만 거르고,
  처리 버튼 노출은 각 화면이 `can(user, 'updateStatus')` 로 따로 판단한다.
- 재고실사표(`#/stock`)는 `APP_MENU` 에서 `viewPerm: 'download'` 로 막혀 있어
  현장작업자에게는 메뉴 자체가 보이지 않는다.
- 🔑 **유통가공 검수는 `updateStatus` 로 판정한다** (`db.canCheckProcessing()`).
  등록 권한(`manageProcessing`)과 **다른 축**이다 — 화주관리자는 웹에서 작업을 등록하지만
  창고에 없어 검수를 하지 않고, 현장작업자는 등록은 못 하지만 사진을 찍는 사람이다
  ([processing.md §7](processing.md#7-권한) 참고). 유통가공 탭 자체는 모두에게 보인다
- 🔑 **서버도 같은 판정을 해야 한다.** `process_jobs` 의 update 정책이 등록 권한만 보던 탓에
  현장작업자의 검수가 **RLS 0행으로 조용히 실패**했다(PostgREST 는 오류를 주지 않는다).
  지금은 정책이 `updateStatus` 까지 열려 있고 **트리거가 검수 컬럼만 고치도록 좁힌다**
  ([processing.md §5-1](processing.md#5-1-모바일-검수-마이그레이션-17--멱등)).
  `store.js` 도 쓰기 결과를 되읽어 0행이면 오류를 던진다 — **앱에 「저장됐습니다」 만 뜨고
  서버 값이 그대로인 상태를 만들지 않는다**
- 🔑 **로그아웃하면 촬영 초안(IndexedDB)이 지워진다.** 사진은 세션 저장소가 아니라
  IndexedDB 에 있어 예전에는 로그아웃해도 남았다. **공용 단말**에서 다음 작업자가 앞사람의
  현장 사진을 그대로 보는 자리였다 (`auth.js` 의 `signOut`). 저장소를 못 열어도 로그아웃은 진행한다
- 🔑 **사진은 「활성 계정」만 읽는다.** 사진 메타·Storage 의 select 정책이
  `my_role() is not null` 이라 **중지된 계정(`active=false`)은 토큰이 남아 있어도 못 본다.**
  현장 사람·제품이 찍힌 개인정보에 가까운 자료라 사진에만 이 조건을 걸었다
- 이슈 처리(접수·담당자확인·종결요청·종결승인)는 `db.canAcceptIssue()` 등 **db.js 의 판정
  함수**를 그대로 쓴다. 웹과 앱이 같은 함수를 부르므로 판정이 갈라지지 않는다
  ([issues.md](issues.md#핵심-로직--상태-전이-) 참고).
- **댓글은 웹과 동일하게 누구나 등록할 수 있다** (현장작업자 포함). 수정·삭제는 작성자 본인만.

- **설치된 PWA 첫 실행은 옛 캐시로 열릴 수 있다.** "앱을 껐다가 다시 열어 주세요" 안내.

- **앱 인쇄는 아직 없다.** 재고실사표는 CSV만 지원한다(대표님 결정 H). 추후 제품검수 기능을
  추가할 때 인쇄 진입점을 붙일 예정이며, 화면 구조(`#toolbar` 자리)는 이미 비워 두었다.
- **웹의 모바일 반응형 처리 화면(`app.html` 의 `isMobile()` 분기)이 아직 코드에 남아 있다.**
  6단계(웹 코드 정리, 앱 운영 1주 후 예정)에서 걷어낸다. 그 전까지는 두 경로가 공존하지만
  실제 사용자는 `shellUrl()` 분기로 `m.html` 만 보게 된다 — [CLAUDE.md](../CLAUDE.md) 참고.
- 오프라인 대응은 이번 범위 밖이다(대표님 결정 E). 온라인 전제, 실패 시 재시도 안내만 한다.
