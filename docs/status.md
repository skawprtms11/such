# 주문처리현황

> 코드 `assets/js/pages/status.js` · 라우트 `#/status` · [공통 규약](common.md) · [CLAUDE.md](../CLAUDE.md)

주문의 처리 단계를 실시간으로 모니터링하는 화면.
**용마담당자가 단계를 눌러 진행 상태를 업데이트**하고, 화주 측은 그것을 실시간으로 확인한다.
모바일에서도 같은 화면을 그대로 쓴다.

---

## 접근 권한

| 역할 | 조회 범위 | 단계 업데이트 | 다운로드 |
|---|---|:---:|:---:|
| 관리자 | 전체 | — | ✅ |
| 용마담당자 | 전체 | — | ✅ |
| 화주관리자 | 전체 | — | ✅ |
| 화주영업팀 | **본인 등록건만** | — | ✅ |

**이 화면은 조회 전용이다.** 단계 업데이트는 각 처리 화면에서 한다.

## 화면 구성

### 상단 — 요약 (4칸)

**조회된 행 전체**를 대상으로 계산한다. (주문정보등록의 "당일" 요약과 다르다)

| 카드 | 계산 |
|---|---|
| 주문건수 | 행 수 |
| 품목수 | `item_count` 합 |
| 출고수량 | `qty` 합 |
| 진행률 | `sum(stage) / (행 수 × 5)` — 막대 그래프 포함 |

진행률이 100%면 막대가 초록색(`.bar__fill--done`)으로 바뀐다.

### 탭 🔑

상단에 탭 3개가 있고, 선택한 탭은 모듈 스코프에 기억된다.

| 탭 | 대상 | 기간 |
|---|---|---|
| **현재진행** | `closed_at` 도 `canceled_at` 도 없는 주문 | **없음 (전부)** |
| **출고완료** | `closed_at` 이 있는 주문 | 완료처리한 달 (기본 이번 달) |
| **출고취소** | `canceled_at` 이 있는 주문 ([주문정보등록](orders.md)에서 취소) | 취소한 달 (기본 이번 달) |

- **완료처리된 주문은 현재진행 목록에서 빠진다.** 이것이 목록을 비우는 유일한 수단이다
- 출고요청일 단건 필터는 없앴다. 기간으로 찾을 때는 상세검색을 쓴다

### 필터

| 항목 | 탭 | 기본값 |
|---|---|---|
| 조회 월 | 출고완료 · 출고취소 | 이번 달 |
| 주문번호 / 거래처명 | 전체 | 없음 |
| 상세검색 | 출고완료 · 출고취소 | 미적용 |

### 상세검색 🔑

우측 상단 `상세검색` 버튼으로 연다 (출고완료·출고취소 탭에만 있다).

| 항목 | 찾는 값 |
|---|---|
| 주문번호 | `order_no` 부분 일치 |
| 제목 | 주문의 `request_note`(요청사항) + 같은 주문번호로 등록된 **이슈 제목** |
| 내용 | 주문의 `remark`(비고) + **이슈 내용** + **조정요청 사유** |
| 출고요청일 기간 | `ship_req_date` 가 시작~종료 사이 |

- 주문 테이블에는 제목·내용 필드가 없어 **이슈·조정요청 본문을 주문번호로 이어 붙여** 훑는다
  (`textIndex()`). 본문 검색을 쓸 때만 색인을 만든다
- **기간을 넣으면 조회 월 대신 그 기간으로 찾는다.** 이때 월 선택은 비활성으로 바뀐다
- 적용 중이면 필터줄에 `상세검색 적용중` 태그와 `해제` 버튼이 나온다
- 조건은 탭별로 따로 기억된다

### 표

| 컬럼 | 비고 |
|---|---|
| 연번 | 역순 (`rows.length - i`) |
| 전송일자 | |
| 차수 | 2차수 이상 주황색 |
| 주문번호 | |
| 거래처명 | |
| 처리현황 | 5단계 배지 (아래 참고) |
| 진행률 | `stage / 5` (%) |
| 파렛트수 | [출고주문처리](shipping.md) 검수작업 탭에서 입력한 `pallet_count`. 없으면 `-` |
| 출고요청일 | `ship_req_date` |
| 상차라벨출력 | A4 라벨 인쇄 버튼 (아래 참고) |
| 완료처리 | 완료처리 버튼. 출고취소 탭에서는 `취소일시` 로 바뀐다 (아래 참고) |

### 모바일 표 (860px 이하) 🔑

좁은 화면에서는 **컬럼 4개만** 보여준다 (`mobileTable`).

```
출고요청일 · 주문번호 · 거래처명 · 처리현황
```

- **출고요청일이 맨 앞이다.** 현장에서 가장 먼저 보는 값이라 왼쪽에 둔다
- **전송일자는 넣지 않는다.** 필요하면 행을 눌러 상세 팝업에서 본다

- **처리현황은 단계 흐름 전체가 아니라 마지막으로 끝난 단계 하나만** 표시한다
  (`lastStepTag`). 아무것도 끝나지 않았으면 `미착수` 회색 태그다
- ⚠️ `steps.js` 의 `currentStep()` 은 **다음에 할 단계**를 돌려주므로 여기서 쓰지 않는다.
  CSV 다운로드가 그 값을 쓴다
- 연번·전송일자·차수·진행률·파렛트수·상차라벨출력은 나오지 않는다.
  **상차라벨 출력은 PC 에서만 한다**
- 🔑 **모바일에서는 상단의 `다운로드` 버튼과 탭 안내 문구도 감춘다.**
  좁은 화면을 목록에 내주기 위해서다 (`isMobile()` 판정).
  창 크기가 기준점을 넘나들면 `matchMedia` 의 `change` 로 상단 버튼까지 다시 그린다
- 요약 4칸도 모바일에서는 **높이를 25% 낮춰** 표시한다 (`@media (max-width: 860px)`)
- 기준점은 출고주문처리와 같은 `(max-width: 860px)` 이고,
  창 크기가 넘나들면 `matchMedia` 의 `change` 로 표를 다시 그린다
- 밀도는 CSS 의 `table.grid--mobile` 이 낮춘다 (폰트 11.5px, 거래처명만 줄바꿈 허용).
  컬럼을 더 넣으면 가로 스크롤이 생기므로 실제 폭(420px 등)에서 확인한다
- **행을 누르면 상세 팝업이 열린다** (`openDetail`). 표에서 뺀 차수·차량구분·요청작업·
  파렛트수·박스수·진행률·요청사항·비고와 **단계별 완료 일시**까지 보여주고,
  하단에서 **완료처리**도 할 수 있다
- 처리현황 배지는 취소된 건이면 `취소`, 완료처리된 건이면 `출고완료` 로 바뀐다
- 팝업은 모듈 스코프의 `detailModal` 로 들고 있다가 **화면을 떠날 때 함께 닫는다.**
  라우터는 화면 모듈의 정리 함수만 부르고 열린 모달을 치우지 않기 때문이다

## 완료처리 🔑

상차작업까지 끝난 주문을 **용마담당자가 최종 마감**하는 단계다 (`db.closeOrder()`).

```
상차작업 완료(loaded_at) ──[완료처리]──▶ closed_at 기록 ──▶ 출고완료 탭으로 이동
```

| 조건 | 표시 |
|---|---|
| 상차작업 전 | `-` (툴팁으로 이유를 알려준다) |
| 상차 완료 · 처리 권한 있음 | `완료처리` 버튼 |
| 상차 완료 · 조회 권한만 | `-` |
| 완료처리됨 | `완료` 태그 + `취소` 버튼(권한 있을 때) |

- 권한은 `can(user, 'updateStatus')` — **관리자와 용마담당자만** 누를 수 있다
- `db.closeOrder()` 가 **상차작업(`loaded_at`)이 없는 주문을 거부한다.** 화면 조건과 이중으로 막는다
- 취소된 주문은 완료처리할 수 없다
- 완료처리를 되돌리면(`취소`) 다시 현재진행 탭으로 돌아온다
- 변동사항 이력에 `출고완료: 진행 → 완료` 로 남는다
- **모바일에는 완료처리 컬럼이 없다.** 행을 눌러 연 상세 팝업 하단에서 처리한다

## 상차라벨 출력 🔑

검수가 끝난 파렛트에 붙이는 A4 라벨을 인쇄한다.
새 창에 라벨을 그리고 인쇄 대화상자를 자동으로 띄운다 (`printLoadLabel` · `labelHtml`).

### 출력 매수 🔑

**파렛트 1장당 앞뒤 2매**를 뽑는다. `labelPages()` 가 페이지 목록을 만든다.

```
4파렛트 → 4/1 4/1 4/2 4/2 4/3 4/3 4/4 4/4   (총 8장)
```

연번은 **`총장수/현재장`** 형식으로 우측 하단에 14pt 로 넣는다.
표의 `상차라벨출력` 버튼에 마우스를 올리면 총 몇 장인지 알려준다.

### 라벨 구성

| 항목 | 값 | 크기 |
|---|---|---|
| 출고일자 | `ship_req_date` | 45pt |
| 주문번호 | `order_no` | 45pt |
| 거래처명 | `customer` | 45pt |
| 주문일자 | `reg_date` | 34pt |
| 총 파렛트수 | `pallet_count` | 34pt |
| 박스수 | **빈칸** — 현장에서 손으로 적는다 | 30mm 높이 |
| 바코드 | `order_no` 의 Code128 (`barcode.js` 의 `code128Svg`) | 폭 100% |
| 연번 | `총장수/현재장` | 14pt |
| **추가건 표시** | `추가건 - 2차수` (2차수 이상일 때만, 오른쪽 위) | **20pt** |

- 🔑 **혼적 추가건(2차수 이상 · 0파렛트)도 라벨을 뽑는다.** 파렛트가 없어도
  1장분(앞뒤 2장)을 출력하고, `총 파렛트수` 칸에 **`기존차수에 혼적적재`** 라고 적는다
- **검수작업이 완료되고 파렛트수가 있을 때만** 버튼이 나온다 (혼적 추가건은 예외).
  아니면 `-` 로 표시한다 (라벨에 총 파렛트수와 연번이 들어가기 때문이다)
- ⚠️ **45pt 는 주문번호(11자)와 거래처명이 한 줄에 들어가는 상한이다.**
  더 키우면 줄바꿈되어 오히려 읽기 어려워진다. 항목을 추가할 때도 A4 한 장을
  넘지 않는지 PDF 로 확인한다
- 바코드는 **주문번호**다. 상차 검수용 파렛트 바코드(`{주문번호}-P01`)와 다르다
- 인쇄 규격은 `@page { size: A4 portrait; margin: 10mm }` 고정이고,
  페이지 구분은 `.label { page-break-after: always }` 로 한다
- 팝업이 차단되면 토스트로 알린다

## 핵심 로직 — 처리현황 단계 🔑

**이 화면에서 단계를 직접 바꾸지 않는다.** 각 화면의 처리 결과가 자동으로 반영된다.

```
주문처리 → 출고작업 → [요청작업] → 검수작업 → 출고적치 → [조정작업] → [추가작업] → 상차작업
```

| 단계 | 완료되는 곳 | 저장 필드 | 표시 조건 |
|---|---|---|---|
| 주문처리 | [주문정보등록](orders.md)의 접수 체크 | `confirmed_at` | 항상 |
| 출고작업 | [출고주문처리](shipping.md) > 출고작업 탭 | `ship_done_at` | 항상 |
| 요청작업 | 출고주문처리 > 검수작업 탭의 요청작업 확인 | `req_work_at` | **`extra_works` 가 있을 때만** |
| 검수작업 | 출고주문처리 > 검수작업 탭 | `inspect_done_at` | 항상 |
| 출고적치 | 출고주문처리 > 출고적치 탭 (파렛트 로케이션 전량 입력) | `stow_done_at` | 항상 |
| 조정작업 | [주문정보등록](orders.md) 이력 팝업에서 조정요청을 모두 확인 처리 | *(계산값)* | **조정요청이 있을 때만** |
| 추가작업 | 출고주문처리 > 추가작업 탭 | `extra_done_at` | **추가작업 요청이 있을 때만** |
| 상차작업 | [당일상차리스트](loading.md)의 상차완료 | `loaded_at` | 항상 |

- 단계 정의는 `config.js` 의 `WORK_STEPS`, 계산은 `assets/js/steps.js` 가 담당한다
- ⚠️ **조정작업만 저장 필드가 없다.** 등록된 조정요청이 모두 확인 처리되었는지로 판단한다
  (`db.adjustMap()` 이 `{ has, done }` 을 계산해 넘긴다)
- 화살표(`→`)로 이어 표시하며, 완료된 단계는 초록으로 채워진다 (`.steps--flow`)
- 🔑 **실제로 착수한 단계만 노란색으로 표시한다** (`.step.is-current`).
  차례가 됐다는 이유만으로는 켜지 않는다 — 아무도 손대지 않은 작업이
  진행중으로 보이면 현황을 잘못 읽게 된다

| 단계 | 노란색이 켜지는 시점 |
|---|---|
| 출고작업 | `작업시작` 을 눌러 `ship_started_at` 이 찍힌 때 |
| 상차작업 | 상차라벨을 **한 장이라도 스캔**한 때 (`inspected > 0`) |
| 그 밖의 단계 | 착수를 따로 기록하지 않아 **표시하지 않는다** |

  판단은 `steps.js` 의 `started()` 가 하고, `WORK_STEPS` 의 `startAt` 이 근거 필드다.
  **취소된 주문과 모든 단계가 끝난 주문에는 노란 단계가 없다**
- 진행률 = 보이는 단계 중 완료된 비율 (`stepRate`)
- 툴팁에 각 단계의 완료 일시가 나온다
- 취소된 주문은 행이 연한 글씨로 표시된다 (`tr.is-canceled`)

조건부 단계 때문에 주문마다 표시되는 단계 수가 다르다. 진행률 분모도 그에 맞춰 달라진다.


## CSV 다운로드

**웹에서만 쓴다.** 모바일에서는 상단 버튼 자체가 나오지 않는다.
파일명 `주문처리현황_{탭}_YYYY-MM-DD.csv` — **현재 탭에 보이는 행만** 내려받는다.

```
연번, 전송일자, 차수, 주문번호, 거래처명, 출고요청일, 처리현황, 진행률,
파렛트수, 박스수, 완료처리
```

`처리현황` 은 단계명 문자열로 변환해 넣는다 (`stage=0` 이면 `미착수`).

## 실시간 갱신

`db.subscribe(reload)` — 5초 폴링.
용마담당자가 PC 에서 단계를 바꾸면 화주 담당자의 휴대폰 화면도 5초 안에 따라온다.
상단바의 `● 실시간` 배지가 이 동작을 나타낸다.

## 수정 시 주의

- **단계명을 화면 코드에 직접 쓰지 않는다.** 항상 `config.js` 의 `WORK_STEPS` 를 참조한다
- 이 화면은 조회 전용이다. 단계를 직접 바꾸는 기능을 되살리지 않는다
  (처리 화면과 상태가 어긋난다)
- 상차리스트 진입 조건도 같은 단계 정의를 쓴다 (`steps.js` 의 `readyToLoad`)
