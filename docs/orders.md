# 주문정보등록

> 코드 `assets/js/pages/orders.js` · 라우트 `#/orders` · [공통 규약](common.md) · [CLAUDE.md](../CLAUDE.md)

화주 영업사원이 출고 주문을 게시판 형태로 등록하고, 이후 변동사항을 수정하며
그 이력을 남기는 화면. 업무 흐름의 **시작점**이다.

---

## 접근 권한 🔑

**이 화면만 역할이 아니라 역할 + 소속으로 판정한다.** 다른 화면은 역할만 본다.

| 역할 | 작성 (등록·수정·조정요청) | 확인 (접수/수정/조정 체크, 이력 확인처리) |
|---|:---:|:---:|
| 관리자 | ✅ 항상 | ✅ 항상 |
| 화주관리자 | ✅ 항상 | ✅ 항상 |
| 화주영업팀 · 용마담당자 | 소속이 **고객사**일 때만 | 소속이 **용마로지스**일 때만 |

정책은 `config.js` 의 `ORDER_POLICY` 에 있고, `auth.js` 의 `allow()` 가 판정한다.
**역할이 목록에 있거나, 소속이 목록에 있으면 허용**한다.

```js
function canWrite(user) { return allow(user, ORDER_POLICY.write); }
function canConfirm(user) { return allow(user, ORDER_POLICY.confirm); }
```

- `주문 등록` 버튼, 상세 팝업의 `수정`·`조정요청` 버튼 → `canWrite()`
- 확인 컬럼 체크박스, 이력 팝업의 확인처리 버튼 → `canConfirm()`
- **역할명이나 소속명을 화면 코드에 직접 쓰지 않는다.** 항상 정책 객체를 거친다

### 조회 범위

조회 범위는 기존대로 역할 기반(`viewAll`)이다. 화주영업팀만 본인 등록건으로 제한된다.

```js
const rows = await db.listOrders({
    ...filter,
    createdBy: can(user, 'viewAll') ? undefined : user.id,
});
```

### 소속 값

`config.js` 의 `COMPANY` 가 유일한 출처다. **자유 입력이 아니라 선택값**이다
(사용자관리 화면에서 목록으로 고른다). 오타가 나면 권한이 어긋나므로 문자열을 직접 쓰지 않는다.

| 코드 | 값 | 역할 |
|---|---|---|
| `COMPANY.CUSTOMER` | 고객사 | 주문을 등록하는 쪽 (구 더퓨어랩) |
| `COMPANY.LOGISTICS` | 용마로지스 | 주문을 처리·확인하는 쪽 (구 용마물류) |

기존 저장 데이터의 옛 명칭은 `db.js` 의 `normalize()` 가 자동으로 바꿔준다.

## 화면 구성

### 필터

| 항목 | 기본값 |
|---|---|
| 등록일 시작 | 30일 전 |
| 등록일 종료 | 오늘 |
| 주문번호 / 거래처명 | 없음 (부분 일치, 대소문자 무시) |

필터 상태는 모듈 스코프의 `filter` 객체에 보관한다. 다른 메뉴에 갔다 돌아와도 유지된다.

### 게시판 표

| 컬럼 | 비고 |
|---|---|
| 연번 | **역순**. 최신 행이 가장 큰 번호 (`rows.length - i`) |
| 등록일자 | `reg_date` — 시스템이 자동 기록 |
| 전송일자 | `send_date` — 사용자 입력 |
| 담당자 | **주문을 등록한 사용자 이름.** `created_by` 를 사용자 목록과 대조해 표시한다 |
| 차수 | 2차수 이상은 주황색(`.seq--multi`) |
| 주문번호 | 클릭 시 상세 팝업. 우측 위에 **건수 배지** (아래 참고) |
| 거래처명 | |
| 추가작업 | 선택한 항목을 파란 태그로. 없으면 `-` |
| 요청사항 | 줄바꿈 허용(`.wrap`) |
| 출고요청일 | |
| 확인 | **접수 체크박스** 하나. 색으로 상태를 알린다 (아래 참고) |
| 진행상태 | 대기 / 진행 / 완료 / 취소 배지 (아래 참고) |

**수정·조정요청·이력 확인은 모두 주문번호를 눌러 여는 상세 팝업에서 처리한다.**

### 주문번호 건수 배지 🔑

수정이나 조정요청이 생기면 주문번호 **우측 위에 합계 건수**가 붙는다 (`<sup class="cnt-badge">`).

| 상태 | 색 |
|---|---|
| 확인처리가 1건이라도 남음 | **빨강** (`.is-pending`) |
| 모두 확인처리됨 | **초록** (`.is-done`) |
| 수정·조정요청 없음 | 배지 없음 |

```js
const total = st.edits + st.restores;        // 표시 건수
const left = st.editsLeft + st.restoresLeft; // 0 이면 초록, 아니면 빨강
```

- 판정 근거는 `db.checkStats()` 가 돌려주는 `{edits, editsLeft, restores, restoresLeft}`
- 툴팁에 `수정 1건 · 조정요청 1건 · 미확인 2건` 처럼 내역이 나온다
- 상세 팝업의 수정이력·조정요청 탭에서 확인처리하면 색이 바뀐다

### 확인 컬럼 - 접수 체크박스 🔑

체크박스는 **접수 하나뿐**이다. 색으로 세 가지 상태를 알린다.

| 상태 | 색 | 조건 |
|---|---|---|
| 접수 전 | **흰색** | `confirmed_at` 이 없음 |
| 접수 완료 | **초록** (`.chk.is-on`) | 접수됨 + 확인할 수정·조정이 없음 |
| 확인 필요 | **빨강** (`.chk.is-alert`) | **접수됐지만 수정·조정 미확인이 남음** |

```
등록              →  흰색
접수 체크          →  초록
수정/조정 발생      →  빨강   (이력 버튼도 함께 빨강)
이력에서 모두 확인   →  다시 초록
```

빨간 상태는 **이력 팝업에서 건별로 확인**해야 풀린다. 표에서는 일괄 확인하지 않는다.
(일괄 확인은 이미 확인한 건의 확인자·시각을 덮어쓸 위험이 있어 화면에서 제거했고,
쓰이지 않게 된 일괄 확인 API 도 함께 지웠다. 확인은 건별 토글만 있다)

- 취소된 주문은 접수 체크박스가 잠긴다
- 확인 권한이 없으면 `disabled` 로 표시만 한다
- 접수 체크는 되돌릴 수 있다. 확인 시각·확인자는 툴팁과 상세 팝업에서 볼 수 있다
- 이력 팝업에서 확인 상태를 바꾸면 `reload()` 를 함께 호출해 색을 즉시 반영한다

### 진행상태 컬럼 🔑

**저장하지 않고 주문 상태에서 계산한다** (`progressOf()`). 우선순위가 있다.

| 상태 | 조건 | 배지 색 |
|---|---|---|
| **취소** | `canceled_at` 이 있음 (다른 조건보다 우선) | 빨강 |
| **완료** | `stage >= 5` (상차완료) | 초록 |
| **진행** | `confirmed_at` 이 있음 (접수됨) | 파랑 |
| **대기** | 그 외 (등록만 된 상태) | 회색 |

값 목록은 `config.js` 의 `PROGRESS` 가 유일한 출처다.
Supabase 에서도 컬럼이 아니라 `order_progress()` 함수로 같은 규칙을 계산한다.

### 주문 취소 🔑

상세 팝업 하단 `수정` 오른쪽의 **`취소` 버튼**으로 처리한다. 확인 대화상자를 거친다.

```js
canCancel(user, o)  // canWrite(user) && !o.canceled_at
```

취소하면:

- 진행상태가 **취소**로 바뀐다 (다른 조건보다 우선)
- 표의 해당 행이 **연한 글씨**로 바뀐다 (`tr.is-canceled`).
  취소 배지와 이력 버튼은 흐려지지 않아 계속 읽을 수 있다
- **수정·조정요청이 막힌다** (`canEdit()` / `canRestore()` 가 false)
- 접수 체크박스가 잠긴다
- 이력에 `취소` 이벤트가 기록된다 (취소자·시각 포함)

⚠️ **취소는 되돌릴 수 없다.** 해제가 필요하면 `cancelOrder()` 의 짝이 되는 함수를 추가해야 한다.


### 일괄등록 🔑

상단 `일괄등록` 버튼으로 연다. **엑셀에서 복사한 표를 그대로 붙여넣는다.**

| 요소 | 설명 |
|---|---|
| 안내 문구 | 팝업 상단에 사용법 4단계와 입력 규칙을 표시한다 |
| `양식 다운로드` | **컬럼 순서 참조용** CSV (필수 항목은 머리글에 `(필수)` 표기) |
| 표 | 등록 폼과 같은 8개 컬럼. 기본 5행 |
| `행 추가` / `전체 지우기` | 수동 조작 |

- **붙여넣기(`paste`)로 행이 자동으로 늘어난다.** 첫 칸에서 8행을 붙여넣으면 표가 8행이 된다
  (탭=열, 줄바꿈=행으로 파싱한다. 단일 값 붙여넣기는 기본 동작 유지)
- 날짜는 `2026-08-30` · `2026/8/30` · `20260830` 을 모두 인식해 `YYYY-MM-DD` 로 정규화한다
  (`normDate()`)
- 추가작업은 한 칸에 여러 개를 넣을 수 있다. **쉼표(`,`) 또는 슬래시(`/`)** 로 구분한다
  (예: `라벨작업, LOT지정` · `라벨작업/박스교체`). `EXTRA_WORKS` 에 없는 값은 오류로 잡는다
- 등록 전 검증에서 걸리면 **행 번호와 함께 오류를 모아 보여주고 등록하지 않는다**
  (`1행: 차량구분은 픽업/용차 만 가능`)
- 빈 행은 건너뛴다. 차수는 등록 시 `db.createOrder()` 가 자동으로 계산한다

### 처리 단계에 따른 조작 제한 🔑

주문이 진행될수록 손댈 수 있는 범위가 줄어든다. 판정은 두 헬퍼가 담당한다.

```js
canEdit(user, o)     // can(user, 'createOrder') && o.stage < 5
canRestore(user, o)  // can(user, 'createOrder') && o.stage < 4
```

| `stage` | 상태 | 수정 | 조정요청 |
|:---:|---|:---:|:---:|
| 0 | 미착수 | ✅ | ✅ |
| 1 | 주문처리 | ✅ | ✅ |
| 2 | 출고작업 | ✅ | ✅ |
| 3 | 라벨작업 | ✅ | ✅ |
| 4 | **패킹리스트 완료** | ✅ | ❌ |
| 5 | **상차완료** | ❌ | ❌ |

- **수정은 상차완료 전까지.** 차에 실린 뒤에는 주문 내용을 바꿀 수 없다
- **조정요청은 패킹리스트 완료 전까지.** 포장이 끝난 뒤에는 되돌릴 수 없으므로
  [이슈등록](issues.md)으로 처리한다
- 조정요청 건수 태그는 단계와 무관하게 계속 보인다 (기록 조회용)
- **조정요청을 등록하면 이슈등록에 `작업요청` 이슈가 자동으로 함께 등록된다**
  (`auto_created` — 목록에 `자동등록` 태그가 붙는다. [issues.md](issues.md) 참고)

## 등록 폼

입력 항목은 **8개다.** 추가작업은 요청사항 바로 앞에 놓인다.

| 항목 | 필드 | 필수 | 비고 |
|---|---|:---:|---|
| 전송일자 | `send_date` | ✅ | 기본값 오늘 |
| 주문번호 | `order_no` | ✅ | |
| 거래처명 | `customer` | ✅ | |
| 출고요청일 | `ship_req_date` | ✅ | 기본값 오늘 |
| 차량구분 | `vehicle_type` | ✅ | `픽업` / `용차` (`config.VEHICLE_TYPES`) |
| **추가작업** | `extra_works` | | **체크박스 다중 선택** (`config.EXTRA_WORKS`) |
| 요청사항 | `request_note` | | textarea |
| 비고 | `remark` | | |

수정 시에는 **변경 사유**(`memo`) 입력란이 추가로 나타나고, 이력에 함께 기록된다.

### 여기에 없는 항목

`item_count`(품목수) · `qty`(출고수량) · `pallet_count`(파렛트수) 는
**사용자 요청으로 등록 폼에서 제거되었다.** 데이터 모델에는 남아 있고
조회(요약·상세·CSV)에는 계속 표시된다. 다시 추가하지 말 것 — 입력 주체가 결정되면
용마담당자 화면이나 WMS 연동으로 채울 예정이다.

## 핵심 로직

### 차수 부여 🔑

등록 폼 상단에서 **신규주문 / 추가주문**을 고른다. 차수는 그 선택으로만 정해진다.

| 선택 | 주문번호 | 차수 |
|---|---|---|
| **신규주문** (기본) | 직접 입력 | 항상 `1차수` |
| **추가주문** | **기존 주문번호를 목록에서 선택** → `a11111-1` 자동 생성 | 그 묶음의 `max(seq) + 1` |

🔑 **추가주문은 주문번호 뒤에 `-1`, `-2` 가 붙는다.** 목록에서 기준 번호(`a11111`)를 고르면
다음 번호(`a11111-1`)가 입력칸에 자동으로 채워진다. 필요하면 직접 고칠 수 있다.
묶음 판정은 주문번호가 아니라 **`base_no`(1차수 주문번호)** 로 한다.

- 추가주문 목록은 `db.listOpenOrderNos()` 가 준다.
  **종결된 주문번호(완료처리 `closed_at` · 취소 `canceled_at`)는 나오지 않는다**
- `<datalist>` 자동완성이며, 고르면 `현재 2차수 → 3차수로 등록됩니다` 안내와 함께
  거래처명이 자동으로 채워진다 (비어 있을 때만)
- 목록에 없는 번호를 넣고 추가주문으로 등록하면 `db.createOrder()` 가 거부한다
- 조회 권한을 따른다 (화주영업팀은 본인 등록건만 목록에 나온다)
- ⚠️ **같은 주문번호로 등록한다고 자동으로 차수가 올라가지 않는다.**
  신규주문이 2차수로 들어가는 문제가 있어 그 규칙을 없앴다
- 일괄등록은 신규주문으로만 들어간다

사용자는 차수 숫자를 직접 입력하지 않는다. `db.createOrder()` 가 계산한다.

```js
const { addition, ...rest } = payload;
const same = db.orders.filter((o) => o.order_no === rest.order_no);
const seq = addition ? Math.max(...same.map((o) => o.seq)) + 1 : 1;
```

- 신규주문 → 항상 `1차수`
- 추가주문 → `2차수`, `3차수` ...
- 등록 완료 토스트가 부여된 차수를 알려준다

Supabase 쪽 자동 증가 트리거(`trg_set_order_seq`)는 **제거했다.**
차수는 화면이 정해서 넣는다 (`orders_no_seq_idx` 유니크 인덱스는 그대로 중복을 막는다).
이미 적용한 DB 가 있다면 `supabase/schema.sql` 의 주석대로 트리거를 지운다.

### 추가작업 (다중 선택) 🔑

`config.js` 의 `EXTRA_WORKS` 가 목록의 유일한 출처다.
현재 `라벨작업`, `박스교체`, `LOT지정` 세 가지.
항목을 추가하면 `supabase/schema.sql` 의 `extra_work` 열거형도 함께 맞춘다.

**값은 배열(`string[]`)로 저장된다.** 체크박스라 `FormData` 에서 일반적인 방법으로는
하나만 읽히므로 `getAll()` 로 따로 읽어야 한다.

```js
const form = new FormData(e.target);
const fd = Object.fromEntries(form);
fd.extra_works = form.getAll('extra_works');   // ← 이 줄이 없으면 값이 하나만 저장된다
```

이력 기록과 변경 감지는 `db.js` 의 `toText()` 가 배열을 `'라벨작업, 박스교체'` 로 합쳐 처리한다.

Supabase 에서는 `extra_work` 열거형의 배열(`extra_work[]`)로 저장한다.

### 조정요청 🔑

등록된 주문의 조정(되돌림)을 요청하는 기능. 표의 **관리 컬럼 왼쪽**에 있다.

- `조정` 버튼은 `can(user, 'createOrder')` 인 사용자에게만 보인다
- 요청이 쌓이면 옆에 `N건` 주황 태그가 붙고, 누르면 내역 모달이 열린다
- 처리 단계와 무관하게 언제든 요청할 수 있다 (수정과 달리 `stage` 제한이 없다)

**작성 방식을 두 가지 중 하나로 고른다.**

| 방식 | `type` | 입력 항목 |
|---|---|---|
| 이메일로 발송 | `email` | **조정사유(선택)만.** 별도 작성 내용 없음 |
| 여기에 작성 | `form` | 주문번호 · 거래처명 · 제품코드 · 수량 · 조정사유(텍스트) |

- 기본 선택은 `이메일로 발송`
- `여기에 작성` 의 주문번호·거래처명은 해당 주문 값으로 채워지고 `readOnly` 다
- 사유 선택 목록은 `config.js` 의 `RESTORE_REASONS`
  (⚠️ 실제 업무 사유로 확정되지 않은 임시 목록)

**숨긴 입력란은 `hidden` 만으로 부족하다.** 필수값 검증과 전송 대상에서 빠지도록
`disabled` 를 함께 토글한다. `switchPane()` 이 그 처리를 한다.

```js
paneForm.querySelectorAll('select, input, textarea')
    .forEach((el) => { el.disabled = isEmail; });
```

등록하면 `restore_requests` 에 저장되고, **주문 이력에도 함께 기록된다**
(`조정요청: 이메일 발송 · 수량 변경`). 이력 버튼으로도 확인할 수 있다.

⚠️ **`이메일로 발송` 을 선택해도 실제 메일은 나가지 않는다.** 현재는 요청 기록만 남는다.
발송에는 서버(Supabase Edge Function 등)가 필요하다.

### 수정 횟수 (`edit_count`) 🔑

**한 번의 수정은 여러 항목이 바뀌어도 1회로 센다.** 변경분을 먼저 모은 뒤 한 번만 올린다.

```js
const changed = Object.entries(patch).filter(([k, v]) => toText(o[k]) !== toText(v));
if (changed.length) {
    o.edit_count = (o.edit_count ?? 0) + 1;
    changed.forEach(([k, v]) => {
        addHistory(db, id, labels[k] ?? k, o[k], v, user, memo, o.edit_count);
        o[k] = v;
    });
}
```

- 값이 실제로 바뀌지 않으면 횟수가 오르지 않는다
- 각 이력 줄에는 몇 번째 수정인지(`rev`)가 함께 남아 이력 모달에 `2회차 수정` 으로 표시된다
- 표의 관리 컬럼에 `2건` 회색 태그로 보인다. 0회면 태그를 그리지 않는다
- 처리현황 변경(`setStage`)은 사용자의 주문 수정이 아니므로 `rev = 0` 이고 횟수에 포함되지 않는다

### 변동사항 이력 🔑

`db.updateOrder()` 가 **변경된 항목마다 한 줄씩** 기록한다.

```js
Object.entries(patch).forEach(([k, v]) => {
    if (String(o[k] ?? '') === String(v ?? '')) return;   // 안 바뀐 항목은 건너뜀
    addHistory(db, id, labels[k] ?? k, o[k], v, user, memo);
    o[k] = v;
});
```

- 이력에는 한국어 항목명이 들어간다 (`send_date` → `전송일자`)
- 변경 사유(`memo`)는 그 변경 묶음 전체에 함께 붙는다
- `이력` 버튼으로 모달에서 확인한다. 항목 · 변경 전 → 후 · 사유 · 일시 · 변경자

`pallet_count` 가 바뀌면 **검수 바코드를 전부 재생성하고 검수 상태를 초기화한다.**
이미 검수 중이던 건이 있으면 처음부터 다시 스캔해야 한다.

### 상세 모달의 '수정됨' 표시와 이전 내용 보기 🔑

주문번호를 누르면 열리는 상세 모달에서, **수정된 적이 있는 항목에 주황색 `수정됨` 배지**가 붙는다.

`db.listHistory(orderId)` 를 한 번 불러 `rev > 0` 인 이력을 항목별로 모은다.
같은 항목이 여러 번 바뀌었으면 **오래된 순**으로 쌓는다.

```js
const editLog = {};
history.filter((h) => h.rev > 0).forEach((h) => {
    (editLog[h.field] ??= []).unshift(h);   // listHistory 는 최신순이라 unshift 로 뒤집는다
});
```

**배지가 붙은 항목은 눌러서 이전 내용을 펼쳐 볼 수 있다.**

```
거래처명 [수정됨]  무신사 로지스틱스                    ▾
  ┌ [최초 내용] 무신사 스토어
  │ 1회차  무신사 스토어  →  무신사 스토어 2센터
  │        2026-08-29 06:41 · 김관리 · 거래처 정정
  │ 2회차  무신사 스토어 2센터  →  무신사 스토어 3센터
  └ …
```

- 맨 위에 **최초 내용**(첫 변경의 `before` 값)을 따로 보여준다
- 그 아래 회차별로 `이전 → 이후`, 일시·작성자·변경 사유를 나열한다
- 클릭과 키보드(Enter / Space) 모두 동작한다 (`role="button"` + `tabindex="0"`)
- 수정 이력이 없는 항목에는 `data-field` 를 붙이지 않아 눌리지 않는다

⚠️ **이력의 항목명(한국어 라벨)과 상세 모달의 항목 이름이 정확히 일치해야 한다.**
`품목수` 와 `출고수량` 을 `품목수 / 출고수량` 처럼 합치면 배지도 이전 내용도 사라진다.
항목 이름을 바꾸면 `db.js` 의 `labels` 도 함께 고친다.

상단에는 `이 주문은 2회 수정되었습니다` 안내가 함께 나온다.

### 상세 팝업 - 탭 구조 🔑

주문번호를 누르면 열린다. **최대 폭 1120px(`modal--xl`)** 이고 세 개의 탭으로 나뉜다.

| 탭 | 내용 | 하단 버튼 |
|---|---|---|
| **주문정보상세** | 항목 2열 그리드. `수정됨` 배지, 눌러서 이전 내용 펼치기 | `수정` |
| **조정요청** | 요청항목 선택 + 등록 폼 + 등록된 요청 목록(접수 처리) | 없음 |
| **수정이력** | 실제 수정 내용만 표시 (건별 확인처리) | 없음 |

- 하단 버튼은 탭에 따라 바뀐다
- ⚠️ **조정요청의 `저장` 버튼은 하단이 아니라 등록 카드 안에 있다.**
  아래쪽 목록과 붙어 있으면 목록에 대한 버튼으로 오해할 수 있어 입력 바로 밑에 뒀다
- **하단에 취소 버튼은 두지 않는다.** 닫기(×)와 헷갈리기 때문이며,
  주문 취소는 조정요청의 `전체취소` 항목으로 처리한다
- 팝업을 닫으면 목록을 갱신한다

#### 조정요청 탭

**요청항목**을 먼저 고른다. 선택하면 아래에 설명이 표시된다 (`config.js` 의 `ADJUST_CATEGORIES`).

| 항목 | 설명 |
|---|---|
| **전체취소** | 주문 전체 취소 처리 (복구 불가하며 주문 재등록 필요) |
| 부분취소 | 특정 제품 또는 특정 수량만 취소 |
| 전체보류 | 주문 전체 출고상차 보류 (출고 작업은 진행) |
| 부분보류 | 특정 제품 또는 특정 수량만 출고상차 보류 (출고 작업은 진행) |
| 기타요청 | 그 외 특이사항 요청 (기본 선택) |

⚠️ **`전체취소` 는 저장 시 주문 자체를 취소 처리한다** (`cancelsOrder: true`).
확인 대화상자를 한 번 더 거치고 설명도 빨간색으로 표시된다.
저장하면 진행상태가 `취소` 로 바뀌고 목록 행이 연한 글씨가 된다.

- 작성 방식(`이메일로 발송` / `여기에 작성`)은 그대로다.
  숨긴 입력란은 `disabled` 로 함께 막는다
- 등록된 요청은 **요청항목 태그**와 함께 목록에 나온다
- 용마담당자가 **`접수`** 버튼으로 처리하면
  [출고주문처리](shipping.md)의 조정요청 탭에 자동 등록된다
- 모두 접수되면 주문처리현황의 **조정작업** 단계가 완료된다

#### 수정이력 탭

- **`rev > 0` 인 실제 수정만 보여준다.** 등록·처리현황·접수확인 이벤트는 제외한다
- 항목별 `이전 → 이후`, 변경 사유·일시·작성자·회차를 표시한다
- 우측 `수정확인` 버튼으로 건별 확인처리한다


### 이력 모달

두 구역으로 나뉜다.

| 구역 | 내용 |
|---|---|
| 변동 이력 | 항목명 + **이전 → 이후** 비교, 변경 사유, 일시·작성자·회차, **우측에 수정확인** |
| 조정요청 | 작성 방식 배지, 사유, 제품코드/수량, 일시·작성자, **우측에 접수 버튼** |

- 수정 항목은 `이전` / `이후` 상자로 나란히 보여준다 (`.diff` 스타일)
- `rev = 0` 인 등록·삭제 이벤트는 이전/이후 없이 한 줄로 표시한다
- **조정요청은 전용 구역에서 보여주므로 변동 이력 목록에서는 제외한다.**
  (데이터에는 남아 있고 화면에서만 걸러낸다)

### 확인 체크 (수정확인 · 접수) 🔑

담당자가 내용을 확인했는지 **건별로** 체크한다. 두 구역 모두 항목 우측에 붙으며
`checkControl()` 하나를 공유한다.

| 구역 | 버튼 문구 | 데이터 속성 | 토글 함수 |
|---|---|---|---|
| 변동 이력 | `수정확인` | `data-check` | `db.toggleHistoryCheck()` |
| 조정요청 | `접수` | `data-check-restore` | `db.toggleRestoreCheck()` |

⚠️ **확인은 건별로만 한다.** 일괄 확인은 이미 확인된 건까지 다시 써서
**먼저 확인한 사람과 시각을 지울** 위험이 있어 화면과 API 양쪽에서 제거했다.
이력은 `db.toggleHistoryCheck()`, 조정요청은 `db.toggleRestoreCheck()` 로 한 건씩 처리한다.

| 상태 | 권한 있음 (`updateStatus`) | 권한 없음 |
|---|---|---|
| 미확인 | 회색 버튼 | 회색 `미확인` 태그 |
| 확인 완료 | **초록 `확인완료` 버튼** (눌러서 해제) | 초록 `확인완료` 태그 |

- 변동 이력은 **실제 수정(`rev > 0`)에만** 붙는다.
  등록·처리현황·접수확인 같은 이벤트는 확인 대상이 아니다. 조정요청은 모든 건에 붙는다
- **건별 확인은 되돌릴 수 있다.** 잘못 눌렀으면 다시 눌러 해제한다.
  표의 체크박스로는 해제할 수 없으므로, 해제는 여기서만 가능하다
- **확인처리한 사용자 이름이 이력 항목에 초록 배지로 남는다**
  (`확인처리 박용마 · 2026-08-29 07:23`). 툴팁이 아니라 본문에 표시된다
- 구역 머리글에 `미확인 3건`(빨강) 또는 `모두 확인`(초록) 요약이 붙는다 (`checkSummary()`)
- **두 구역의 확인 상태는 서로 독립적이다**
- 확인 상태가 바뀌면 `draw()` 로 모달 내용을 다시 그린다 (모달은 닫히지 않는다)

### 삭제

`db.deleteOrder()` 는 주문과 파렛트를 함께 지우고 이력에 삭제 기록을 남긴다.
확인 대화상자를 거친다. Supabase 정책에서는 관리자이거나
**본인이 등록한 `stage=0` 인 건**만 삭제할 수 있다.

## CSV 다운로드

파일명 `주문등록내역_YYYY-MM-DD.csv`, **현재 조회된 행 전체**가 대상이다.

```
연번, 등록일자, 전송일자, 담당자, 차수, 주문번호, 거래처명, 추가작업, 요청사항,
출고요청일, 진행상태, 접수확인, 수정횟수, 조정요청, 차량구분, 품목수, 출고수량, 비고
```

추가작업은 ` / ` 로 이어 붙이고, 수정횟수와 조정요청은 건수를 넣는다.
표에 없는 차량구분·품목수·출고수량·비고까지 포함한다.
`downloadCsv()` 가 BOM 을 붙여 엑셀 한글 깨짐을 막는다.

## 수정 시 주의

- **연번은 역순이다.** `rows.length - i` 를 그냥 `i + 1` 로 바꾸면 최신 건이 1번이 된다
- 차수 계산 로직은 `db.js` 에 있다. 화면에서 다시 계산하지 않는다
- 등록 폼에 항목을 추가할 때 `db.createOrder()` 의 기본값도 함께 확인한다
- 요약은 **당일 등록분**이다. 필터 기간 합계로 바꾸면 업무 의미가 달라진다
- 추가작업은 배열이다. 체크박스를 다룰 때 `form.getAll('extra_works')` 를 빠뜨리지 않는다
- 조정요청 폼에서 숨긴 입력란은 반드시 `disabled` 로 함께 막는다.
  `hidden` 만 걸면 숨겨진 필수 항목 때문에 제출이 막힌다
- 수정/조정 가능 여부는 `canEdit()` / `canRestore()` 로만 판정한다.
  조건을 화면 여러 곳에 흩어 쓰지 않는다
- 수정 횟수는 변경분을 모은 뒤 **한 번만** 올린다. 항목마다 올리면 횟수가 부풀려진다
- 수정·조정요청 진입점은 상세 팝업 하나뿐이다. 표에 버튼을 되살리지 않는다
- 진행상태는 저장하지 않는다. `progressOf()` 로만 계산한다. 컬럼을 만들면 상태가 어긋난다
- 취소된 주문은 수정·조정요청·접수 체크가 모두 막힌다. 새 기능을 붙일 때도 확인한다
- 권한은 `canWrite()` / `canConfirm()` 로만 판정한다. 이 화면에서
  `can(user, 'createOrder')` 를 다시 쓰지 않는다 (소속을 보지 않아 판정이 어긋난다)
- **수정·조정 체크 상태를 주문에 따로 저장하지 않는다.** 이력의 개별 확인 상태에서
  매번 계산한다(`db.checkStats()`). 별도 필드를 만들면 새 변경이 생겨도 풀리지 않는다
- 수정확인·조정확인은 되돌릴 수 있다. 접수확인과 동작이 다르니 혼동하지 않는다
- 확인 UI 는 `checkControl()` 하나로 공유한다. 구역마다 따로 만들지 않는다
- **확인은 건별 토글만 제공한다.** 일괄 확인은 확인자·확인 시각을 덮어쓸 위험이 있어 없앴다
- 상세 모달의 항목 이름과 `db.js` 의 이력 라벨은 짝을 이룬다. 한쪽만 바꾸면
  `수정됨` 배지와 이전 내용 보기가 동작하지 않는다
