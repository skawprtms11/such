# 업무체크리스트

> 코드 `assets/js/pages/checklist.js`(웹) · `assets/js/mobile/screens/checklist.js`(앱 일일) ·
> `assets/js/mobile/screens/process.js`(앱 업무프로세스 · 보기 전용)
> 라우트 웹 `#/checklist` · 앱 `#/checklist` `#/process` · [공통 규약](common.md) · [CLAUDE.md](../CLAUDE.md)

담당자별 **업무 누락을 막고 담당을 분명히 하는** 화면.
사용자가 만든 **업무구분**(입고·출고·반품 …) 아래 **업무항목**(B2B출고·B2C출고 …)마다
**업무 흐름을 프로세스 순서대로** 등록하고, 프로세스마다 **체크항목**을 단다. 담당자는 날짜별로 체크항목을 중심으로 체크한다.
작업 중 **상황**(입고수량오류·제품틀림 등)이 생기면 그 자리에서 「발생」 처리해
대응 프로세스가 흐름 사이에 끼어든다.

공지사항이 *전체 대상 안내*, 이슈등록이 *개별 건의 문제 제기*라면,
업무체크리스트는 **반복 업무의 이행 확인**이다.

---

## 구조 🔑 — 트리 한 그루가 업무 흐름이다

항목(`checklist_items`)은 트리이고, 노드마다 **종류(`kind`)** 가 있다.

| 종류 | 저장값 | 역할 | 둘 수 있는 하위 |
|---|---|---|---|
| 업무구분 | `division` | **최상위 묶음.** 사용자가 「업무구분 추가」로 만든다 (입고·출고·반품 …). 이름은 겹칠 수 없다 | 업무항목 |
| 업무항목 | `group` | 업무구분 아래 흐름 한 벌 (B2B출고·B2C출고 …). 같은 업무구분 안에서 이름이 겹칠 수 없다. **복제**할 수 있고 다른 업무구분으로 **옮길** 수 있다 | 프로세스 · 체크항목(단독 업무) |
| 프로세스 | `process` | 업무 흐름의 한 단계. **형제 순서(`sort_order`)가 곧 업무 순서** | 체크항목 · 상황 · 하위 프로세스 |
| 상황 | `situation` | 그 단계에서 생길 수 있는 예외 상황. **발생 처리한 날짜에만** 하위가 끼어든다 | 대응 프로세스 · 체크항목 |
| 체크항목 | `check` | 담당자가 실제로 체크하는 항목. 주기·담당자를 가진다 | 없음 (말단) |

최상위에는 업무구분만 있다. 허용 관계는 `config.js` 의 `CHECK_KIND_CHILDREN` 이 유일한
출처이고, `db.createChecklistItem()` 이 거부한다. **종류는 수정으로 바꿀 수 없다** (지우고 다시 만든다).
`category` 컬럼은 최상위(업무구분) 이름을 담는 옛 컬럼이다 — 화면 로직은 쓰지 않고, 이름을
바꾸면 하위까지 함께 맞춘다.

```
입고 (업무구분)
 ├ 일반 입고 (업무항목)   ① 하차 파렛트수 확인 → ② 입고거래명세서 확인 → … 
 └ 반품 입고 (업무항목)   ① … 
출고 (업무구분)
 ├ B2B출고 (업무항목)
 └ B2C출고 (업무항목)    ← B2B출고를 「복제」한 뒤 다른 점만 고친다
```

입고 예시:

```
입고
 ① 하차 파렛트수 확인        ☐ 차량 도착 시각 기록  ☐ 하차 파렛트수 = 송장 대조
 ② 입고거래명세서 확인       ☐ 거래명세서 수령·품목 대조
     ⚠ 입고수량오류  ──발생──▶  ↳ 수량 차이 기록 → 화주 담당자 보고 → 명세서 정정본 수령
     ⚠ 제품 틀림     ──발생──▶  ↳ 오입고 제품 격리 → 반송 여부 확인
 ③ 입고검수                  ☐ LOT 확인  ☐ 유효기간 작성  ☐ 외관·파손 확인
 ④ 입고라벨 부착             ☐ 파렛트별 라벨 출력·부착
 ⑤ 입고적치                  ☐ 로케이션 지정·적치
 ⑥ WMS 입고처리              ☐ WMS 입고 확정
 ⑦ 실물 입고적치 검증        ☐ WMS 재고 = 실물 로케이션 대조
```

이 예시는 `config.js` 의 `CHECK_TEMPLATES` 에 견본으로 들어 있고, 업무프로세스 탭에서 업무구분을
고른 뒤 **「견본: 입고」** 버튼을 누르면 그 업무구분 아래에 같은 이름의 업무항목을 만들며 한 번에
등록한다(`db.seedChecklistTemplate`). 그 업무구분에 같은 이름의 업무항목이 이미 있으면 버튼이 사라진다.

### 체크 대상

**일일체크리스트에는 업무프로세스 탭에서 「일일」(`daily`)을 켠 항목만 나온다.** 🔑
켜지 않은 체크항목은 업무프로세스 보드에는 있지만 일일체크리스트에서는 빠진다 (참고용 절차).

| 노드 | 체크 대상인가 |
|---|---|
| 체크항목 (`daily` 켬) | ✅ (그 날짜에 주기가 맞을 때) |
| 체크항목·하위 프로세스가 없는 프로세스 (`daily` 켬) | ✅ 단계 자체를 체크한다 (`단계 완료`) — 상황만 달려 있어도 같다 |
| `daily` 를 끈 체크항목·프로세스 | ❌ 일일체크리스트에 나오지 않는다 |
| 체크항목이나 하위 프로세스가 있는 프로세스 | ❌ 하위 집계만 (`done / total`) |
| 상황 | ❌ 체크가 아니라 **발생 처리**다 (아래) |

### 상황 발생 🔑

- **별도 테이블이 없다.** 상황 노드에 그 날짜의 `checklist_checks` 기록이 있으면
  "그 날짜에 발생했다"는 뜻이고 `memo` 가 발생 내용이다
- 발생 처리하면 상황의 하위(대응 프로세스·체크항목)가 **그 날짜의 대상에 들어가고**
  집계(`total`)에 더해진다. 발생 안 된 상황은 프로세스 밑에 **「상황 발생 시」 후보 칩**으로만 보인다
- **발생 해제**하면 그 상황 아래 같은 날짜의 체크 기록도 함께 지운다
  (끼어들었던 단계가 통째로 빠진다). 화면은 확인 문구로 알린다
- 상위 상황이 발생 처리되지 않은 항목은 체크할 수 없다 (`db.setCheck` 가 거부)
- 상황은 **날짜당 1번**만 발생 처리된다 (unique). 같은 날 여러 건이면 발생 내용(memo)에 적는다

### 담당자 상속 🔑

체크항목의 담당자를 비우면 **가장 가까운 상위(프로세스 → 업무항목 → 업무구분)의 담당자**를 따른다.
끝까지 없으면 공통 업무(누구나 체크)다. 프로세스·업무항목·업무구분에 담당자를 한 번만 적으면
그 아래가 모두 그 사람 일이 된다.

```
db.js   effectiveAssignee(item)              →  rows 의 assignee_eff_id / assignee_eff_name
서버    checklist_effective_assignee(item)   →  checklist_checks RLS 가 이 값으로 판정
```

## 접근 권한

| 역할 | 조회 | 일일체크리스트 체크·상황 발생 | 업무프로세스 편집(등록·수정·삭제) | 남의 항목 대신 체크 |
|---|:---:|:---:|:---:|:---:|
| 관리자 | ✅ | ✅ | ✅ | ✅ |
| 용마담당자 | ✅ | ✅ | ✅ | ✅ |
| 화주관리자 | ✅ | ✅ | ✅ | ✅ |
| 화주영업팀 | ✅ | 본인 담당만 | ❌ | ❌ |
| 현장작업자 | ✅ | 본인 담당만 | ❌ | ❌ |

- 관리 권한은 `config.js` 의 `PERMISSION` 에 있는 **`manageChecklist`** 다.
  화면은 `can(user, 'manageChecklist')`(웹) 으로만 판정하고 역할명을 직접 비교하지 않는다
- 체크·상황 발생 판정은 **`db.canCheckItem(user, item)` 한 곳**에 있다 — 웹·앱이 같은 함수를 쓴다.
  `item` 은 `dailyFlow()` 가 상속 담당자(`assignee_eff_id`)를 붙여 준 것이어야 한다

```
상속 담당자 본인  또는  담당자 없음(공통 업무)  또는  manageChecklist 권한자(대신 체크)
```

- 서버 RLS 도 같은 기준이다 (`supabase/schema.sql` 의 `can_manage_checklist()` ·
  `checklist_effective_assignee()`). **화면 제어만 믿지 않는다**

## 화면 구성 (웹) — 목적이 다른 탭 2개 🔑

| 탭 | 목적 | 읽는 법 | 모양 |
|---|---|---|---|
| **일일체크리스트** (기본) | 오늘 내가 **빠뜨리면 안 되는 것**을 챙긴다 | 위에서 아래로 훑고 체크 | 계층 머리글(업무구분 › 업무항목) + 체크 줄 목록. 미완료 먼저, 완료는 접힘 |
| **업무프로세스** (`manageChecklist`) | 업무 흐름과 **갈래**를 한눈에 보는 매뉴얼 | 플로우차트를 따라간다 | 프로세스 박스 → 판단 마름모 → 분기 레인 → 합류 → 다음 박스. 편집은 편집 모드에서만 |

두 탭은 같은 데이터(업무구분 → 업무항목 → 프로세스 → 체크항목/상황)를 **다르게 그릴 뿐**이다.
흐름 구조는 업무프로세스가 맡고, 일일체크리스트는 그 구조를 줄 아래 작은 캡션으로만 남긴다.

### 탭 1 「일일체크리스트」 (기본)

```
[◀ 2026-09-10 ▶ 오늘]  담당자 [나 ▾]  [미완료|전체]         남은 5 · 7 / 12 ▓▓▓░░  [상황 발생 1건] [어제 미체크 2건 →]
입고 ──────────────────────────────────────────────────────────────── 1 / 8
 일반 입고   │ ☐ 하차 파렛트수 = 송장 파렛트수 대조  [어제 미체크]       김현장            메모 │
 1 / 8      │     ① 하차 파렛트수 확인 · 일                                                    │
            │ ☐ 거래명세서 수령·품목 대조                                김현장            메모 │
            │     ② 입고거래명세서 확인 · 일                                                  │
            │   ⚠ 상황  [입고수량오류 발생 09:30 김현장 · 3박스 부족  ✎ ✕]  [제품 틀림 ·발생·]      │
            │ ☐ 품목별 차이 수량 사진 촬영                               김현장            메모 │
            │     ② 입고거래명세서 확인 › ⚠ 입고수량오류 › ① 수량 차이 기록 · 일   (옅은 주황 줄)  │
            │ ☐ LOT 확인      ③ 입고검수 · 일                            공통                 │
            │ ▸ 완료 3건 보기                                                                  │
출고 ──────────────────────────────────────────────────────────────── 0 / 2
 B2B출고    │ ☐ 단계 완료 피킹 리스트 출력   ① 출고 피킹 › ① 피킹 리스트 출력   이담당           │
```

| 요소 | 동작 |
|---|---|
| 날짜 이동 | `◀` `▶` 로 하루씩, 날짜칸 직접 선택, `오늘` 버튼 |
| 담당자 | 기본 `나`(본인 담당 + 공통 업무). **`manageChecklist` 권한자만** `전체`·특정 담당자를 고를 수 있다. 상속 담당자로 거른다 |
| `미완료 \| 전체` | 기본 `미완료` — 완료 줄은 업무항목마다 「▸ 완료 N건 보기」 로 접힌다. `전체` 면 완료 줄도 자리에 펼친다 |
| 진행 | `남은 N · done / total` 과 막대. 100% 면 초록 |
| `상황 발생 N건` | 그 날짜에 발생 처리된 상황 수 (주황 배지) |
| `어제 미체크 N건 →` | 전날 미체크가 있을 때만 나오고, 누르면 **전날로 이동**한다 |
| **줄 안 「어제 미체크」 꼬리표** | 전날에도 대상이었는데 체크하지 않은 항목(수시 제외)에 붉은 꼬리표가 붙는다 (`row.late`) |
| 체크박스 | 켜면 기록 생성, 끄면 기록 삭제. 제목을 눌러도 된다. 체크한 **시각·사람**이 오른쪽에 남는다 |
| 프로세스 캡션 | 줄 아래 작은 글씨 `① 프로세스 › ⚠ 상황 › ① 대응 프로세스 · 주기`. 상황 아래 줄은 옅은 주황 바탕 |
| 메모 | 체크한 항목에만 남길 수 있다. 메모가 있으면 아이콘이 파랗게 표시된다 |
| 상황 칩 (발생 전) | 프로세스의 마지막 줄 뒤 「⚠ 상황」 줄. 점선 칩 + 「발생」. 누르면 발생 내용을 묻고 발생 처리한다. 권한 없으면 비활성 |
| 상황 칩 (발생) | 주황 실선. 발생 시각·사람·내용. `메모` 로 내용 수정, `✕` 로 발생 해제(확인 문구). 발생하면 대응 항목이 아래 줄로 끼어든다 |

- 줄 순서 = 업무 순서(업무구분 → 업무항목 → 프로세스 구간). 그 안에서 미완료가 먼저다
- 업무항목에 바로 둔 체크항목은 캡션 「단독 업무」 로 그 업무항목 마지막에 나온다
- 체크 권한이 없는 항목은 회색 + 체크박스 비활성 상태로 **조회만** 된다
- 화면은 `db.dailyTable(date, f)` 의 `divisions` 를 그대로 그린다. 날짜·주기·상속·지연 계산을 하지 않는다

### 탭 2 「업무프로세스」 (`manageChecklist`) — 플로우차트 매뉴얼

```
업무구분 [입고] [출고] [반품]                   [개요|상세] [편집] [인쇄]  (편집 모드: [+ 업무구분 추가])
┌ ■ 입고  설명 · 담당                                    (편집 모드: ↑ ↓ ✎ 🗑 · [견본: 입고] [+ 업무항목 추가]) ┐
업무항목 [≡ 일반 입고] [≡ 반품 입고]
┌ ≡ 입고 › 일반 입고                                       (편집 모드: ↑ ↓ ✎ 🗑 [복제] · [+ 프로세스 추가] [+ 단독 체크항목]) ┐

      ┌ ① 하차 파렛트수 확인   담당 김현장 ┐
      │   체크 2                          │      ← 개요: 요약 한 줄 / 상세: 체크항목 목록
      └──────────────────────────────────┘
                      ▼
      ┌ ② 입고거래명세서 확인 ┐
      └──────────────────────┘
                      ▼
                  ◇ 입고수량오류      ── 예 ──▶  ┌ ⚠ 입고수량오류 발생 시  명세서 수량과 실물이 다를 때 ┐
                     발생?                       │   ▼ ① 수량 차이 기록  ☐ 품목별 차이 수량 사진 촬영   │
                  │ 아니오                       │   ▼ ② 화주 담당자 보고  ☐ 이슈등록                 │
                  ▼                              │   ▼ ③ 명세서 정정본 수령                          │
                  ◇ 제품 틀림 발생?  ── 예 ──▶   │   ↩ 다음 단계로 합류                              │
                  │ 아니오                       └─────────────────────────────────────────────┘
                  ▼
      ┌ ③ 입고검수  체크 3 ┐
      …
```

- **읽는 규칙**: 가운데 줄기가 정상 흐름. 상황이 달린 프로세스 뒤에는 상황마다 **판단 마름모**(`상황명 발생?`)가
  놓인다. `예` 는 오른쪽 **분기 레인**(주황 점선 상자)으로 빠져 대응 단계 ①→②→③ 을 거친 뒤 **합류선**으로
  다음 정상 단계에 돌아오고, `아니오` 는 그대로 아래로 내려간다. 상황 뒤의 「아니오」 화살표가 곧 다음 단계로
  가는 화살표라 따로 겹쳐 그리지 않고, 시작·완료 타원은 두지 않는다. 하위 프로세스는 박스 안 작은 사슬이고,
  그 안의 상황은 옆에 둘 자리가 없어 아래에 레인만 붙는다
- **개요 / 상세**: 개요(기본)는 박스에 이름·설명·담당자·`체크 N · 하위 N · 상황 N` 요약만. 상세는 체크항목 목록을
  펼친다. 좁은 화면(960px 이하)에서는 레인이 마름모 아래로 내려온다
- **편집 모드**: 「편집」 을 켜야 순서·수정·삭제·추가·「일일」 토글·복제·견본 버튼(`fc-tools`)이 보인다.
  켜면 상세로 바뀌고, 개요로 돌아가면 편집이 끝난다. 폼은 그 박스 머리 아래 인라인으로 열린다
- **인쇄**: 업무항목 하나를 매뉴얼로 인쇄한다(`window.print`). 사이드바·탭·도구를 숨기고 상세로 펼친다
  (`body.cl-printing` + `@media print`)
- **업무구분 탭 줄**(검정 칩): 최상위. 업무구분 머리에 설명·담당자. 편집 모드에서 `↑↓`·`✎`·`🗑`(아래 업무항목
  전체 삭제)와 「업무항목 추가」, 견본(`CHECK_TEMPLATES`) 버튼(그 업무구분에 같은 이름이 없을 때만)
- **업무항목 칩 줄**: 고른 업무구분의 업무항목들. 업무항목 머리에 `업무구분 › 업무항목` 경로. 편집 모드에서
  `↑↓` · `✎`(수정 폼에서 **업무구분을 바꿔 옮길 수 있다**) · `🗑` · **「복제」** · 「프로세스 추가」 「단독 체크항목」
- **복제**(`db.duplicateChecklistGroup`): 프로세스·상황·체크항목·포함 여부까지 통째로 복사해 같은 업무구분
  맨 뒤에 「이름 복사」로 만든다. 체크 기록은 복사하지 않는다. B2B출고 → B2C출고처럼 비슷한 흐름을 짤 때 쓴다
- **미분류**: 스키마 마이그레이션 전에 만들어져 업무구분이 없는 업무항목이 있으면 「미분류」 탭이 마지막에
  붙는다. 수정 폼에서 업무구분을 고르면 옮겨진다
- 체크항목 줄 앞의 **「일일」 토글**이 일일체크리스트 포함 여부다 (`daily`). 체크항목이 없는 잎 프로세스는
  박스 머리에 토글이 있다. 폼의 「일일체크리스트 포함」과 같은 값이며, 새 체크항목은 켜진 채로 시작한다

| 종류 | 폼 필드 |
|---|---|
| 업무구분 | 이름(전체에서 겹치면 거부) · 설명 · 담당자(기본) · 활성 |
| 업무항목 | 이름(같은 업무구분 안에서 겹치면 거부) · **업무구분**(바꾸면 옮겨진다) · 설명 · 담당자(기본) · 활성 |
| 프로세스 | 프로세스명 · 설명 · 담당자(기본 — 하위가 따른다) · 일일체크리스트 포함(잎 프로세스일 때만 뜻이 있다) · 활성 |
| 상황 | 상황명 · 어떤 때인지(대응 요령) · 담당자 · 활성 |
| 체크항목 | 항목명 · 설명 · 주기(+요일/일자) · 담당자(비우면 상위 담당 따름) · **일일체크리스트 포함** · 활성 |

- 삭제는 **하위 항목까지 함께** 지운다(확인 문구로 개수를 알린다). 체크 기록을 남기려고
  행을 지우지 않고 `deleted_at` 만 찍는다(soft delete)
- 비활성 항목은 업무프로세스 탭에서만 흐리게 보이고 일일체크리스트에는 나오지 않는다

## 화면 구성 (앱)

### `#/checklist` 일일체크리스트 — 상단바 메뉴

웹의 목록을 **한 열**로 편 것이다. 업무구분은 굵은 머리, 업무항목은 소제목, 그 아래 체크 줄.
미완료가 먼저이고 완료 줄은 「▸ 완료 N건 보기」 로 접힌다(업무항목마다).

```
입고  1 / 8                                 ← 업무구분 머리
일반 입고  1 / 8                            ← 업무항목 소제목
☐ 하차 파렛트수 = 송장 대조  [어제 미체크]
  ① 하차 파렛트수 확인 · 일 · 김현장
☐ 거래명세서 수령·품목 대조
  ② 입고거래명세서 확인 · 일 · 김현장
  [⚠ 입고수량오류 발생 · 3박스 부족 ···] [⚠ 제품 틀림 ·발생·]
☐ 품목별 차이 수량 사진 촬영
  ② 입고거래명세서 확인 › ⚠ 입고수량오류 › ① 수량 차이 기록 · 일
▸ 완료 3건 보기
```

- 날짜 이동(`◀ 날짜 ▶ 오늘`) · 큰 진행 카운터(아래 한 줄에 `남은 항목 N개 · 상황 발생 N건`) ·
  `어제 미체크 N건 보기` 버튼(전날로 이동)
- 체크 줄 전체가 터치 영역(48px 이상)이라 장갑을 낀 채 눌러도 빗나가지 않는다
- 담당자 필터가 없다 — **로그인 사용자 본인 담당(상속 포함) + 공통 항목만** 본다
- 상황 칩: 발생 전은 점선 「발생」 → **시트**에 어떤 때인지·대응 절차가 보이고 발생 내용을 적어 「발생 처리」.
  발생한 칩(주황 실선)을 누르면 시트에서 내용 수정 · 「발생 해제」(빨간 버튼)
- 메모는 체크한 항목의 메모 아이콘을 눌러 시트에서 입력한다

### `#/process` 업무프로세스 — 상단바 메뉴 · 보기 전용

현장에서 매뉴얼을 펼쳐 보는 화면이다. 업무구분·업무항목 세그먼트로 고르면 그 흐름을 **세로 스테퍼**로
그린다 — 시작 → 프로세스 박스(체크항목 목록 포함) → `◇ 상황명 발생?` → `예 ↓` 들여쓴 주황 점선 레인
(대응 단계 ①→②→③, `↩ 다음 단계로 합류`) → `아니오 ↓` → … → 완료. 하위 프로세스는 박스 안 작은 사슬.
편집은 웹에서만 한다. 비활성 업무구분·업무항목·항목은 나오지 않는다.

## 데이터 (`db.js`)

주기 판정·담당자 상속·상황 발생·권한 판정은 **`db.js` 한 곳**에만 있다. 화면은 결과만 그린다.

| 함수 | 설명 |
|---|---|
| `listChecklistItems(f)` | 항목 목록. `root`(업무항목 id → 그 아래 전체) `kind` `includeInactive` `assignee` 로 거른다 |
| `listChecklistDivisions()` | 업무구분(최상위 `division`) 목록. 비활성 포함 |
| `listChecklistGroups(divisionId?)` | 업무항목 목록. 업무구분 id 로 거른다. `null` 이면 업무구분 없는 옛 업무항목(미분류) |
| `duplicateChecklistGroup(id, user)` | 업무항목을 하위 전체와 함께 복제. `{group, count}` 반환 |
| `checklistTree(rows)` | 평평한 목록을 `{item, depth, children}` 트리로 묶는다 (순수 함수) |
| `allowedChildKinds(parentKind)` | 그 종류 아래 둘 수 있는 종류 (`CHECK_KIND_CHILDREN`) |
| `createChecklistItem(payload, user)` | 등록. 최상위는 업무항목만. 순서는 형제 맨 뒤. 종류 관계·업무항목 이름 중복을 검증한다 |
| `seedChecklistTemplate(name, divisionId, user)` | `CHECK_TEMPLATES[name]` 으로 그 업무구분 아래 업무항목 한 벌을 만든다. `{group, count}` 반환 |
| `updateChecklistItem(id, patch, user)` | 수정 (종류는 못 바꾼다). 업무항목은 `parent_id` 로 다른 업무구분으로 옮긴다. 최상위 이름을 바꾸면 하위 `category` 도 맞춘다 |
| `moveChecklistItem(id, dir, user)` | 형제 사이 순서 이동 (`'up'` / `'down'`) |
| `deleteChecklistItem(id, user)` | 하위까지 soft delete. 지운 개수를 돌려준다 |
| `dailyFlow(date, {assignee})` | 🔑 **날짜별 판정 뷰모델.** 업무항목 → 프로세스(순번·집계·체크항목·하위·상황) → 상황(발생 여부·하위). 주기·상속·발생 판정이 여기서 끝난다 |
| `dailyTable(date, {assignee})` | 🔑 **일일체크리스트 뷰모델.** `dailyFlow` 를 프로세스 단위 구간(section)으로 편다 — `{path:[{title,no,sit}], sit, rows, situations}`. `divisions`(업무구분 → 업무항목) 로 묶어 주고, 줄마다 `late`(전날 미체크)를 붙인다. 웹·앱 목록이 이것을 그린다 |
| `dueItems(date, {assignee})` | `dailyFlow` 를 평평하게 편 체크 대상 목록 (발생 안 된 상황 아래는 뺀다) + `path` `check` `assignee_eff_*` |
| `listChecks(date)` | 그 날짜의 체크 기록 |
| `setCheck(itemId, date, on, memo, user)` | 체크/해제. 상황 노드면 **발생/해제**. 해제는 하위 기록도 같은 날짜 것을 지운다 |
| `checklistSummary(date, {assignee})` | `{total, done, raised, missed, prevDate}` — `raised` 는 발생 상황 수, `missed` 는 **전날** 미체크 수 |
| `canManageChecklist(user)` `canCheckItem(user, item)` | 권한 판정 (웹·앱 공용) |

### `dailyTable` 뷰모델

```
{ date, done, total, raised,
  divisions: [ { item, name, done, total, groups: [Group] } ],   // 업무구분 순서
  groups:    [Group] }                                            // 평평하게 (집계·호환)
Group   = { item, name, division, done, total, sections: [Section] }
Section = { key, path: [{title, no, sit}], sit: item|null, rows: Row[](+late), situations: SituationVM[] }
  path        프로세스 경로 (하위·대응 프로세스는 상위부터, 상황 아래면 상황명도 든다)
  sit         이 구간이 발생한 상황 아래면 그 상황 (화면이 주황으로 표시)
  rows        그 구간에서 체크할 항목 (단계 자체 체크 포함)
  situations  그 프로세스에 직접 달린 상황 (발생 전 후보 + 발생한 것)
```

구간 순서 = 업무 순서. 발생 안 된 상황의 하위 구간은 나오지 않는다.

### `dailyFlow` 뷰모델

```
{ date, done, total, raised, groups: [
    { item, name, done, total, loose: Row[],      // loose = 업무항목에 바로 둔 단독 체크항목
      processes: [ProcessVM] } ] }
ProcessVM   = { item, no, done, total, rows: Row[], subs: ProcessVM[],
                situations: SituationVM[], self: Row|null }   // self = 하위 없는 단계 자체
SituationVM = { item(+assignee_eff_*), active: check|null, rows: Row[], subs: ProcessVM[], done, total }
Row         = 항목 + { path, check, assignee_eff_id, assignee_eff_name, process_id }
```

- 담당자 필터는 **상속 담당자**로 거른다. 담당자가 없는 **공통 업무는 누구의 목록에나 든다.**
  내 일이 하나도 없는 프로세스·상황은 나오지 않는다
- 발생 안 된 상황은 `active: null` 이고 `done/total` 이 0 이다 (후보 칩용)
- 웹 업무프로세스 탭은 이 뷰모델이 아니라 트리(`checklistTree`)를 같은 모양으로 바꿔 보드를 그린다

### 주기 판정 🔑

`dailyFlow()` 안의 `isDueOn()` 이 유일한 출처다. 화면에서 날짜를 다시 계산하지 않는다.
**주기는 체크항목에만 있다.** 프로세스·상황은 `daily` 로 저장되고 화면에 보이지 않는다.

| 주기 | 저장값 | 나오는 날 |
|---|---|---|
| 일 | `daily` | 매일 |
| 주 | `weekly` + `weekday`(0=일 ~ 6=토) | 지정 요일 |
| 월 | `monthly` + `monthday`(1~31) | 지정 일자. **말일 보정** — `31` 이면 그 달 말일(2월은 28·29일) |
| 수시 | `adhoc` | 날짜와 무관하게 항상 |

- **수시는 `어제 미체크` 집계에서 뺀다.** 날짜 개념이 없어 "밀렸다"고 볼 수 없다
- 비활성(`active = false`) 항목과 삭제된 항목은 일일체크리스트에 나오지 않는다.
  업무프로세스 탭은 `includeInactive: true` 로 비활성까지 본다

### 테이블

| 테이블 | 주요 필드 |
|---|---|
| `checklist_items` | `category`(업무구분 이름 · 옛 컬럼) `parent_id` **`kind`**(division/group/process/situation/check) `title` `description` `cycle` `weekday` `monthday` `assignee_id` `assignee_name` `sort_order` `active` **`daily`**(일일체크리스트 포함) `deleted_at` |
| `checklist_checks` | `item_id` `check_date` `memo` `checked_by` `checked_by_name` `checked_at` · **`unique(item_id, check_date)`** |

- 체크는 **항목·날짜당 1건**이다. 두 사람이 같이 눌러도 한 건만 남는다
- 상황 노드의 체크 기록 = 발생 기록. `memo` = 발생 내용
- `kind` 가 없는 옛 항목은 `db.js` 의 `normalize()` 와 스키마의 backfill 이
  **하위가 있으면 프로세스, 없으면 체크항목**으로 본다. 고정 구분 시절의 최상위 항목은
  스키마 마이그레이션이 `category` 별 업무항목(`ci_grp_<md5>`)을 만들어 그 아래로 옮기고,
  업무구분 도입 때는 최상위 업무항목마다 같은 이름의 업무구분(`ci_div_<md5>`)을 만들어 그 아래로 옮겼다
  (입고 › 입고 — 이름은 화면에서 고친다)
- 두 테이블 모두 Realtime 에 올라가 있어 다른 사람의 체크가 즉시 반영된다

---

## 상수 (`config.js`)

| 상수 | 값 |
|---|---|
| `CHECK_KIND` / `CHECK_KINDS` | `division` `group` `process` `situation` `check` (저장값) / 표시 문구 `업무구분` `업무항목` `프로세스` `상황` `체크항목` |
| `CHECK_KIND_CHILDREN` | 종류별 허용 하위 종류. `root` 키는 최상위(업무구분만) |
| `CHECK_TEMPLATES` | 업무항목 이름별 견본 (현재 `입고`). 「견본: 이름」 버튼이 쓴다 |
| `CHECK_CYCLE` | `daily` `weekly` `monthly` `adhoc` (저장값) |
| `CHECK_CYCLES` | 표시 문구 `일` `주` `월` `수시` |
| `WEEKDAYS` | `['일','월','화','수','목','금','토']` — 배열 순서가 `Date.getDay()` 와 같다 |
| `cycleLabel(item)` | `주(화)` `월(25일)` 처럼 한 줄로 만든다 (웹·앱 공용) |

## 보완 여지 (설계상 열어 둔 곳)

- **다른 견본** — `CHECK_TEMPLATES` 에 `출고` `반품` 을 더하면 「견본: 이름」 버튼이 저절로 생긴다
- **상황 아래 상황** — 허용하지 않는다(`CHECK_KIND_CHILDREN`). 필요하면 상수만 열면 되지만
  `dailyFlow` 의 `buildSituation` 이 상황 하위 상황을 무시하므로 함께 고쳐야 한다
- **상황 여러 번 발생** — 날짜당 1건이다. 건별 기록이 필요해지면 발생 기록을 별도 테이블로 뺀다
- **프로세스 간 조건 분기** (예: 냉장 입고면 ⑤ 대신 ⑤′) — 지금은 상황으로 표현한다

## 알려진 제약

- **미체크 알림은 화면 안의 배지뿐이다.** 푸시·메일 알림은 서버가 필요해 넣지 않았다
- **주기가 겹치는 항목을 한 줄로 합치지 않는다.** 같은 일을 매일·매주 두 번 넣으면
  두 줄로 나온다 (등록할 때 정리한다)
