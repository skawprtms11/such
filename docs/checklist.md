# 업무체크리스트

> 코드 `assets/js/pages/checklist.js`(웹 셸) · `assets/js/pages/checklist/*.js`(탭별 모듈) ·
> `assets/js/checkflow.js`(도식 좌표 · 순수 함수) ·
> `assets/js/mobile/screens/checklist.js`(앱 일일) ·
> `assets/js/mobile/screens/process.js`(앱 업무프로세스 · 보기 전용)
> 라우트 웹 `#/checklist` · 앱 `#/checklist` `#/process` · [공통 규약](common.md) · [CLAUDE.md](../CLAUDE.md)

담당자별 **업무 누락을 막고 담당을 분명히 하는** 화면.
사용자가 만든 **업무구분**(입고·출고·반품 …) 아래 **업무항목**(B2B출고·B2C출고 …)마다
**업무 흐름을 프로세스 순서대로** 등록해 매뉴얼로 삼는다(업무프로세스 탭).
작업 중 생길 수 있는 **상황**(입고수량오류·제품틀림 등)도 그 흐름 안에 적어 둔다.

🔑 **담당자가 날짜별로 체크하는 것은 흐름이 아니라 「체크리스트 등록」 탭에서 만든 독립
체크항목이다.** 등록 기준(일별·주차별·월별)에 따라 일일체크리스트에 나온다 — 흐름(트리)과
체크(기간)는 쓰임이 달라 갈라 두었다.

공지사항이 *전체 대상 안내*, 이슈등록이 *개별 건의 문제 제기*라면,
업무체크리스트는 **반복 업무의 이행 확인**이다.

---

## 구조 🔑 — 소유는 트리, **흐름은 간선**

항목(`checklist_items`)은 트리이고, 노드마다 **종류(`kind`)** 가 있다.
트리는 소유(소속·담당자 상속·삭제 전파)만 정하고, **단계 순서는 간선 테이블**이 정한다
(`checklist_edges` · 아래 「순차 · 갈래 · 합류」).

| 종류 | 저장값 | 역할 | 둘 수 있는 하위 |
|---|---|---|---|
| 업무구분 | `division` | **최상위 묶음.** 사용자가 「업무구분 추가」로 만든다 (입고·출고·반품 …). 이름은 겹칠 수 없다 | 업무항목 |
| 업무항목 | `group` | 업무구분 아래 흐름 한 벌 (B2B출고·B2C출고 …). 같은 업무구분 안에서 이름이 겹칠 수 없다. **복제**(간선까지)할 수 있고 다른 업무구분으로 **옮길** 수 있다. **흐름 한 벌의 경계**다 — 간선은 같은 업무항목 안에서만 잇는다 | 프로세스 · 체크항목 |
| 프로세스 | `process` | 업무 흐름의 한 단계. 순서는 **간선**이 정한다 (`sort_order` 는 흐름과 무관하다) | 체크항목 · 상황 |
| 상황 | `situation` | 그 단계에서 생길 수 있는 예외 상황. **발생 처리한 날짜에만** 하위가 끼어든다 | 대응 프로세스 · 체크항목 |
| 체크항목 | `check` | 담당자가 실제로 체크하는 항목. 주기(등록 기준)·담당자를 가진다. 🔑 **최상위(`parent_id` 없음)로 두면 일일체크리스트 항목**이고 「체크리스트 등록」 탭이 만든다. 프로세스·상황 아래 것은 옛 모델의 잔재다 (아래 「체크 대상」) | 없음 (말단) |

최상위에는 **업무구분과 독립 체크항목** 둘이 올 수 있다. 허용 관계는 `config.js` 의 `CHECK_KIND_CHILDREN` 이 유일한
출처이고, `db.createChecklistItem()` 이 거부한다. **종류는 수정으로 바꿀 수 없다** (지우고 다시 만든다).

### 순차 · 갈래 · 합류 — 간선 테이블 🔑

**소유(트리)와 흐름(간선)을 나눈다.** 트리는 「누구 아래 있나」만 정하고,
단계 순서는 간선 테이블(`checklist_edges`)이 **유일한 출처**다.

| 정하는 것 | 저장 |
|---|---|
| 소유 — 업무항목 소속 · 담당자 상속 · 삭제 전파 · RLS | `checklist_items` 의 `parent_id` · `sort_order` |
| **흐름** — 다음 단계 · 갈래 · 합류 · 조건 | `checklist_edges` 의 `from_id` · `to_id` · `label` · `sort_order` |

- 간선 한 줄 = `from_id → to_id`. **`from_id` 가 null 이면 흐름의 시작**(entry)이다
- **갈래** = 같은 `from_id` 에서 나가는 간선이 여럿. 좌→우는 간선의 `sort_order`
- **합류** = 같은 `to_id` 로 들어오는 간선이 여럿. 버스로 모여 화살촉 하나로 꽂힌다
- **조건**은 간선의 `label` 이다 (`수출 건일 때`) — 도식에서는 선 위 칩, 앱에서는
  갈래 머리(`4.2 해외 · 수출 건일 때`)로 읽는다
- 갈래와 합류가 **한 단계씩 짝지어야 하는 제약이 없다.** 「갈래 A 는 세 단계 뒤에서,
  B 는 바로 합류」 같은 흐름이 그대로 표현된다 (옛 `child_flow` 모델이 못 하던 것이다)
- 🔑 **순환은 넣을 때 막는다** (`db.addProcessEdge`). 그래도 남아 있으면 마지막 층으로
  격리하고 `cyclic` 로 알린다 — 화면이 통째로 비지 않게 하려는 안전판이다
- 🔑 **단계를 지우면 앞뒤를 잇는다**(bridge). 잇지 않으면 뒷 단계가 시작 노드가 되어
  1층으로 튄다. 확인 문구(「③ 와 ⑤ 를 잇습니다」)는 `db.bridgeInfo` 가 준다
- 🔑 **상황(`situation`) 아래 대응 프로세스는 간선에 넣지 않는다.** 갈래는 「늘 있는 경로」,
  상황은 「그날 생긴 일」이라 층이 다르다. 그 안은 트리 사슬(`sort_order`)로 남는다
- ⚠️ `moveChecklistItem` · `reorderChecklistItems` 는 **흐름 번호를 바꾸지 않는다.**
  단계 순서 편집은 간선으로만 한다 (그래서 단계의 ✎ 모달에는 ↑↓ 가 없다)
- 옛 `child_flow`(`seq`/`fork`/`join`) 모델은 걷어냈다. 컬럼은 스키마에 남아 있으나
  코드는 읽지도 쓰지도 않는다

#### 번호 규칙 🔑 — **층이 곧 번호**다

- 층 `layer(v) = 1 + max(layer(선행자))` · 시작 노드는 1 (Kahn 위상정렬 · 최장경로)
- 층에 노드가 **1개면 정수**(캡션이 `③` 으로 그린다), **2개 이상이면 `층.k`**
  (`4.1` `4.2` · k = 층 안의 좌→우 — `checkflow.flowNos` 가 정하고 도식 열 순서와 같다 (P12))
- 합류 노드는 `max(선행자 층) + 1` 이라 **갈래 블록 뒤에 저절로** 놓인다.
  옛 모델의 「갈래 부모가 슬롯 2칸을 먹는다」 같은 보정이 없다
- **번호는 저장하지 않는다** — 간선이 바뀌면 그때그때 다시 계산한다.
  판정은 `db.processFlow` **한 곳**이고 도식·앱·인쇄·캡션이 모두 그 결과만 읽는다
- 상황 아래 대응 프로세스는 간선 밖이라 번호가 `1 2 3`(트리 순서)이다
- `circled(n)` 은 정수만 `①②③` 으로 바꾸고 점 번호(`4.1`)는 원문을 그대로 둔다.
  혼용이 그대로 신호가 된다 — **원문자는 한 줄기, 점 번호는 갈래**다

```
① 하차 파렛트수 확인
② 입고거래명세서 확인
③ 입고검수                 ← 여기서 갈라진다 (간선 2개)
  4.1 냉장 · 냉장품일 때     4.2 상온
⑤ 입고적치                 ← 두 갈래가 같은 to 로 들어온다 (합류 · 화살촉 1개)
```

`category` 컬럼은 최상위(업무구분) 이름을 담는 옛 컬럼이다 — 화면 로직은 쓰지 않고, 이름을
바꾸면 하위까지 함께 맞춘다.

```
입고 (업무구분)
 ├ 일반 입고 (업무항목)   ① 하차 파렛트수 확인 → ② 입고거래명세서 확인 → … 
 └ 반품 입고 (업무항목)   ① … 
출고 (업무구분)
 ├ B2B출고 (업무항목)
 └ B2C출고 (업무항목)    ← B2B출고를 「복제」한 뒤 다른 점만 고친다
```

입고 예시:

```
입고
 ① 하차 파렛트수 확인        ☐ 차량 도착 시각 기록  ☐ 하차 파렛트수 = 송장 대조
 ② 입고거래명세서 확인       ☐ 거래명세서 수령·품목 대조
     ⚠ 입고수량오류  ──발생──▶  ↳ 수량 차이 기록 → 화주 담당자 보고 → 명세서 정정본 수령
     ⚠ 제품 틀림     ──발생──▶  ↳ 오입고 제품 격리 → 반송 여부 확인
 ③ 입고검수                  ☐ LOT 확인  ☐ 유효기간 작성  ☐ 외관·파손 확인
 ④ 입고라벨 부착             ☐ 파렛트별 라벨 출력·부착
 ⑤ 입고적치                  ☐ 로케이션 지정·적치
 ⑥ WMS 입고처리              ☐ WMS 입고 확정
 ⑦ 실물 입고적치 검증        ☐ WMS 재고 = 실물 로케이션 대조
```

이 예시는 `config.js` 의 `CHECK_TEMPLATES` 에 견본으로 들어 있고, 업무프로세스 탭에서 업무구분을
고른 뒤 **「견본: 입고」** 버튼을 누르면 그 업무구분 아래에 같은 이름의 업무항목을 만들며 한 번에
등록한다(`db.seedChecklistTemplate`). 그 업무구분에 같은 이름의 업무항목이 이미 있으면 버튼이 사라진다.

### 체크 대상 🔑

**일일체크리스트에 나오는 것은 독립 체크항목뿐이다.** 트리(업무구분 › 업무항목 › 프로세스)를
타고 내려가 판정하지 않는다 — `db.checklistBoard()` 가 조건 하나로 고른다.

```
kind = 'check'  AND  parent_id 없음  AND  active  AND  cycle ≠ adhoc
```

| 노드 | 일일체크리스트 대상인가 |
|---|---|
| **독립 체크항목** (최상위 · 활성 · 일/주/월) | ✅ 그 기간(일·주·달) 내내 나온다 |
| 독립 체크항목 중 `adhoc`(수시) | ❌ 기간 개념이 없어 보드가 다루지 않는다 (등록 탭에도 없다) |
| 비활성(`active=false`) · 삭제된 항목 | ❌ (등록 탭에서는 흐리게 보인다) |
| 프로세스·상황 아래 체크항목 | ❌ 흐름 설명용이다 — 업무프로세스 탭에도 보이지 않는다 |
| 프로세스 · 상황 | ❌ 흐름의 구성 요소다 |

- 🔑 **`daily` 플래그로 거르지 않는다.** 독립 항목은 그 자체가 일일체크리스트 항목이라
  플래그가 뜻이 없다 (보드는 `active` 만 본다). 그래서 **독립 체크항목 등록·수정 폼에는
  「일일체크리스트 포함」 체크박스를 내지 않는다** — 트리 안의 체크항목·프로세스에만 나온다
- 🔑 **「지난 기간 미체크」(`late`)는 항목을 만든 시점을 본다.** 항목 `created_at` 이 이전 기간
  시작일보다 뒤면 그 기간에는 체크할 수 없었으므로 표시하지 않는다 (방금 등록한 항목이 바로
  미체크로 뜨지 않는다)
- 프로세스 아래에 있던 옛 체크항목은 스키마의 1회성 이행 SQL 이 **담당자를 구운 뒤 독립 항목으로
  옮긴다** (`legacy_parent_id` 에 옛 부모를 남긴다 — 되돌릴 수 있다). 규칙 세 가지가 중요하다 —
  ① **상황과 그 하위 전체는 제외** ② 담당자 굽기는 **정·부가 모두 빈 항목만**
  (부담당자만 지정한 항목의 `sub_assignees` 를 덮어쓰지 않는다) ③ **group 조상이 없어도 떼어낸다**
  (없으면 기존 `category` 유지 — 안 그러면 트리에도 보드에도 안 나오는 항목이 남는다).
  실행 전 백업표 `public._cl_mig_bak_YYYYMMDD` 를 만들고 롤백은 그 표에서 복원한다

### 상황 발생 🔑 — 업무프로세스(매뉴얼) 쪽 이야기다

⚠️ **일일체크리스트에서 상황 발생 처리 UI 는 걷어냈다.** 아래는 업무프로세스 탭이 흐름을
설명하는 방식과 데이터 규칙이다 (`db.setCheck` 의 상황 처리 분기는 그대로 살아 있다).

- **별도 테이블이 없다.** 상황 노드에 그 날짜의 `checklist_checks` 기록이 있으면
  "그 날짜에 발생했다"는 뜻이고 `memo` 가 발생 내용이다
- 발생 처리하면 상황의 하위(대응 프로세스·체크항목)가 **그 날짜의 대상에 들어가고**
  집계(`total`)에 더해진다. 발생 안 된 상황은 프로세스 밑에 **「상황 발생 시」 후보 칩**으로만 보인다
- **발생 해제**하면 그 상황 아래 같은 날짜의 체크 기록도 함께 지운다
  (끼어들었던 단계가 통째로 빠진다). 화면은 확인 문구로 알린다
- 상위 상황이 발생 처리되지 않은 항목은 체크할 수 없다 (`db.setCheck` 가 거부)
- 상황은 **날짜당 1번**만 발생 처리된다 (unique). 같은 날 여러 건이면 발생 내용(memo)에 적는다

### 담당자 — 정 1명 + 부 여러 명 🔑

노드마다 **정담당자**(`assignee_id` · `assignee_name`) 1명과 **부담당자**(`sub_assignees` ·
`[{id, name}]`) 여러 명을 둘 수 있다. 속성 모달에서 정담당자는 선택 하나, 부담당자는
「+ 부담당자 추가」 로 줄을 늘려 고른다. 정담당자와 같은 사람·중복은 저장할 때 빠진다.

- **체크 권한은 정·부가 같다.** 부담당자도 정담당자 대신 체크·상황 발생 처리를 할 수 있다
- 일일체크리스트의 담당자 필터(`전체` · `나` · 특정 담당자)는 정·부 어느 쪽이든 그 사람이면 보여 준다.
  🔑 **필터 자체가 `manageChecklist` 권한자에게만 보인다** — 권한이 없으면 본인 담당 + 공통만 나온다
- 담당 칸에는 정담당자 이름이 크게, 부담당자는 아래 작은 글씨 「부 이담당, 박용마」 로 붙는다

### 담당자 상속 🔑

체크항목의 담당자(정·부 모두)를 비우면 **가장 가까운 상위(프로세스 → 업무항목 → 업무구분)의
담당자 묶음(정 + 부)** 을 따른다. 끝까지 없으면 공통 업무(누구나 체크)다. 프로세스·업무항목·업무구분에
담당자를 한 번만 적으면 그 아래가 모두 그 팀 일이 된다. 정·부는 한 묶음이라 상위에 정만 있으면 부도
비어 있는 채로 내려온다 (부만 따로 상속하지 않는다).

```
db.js   effectiveAssignee(item)   →  rows 의 assignee_eff_id / assignee_eff_name / assignee_eff_subs
서버    checklist_can_check(item) →  checklist_checks RLS 가 이 값으로 판정 (관리자 · 공통 · 정 · 부)
```

## 접근 권한

| 역할 | 조회 | 일일체크리스트 체크 | 업무프로세스 편집 · 체크리스트 등록 | 남의 항목 대신 체크 · 전체 보기 |
|---|:---:|:---:|:---:|:---:|
| 관리자 | ✅ | ✅ | ✅ | ✅ |
| 용마담당자 | ✅ | ✅ | ✅ | ✅ |
| 화주관리자 | ✅ | ✅ | ✅ | ✅ |
| 화주영업팀 | ✅ | 본인 담당만 | ❌ | ❌ |
| 현장작업자 | ✅ | 본인 담당만 | ❌ | ❌ |

- 관리 권한은 `config.js` 의 `PERMISSION` 에 있는 **`manageChecklist`** 다.
  화면은 `can(user, 'manageChecklist')`(웹) 으로만 판정하고 역할명을 직접 비교하지 않는다
- 체크·상황 발생 판정은 **`db.canCheckItem(user, item)` 한 곳**에 있다 — 웹·앱이 같은 함수를 쓴다.
  `item` 은 `checklistBoard()` 가 상속 담당자(`assignee_eff_id` · `assignee_eff_subs`)를 붙여 준 줄이어야 한다

```
상속 정담당자 본인  또는  상속 부담당자 중 한 명  또는  담당자 없음(공통 업무)  또는  manageChecklist 권한자(대신 체크)
```

- 서버 RLS 도 같은 기준이다 (`supabase/schema.sql` 의 `can_manage_checklist()` ·
  `checklist_can_check()`). **화면 제어만 믿지 않는다**
- 🔑 **`checked_by is null` 인 행도 지나가야 한다.** 체크 없이 메모만 남긴 행과 체크 해제
  (메모가 남아 행을 지우지 않는 경우)가 `checked_by` 를 비우므로, `checklist_checks` 의
  insert·update 정책은 `checked_by = auth.uid()` 외에 `checked_by is null` +
  `checklist_can_check(item_id)` 를 함께 허용한다

## 화면 구성 (웹) — 목적이 다른 탭 3개 🔑

탭 순서는 **일일체크리스트 | 업무프로세스 | 체크리스트 등록** 이다.

| 탭 | 목적 | 읽는 법 | 모양 |
|---|---|---|---|
| **일일체크리스트** (기본) | 오늘 내가 **빠뜨리면 안 되는 것**을 챙긴다 | 구획(일별 › 이번 주 › 이번 달)마다 훑고 체크 | 등록 기준 3구획 표. 7컬럼 `구분 · 항목 · 주기 · 담당자 · 내용 · 체크 · 특이사항` |
| **업무프로세스** (`manageChecklist`) | 업무 흐름(갈래·합류)을 한눈에 보는 매뉴얼 · **흐름 편집** | 위에서 아래로 단계를 따라간다 (옆으로 벌어지면 갈래, 다시 모이면 합류) | 세 칸 — 좌 트리(업무구분 › 업무항목) · 중 흐름 도식(제목만 보이는 카드 + 선) · 우 설명 표. 상황은 카드 안 주황 블록 |
| **체크리스트 등록** | 담당자별 체크리스트를 **기준(일·주·월)별로 등록** | 표에 바로 적는다 | 인라인 편집 표 `구분 · 항목 · 주기 · 담당자 · 내용` + `≡` 순서 + `✕`. `manageChecklist` 권한자만 편집, 그 밖은 읽기 전용 |

|---|---|
| `pages/checklist.js` | 셸 · 탭 전환 · 공유 state · 실시간 구독(`guarded`) |
| `pages/checklist/daily.js` | 탭1 (등록 기준 3구획 표) |
| `pages/checklist/process.js` | 탭2 셸 · 좌측 트리 · 우측 설명 표 · 흐름 편집 이벤트(카드 우클릭 메뉴 · 연결 모드 · 간선 팝오버) |
| `pages/checklist/flowview.js` | 탭2 가운데 도식 렌더 (카드 HTML + SVG 선) |

탭2 는 흐름(트리 + 간선)이다. 한 화면에 섞지 않는다.

### 탭 1 「일일체크리스트」 (기본)

등록 기준(일별·주차별·월별)으로 묶은 **내 체크리스트**다. 화면은 `db.checklistBoard()` 가 준
세 묶음을 그대로 그린다 — 기간·상속·지연 계산을 화면이 다시 하지 않는다.

```
[◀ 2026-09-18 ▶ 오늘]   담당자 [전체 ▾]                         남은 5 · 7 / 12 ▓▓▓░░

일별  9/18                                                                        3 / 5
 구분 │ 항목                          │ 주기 │ 담당자 │ 내용        │ 체크 │ 특이사항
 입고 │ 하차 파렛트수 대조 [완료]      │ 일별 │ 김현장 │ 송장과 대조 │  ☑  │ 1파렛 지연
      │   2026-09-18 08:12 김현장     │      │        │             │     │
 입고 │ LOT 확인 [지난 기간 미체크]    │ 일별 │ 공통   │             │  ☐  │
이번 주  9/14~9/20                                                                1 / 4
 출고 │ 주간 재고 실사                 │ 주차별│ 이담당 │ 창고 A·B    │  ☐  │
이번 달  9월                                                                      0 / 3
 안전 │ 소화기 점검                    │ 월별 │ 박용마 │             │  ☐  │
```

| 요소 | 동작 |
|---|---|
| 날짜 이동 | `◀` `▶` 로 하루씩, 날짜칸 직접 선택, `오늘` 버튼. **날짜가 속한 기간**(주·달)의 구획이 함께 바뀐다 |
| 구획 3개 🔑 | `일별`(그 날짜) · `이번 주`(월~일 · 머리에 `9/14~9/20`) · `이번 달`(`9월`). 항목이 없는 구획은 「이 기준으로 등록된 항목이 없습니다」 한 줄로 남는다 |
| 담당자 | 기본 `전체`. 🔑 **`manageChecklist` 권한자에게만 보인다** — 권한이 없으면 `checklistBoard` 가 본인 담당(정·부) + 공통만 준다. 상속 담당자로 거른다 |
| 진행 | `남은 N · done / total` 과 막대. 100% 면 초록. 카드 머리에도 `done / total` 이 붙는다 |
| 체크박스 | 켜면 그 **기간**의 기록 1건이 생긴다. 같은 주·같은 달 안에서는 어느 날 눌러도 같은 기록이다 (`db.periodStart`) |
| 체크한 줄 🔑 | **사라지지 않는다.** 흐리게 + 「완료」 배지 + `체크한 시각 · 사람` 이 남는다 (누가 언제 했는지가 현장의 근거다) |
| `지난 기간 미체크` | 직전 기간(어제 · 지난주 · 지난달)에 체크 기록이 없으면 붉은 꼬리표가 붙는다 (`row.late`) |
| 특이사항 | 줄마다 인라인 입력칸. **체크 전에도 적을 수 있다** (`db.setCheckMemo`) — 그날 있었던 일은 체크 여부와 별개다. 체크를 해제해도 특이사항은 지워지지 않는다 |

- 체크 권한이 없는 줄은 회색 + 체크박스·특이사항이 잠긴다 (조회만)
- 등록된 항목이 하나도 없으면 「등록된 체크리스트가 없습니다 — 체크리스트 등록 탭에서 추가하세요」
- ⚠️ 옛 화면의 **`일일 | 전체` 세그먼트 · 상황 발생 칩 · 「어제 미체크 N건 →」 버튼 · 완료 접기**는
  없앴다. 트리 판정을 걷어내면서 함께 빠진 것이고, 되살리지 않는다

### 탭 2 「업무프로세스」 (`manageChecklist`) — 세 칸 (구성 · 흐름 · 설명)

🔑 **이 탭이 다루는 것은 두 가지뿐이다 — 흐름(카드·선·라벨)과 그 설명 표.**
체크항목(`kind='check'`)은 **여기서 만들지도 보이지도 않는다** (아래 「체크 대상」 참고).

```
 좌 pm-nav (230)          │  중 pm-canvas (가변 · 가로 스크롤)          │  우 pm-side (320)
─────────────────────────┼───────────────────────────────────────────┼──────────────────────
업무구분 › 업무항목 [+구분]│ 입고 › 일반 입고 · 담당 (✎ 복제) [편집][인쇄]│ ⑤ 입고적치   [+ 행 추가]
■ 입고                  2 │  ┌ 3  입고검수                    ✎ ▾┐     │ 구분 │ 내용      │비고
   │ 일반 입고  ◀ 선택    │  └────────────┬──────────────────────┘     │ 준비물│ 팔레트 라벨│양식v2
   │ 반품 입고            │        (카드 우클릭 → 메뉴)              │ 주의 │ 온도 기록  │
■ 출고                  2 │      ┌──────┴──────┐  ← T자 (갈래 부모는   │      │ (빈 행)   │

                          │  ┌ 5  입고적치 …                            │      │           │
```

**카드**는 기본이 **번호 배지 + 제목 한 줄**이다 (좌상단 사각 배지 · 갈래 줄은 점선 테두리).
머리를 누르면 펼쳐져 **설명 · 담당 · 상황 블록 · 「+ 상황」** 이 나오고, 다시 누르면 접힌다.
흐름을 눈으로 훑는 것이 목적이라 접힌 상태가 기본이다 (`state.open` 에 펼친 id 를 담는다).

#### 흐름 편집 = 카드 우클릭 메뉴 🔑

「속성 폼에서 연결 방식을 고르기」를 버리고 **카드를 우클릭해** 흐름을 만든다.
🔑 **편집 수단은 이 메뉴 하나다** — 호버로 뜨던 `＋`(다음 단계) · `↳`(잇기) 버튼은 없앴다
(손잡이가 둘이면 어느 쪽이 갈래인지 알기 어렵고, 손가락으로는 호버가 없다).

| 메뉴 항목 | 하는 일 | db |
|---|---|---|
| `하위 프로세스 추가` | 카드 아래 틈에 이름 입력칸 → Enter (입력칸이 **새 카드로 옮겨가** 사슬을 계속 만든다) | `createChecklistItem({from_id})` |
| **갈래 만들기** | 별도 항목이 아니다 — 하위 프로세스가 이미 있는 카드를 **다시 우클릭해 또 추가** | 같음 (간선이 하나 더) |
| `연결…` (합류) | **연결 모드**(파란 배너 「연결할 단계를 클릭하세요 · Esc 취소」) → 대상 카드 클릭 | `addProcessEdge` |
| `속성` | 속성 모달 (카드 머리의 `✎` 와 같다) | `updateChecklistItem` |
| `삭제` | 확인 문구에 「③ 와 ⑤ 를 잇습니다」 가 붙는다 (모달의 삭제와 **같은 문구** — `form.deleteText` 한 곳) | `deleteChecklistItem` (bridge) |
| 갈래 좌우 순서 | 선 위 라벨 칩 → 팝오버의 `←` `→` | `reorderEdges` |
| 조건 라벨 · 연결 끊기 | 선 위 라벨 칩(라벨 없는 간선은 편집 모드에서 작은 점) → 팝오버 | `setEdgeLabel` · `removeProcessEdge` |

- **편집 모드에서만 네 항목이 나온다.** 비편집 모드에서는 `속성 보기` 하나뿐이고
  (읽는 화면에서 구조가 바뀌면 안 된다), **연결 모드에서는 열리지 않는다** (지금은 대상을
  고르는 중이다 · Esc 로 빠져나온다). 아이콘은 이모지가 아니라 `icons.js` 의 단색 SVG 다
- 메뉴는 **Esc · 바깥 클릭**으로 닫히고 문서에 건 리스너를 그때 걷는다. 화면을 떠나거나
  탭을 바꿀 때는 `disposeManage()` 가 남은 메뉴·간선 팝오버·연결 모드 Esc 를 모두 걷는다
- 🔑 **연결은 클릭 전에 두 번 알린다** — 카드에 마우스를 올리면 예상 화살표를 **점선**으로
  그려 보이고(`.pm-ghost` — 임시 SVG 라 다시 그리면 사라진다), 클릭하면
  「「③ WMS처리」 → 「⑦ 출고완료」 로 연결하시겠습니까?」 로 확인한다.
  **취소하면 연결 모드를 그대로 둔다** (다른 카드를 바로 고를 수 있게)

- 🔑 **연결 모드에서 고를 수 없는 카드는 흐리게 막는다.** 판정은 화면이 하지 않는다 —
  `from → to` 가 순환이 되는 조건은 「to 에서 from 으로 닿는다」 = **from 의 선행자들**이라
  `db.reachableFrom(groupId, fromId, {reverse:true})` 가 그대로 답이다.
  거기에 자기 자신과 이미 이어진 곳을 더한 집합이 비활성 대상이다
  (그래도 눌리면 `addProcessEdge` 가 다시 거부한다 — 화면은 안내, 규칙은 db)
- **상태 알림은 막지 않는다** — 시작 노드 2개 이상이면 회색 배지 「시작 단계 N개」,
  나가는 간선이 없는 노드가 2개 이상이면 각 카드에 주황 칩 「이후 단계 없음」,
  `cyclic` 이면 빨간 경고. 만드는 중에는 흐름이 잠깐 끊겨 있는 것이 정상이다
- **버린 것**: 프로세스 드래그 정렬 · ↑↓ 이동(단계만 · 상황은 유지) · 「하위 프로세스 연결
  (순차/갈래)」 폼 · 「+ 하위 프로세스」 · 들여쓰기 레일 · **호버 손잡이 `＋` `↳`**
- **상황(`situation`)** 은 그대로다 — 카드 안 주황 블록이고, 그 아래 대응 프로세스는
  트리 사슬(번호 `1 2 3`), 순서는 ≡ 드래그·↑↓ 로 바꾼다

#### 우측 — 프로세스 설명 표 (구분 · 내용 · 비고) 🔑

고른 단계에 붙는 자유 입력 표다 (`checklist_notes`). 흐름을 말로 설명하는 자리다.

- 머리에 **번호 + 단계 이름**이 붙어 있다 (sticky — 표가 길어도 무엇의 설명인지 보인다)
- 무엇을 보여 줄지는 `state.pick` 하나로 갈린다 — **단계**를 고르면 그 단계,
  **상황 블록**을 고르면 그 상황(주황), **아무것도 고르지 않으면 업무항목**(개요 자리)이다.
  대상 id 만 다르고 표는 똑같다 (`listChecklistNotes` 는 셋을 모두 받는다)
- 행 추가: **마지막 줄이 늘 빈 행**이고 값이 들어오면 그때 등록된다
  (「행 추가」 버튼은 그 빈 행으로 커서를 옮긴다 · 마지막 행에서 Tab 도 같다)
- `구분` 은 그 업무항목에서 이미 쓴 값으로 `datalist` 자동완성 (`db.noteLabels`)
- 순서는 `≡` 드래그(`reorderChecklistNotes`), 삭제는 `✕`(확인 없음 — **하드 삭제**)
- 입력 중에는 `is-dirty` 가 붙어 실시간 갱신이 값을 지우지 않는다 (`checklist.js` 의 `guarded`).
  저장이 실패하면 **토스트만 띄우고 적은 값을 남긴다**

#### 도식 배치 (2-pass) 🔑

- 카드 높이는 접힘·펼침에 따라 달라져 계산식이 없으므로 **먼저 붙여 재고(1-pass)
  그 값으로 자리를 잡는다(2-pass)**
- 🔑 **순서가 있다**: 열 수(`dagCols` — 더미 열까지 센다)는 측정 없이 셀 수 있으므로 →
  레인 폭(`laneWidth(avail, cols, {gapX})`)을 정해 `--pm-lane` 으로 내려주고 →
  **그다음에** 높이를 잰다 → `layoutDag`. 어기면 다른 폭으로 줄바꿈된 높이를 쓰게 되어
  선이 카드에서 떨어진다. 레인 폭의 유일한 출처는 `checkflow.js` 이고 CSS 는 변수만 읽는다
- **치수** — `gapY 56`(층 사이 · 버스와 라벨이 이 틈 가운데를 지난다) · `gapX 40`(열 사이) ·
  레인 폭 `200~260` 가변. 들여쓰기는 없다 (옛 `colGap` 파생도 함께 사라졌다).
  레인 폭은 **열 수에 맞춰 정한다** — 열이 화면에 들어오면 꽉 채우고, 안 들어오면 200px 에서
  멈추고 가로 스크롤한다
- 🔑 **T자 배치 — 규칙 하나다: 「그 층에 항목이 하나뿐인 카드」만 자식들이 내려가는 자리의
  가운데로 옮긴다** (반열 = `(lane + gapX) / 2` 단위 · `layoutDag`).
  갈래 부모가 자식 열 범위의 **가운데 위**로 올라가 세로 기둥 + 가로 버스, 곧 T 가 된다.
  - **아래 층부터 위로** 정하므로 갈래 부모 위의 **순차 줄기도 차례로 따라 올라온다**
    (`③ → 4.1/4.2 → ⑦` 예시에서 ①②③ 이 함께 반열로 간다 — 검사기의 고정 예시가 단언한다)
  - 자식이 다음 층에서 **더미 열**로 내려가면(긴 간선) 그 더미 열을 자식 자리로 본다 —
    선이 실제로 지나는 열이 T 의 팔이다
  - ⚠️ **옆에 다른 카드나 지나가는 선(더미)이 있는 층은 옮기지 않는다.** 옮기면 같은 층의
    x 대역이 겹치거나(P4) 카드가 지나가는 선을 삼킨다(P2). 혼자인 층은 열 번호가 0 이라
    왼쪽으로 밀려날 일도 없다. **합류·순차 배치 규칙은 그대로다** (합류는 `max(pred 층)+1`)
- **선만 SVG 다.** 카드는 HTML 이라 접힘·✎ 모달·상황 블록이 그대로 살아 있다
- 라벨 칩은 SVG 가 아니라 **HTML**(`.pm-labels`)이다 — 같은 좌표계에 얹어 클릭·팝오버를 붙인다.
  배치할 때마다 다시 만들어지므로 클릭은 `.pm-canvas` 에 **위임**해 받는다
- 🔑 **라벨 칩의 자리·크기는 `layoutDag` 가 정한다** (`left·top·width·height` 를 인라인으로
  준다 · 폭은 `LABEL_SIZE` 로 글자 수에서 어림하고 넘치면 말줄임). 자리는 **그 갈래가
  내려가는 열의 x**(버스에서 내려오는 세로 구간)이고, 같은 틈에서 겹치는 칩은 **오른쪽으로
  밀어** 겹침을 없앤다 (P13).
  ⚠️ 예전에는 「출발 카드 중심 x · 틈 가운데 y」라 **같은 `from` 에서 나가는 갈래의 칩이 모두
  한 점에 겹쳐**, 가려진 간선은 조건 라벨·갈래 순서·연결 끊기를 열 수 없었다.
  CSS 로 자리를 옮기면 이 계산이 무의미해지므로 CSS 는 모양만 준다
- 🔑 **`arrange`(층·열 계산)는 같은 배열로 연달아 부르면 한 번만 돈다** — `dagCols`(폭)와
  `layoutDag`(좌표)가 한 배치에서 함께 불리므로 결과 한 벌을 재사용한다 (레퍼런스가 같을 때만)
- ⚠️ **선에 반투명을 쓰지 않는다.** 같은 `to` 로 들어오는 합류 버스는 좌표가 완전히 겹쳐
  그려지므로, 반투명이면 겹친 자리만 진해져 「굵은 선」 으로 오해한다
- **다시 배치하는 때** — 창 리사이즈(디바운스 1회) · 우측 구역 **드래그 종료 시 1회**(끄는 동안
  매 프레임은 하지 않는다 · 높이를 다시 재는 일이라 무겁다) · 서랍 여닫기 · 세그먼트 전환
  (뒤 둘은 화면을 통째로 다시 그리므로 저절로 따라온다). 창 리사이즈 구독과 **연결 모드의
  Esc 리스너 · 간선 팝오버의 문서 리스너**는 화면을 떠날 때 끊는다
  (`disposeManage()` — `checklist.js` 의 정리 함수가 부른다)
- **인쇄**는 상세를 모두 펼치고 **설명 표를 카드 아래 작은 표로 붙인 뒤** A4 폭(≈680px)으로
  다시 배치한다 (표를 붙인 뒤 배치해야 선이 카드에 붙는다). 카드·표는 페이지 사이에서
  자르지 않는다(`break-inside: avoid`). 끝나면 펼침 상태를 원래대로 돌린다

#### 무교차 근거 — 이제는 **기준선으로 관리**한다 🔑

옛 트리판의 V1~V7 은 「교차 0」을 목표로 했다. **DAG 에서는 교차 0 이 불가능하다**
(층·열이 정해진 그래프에서 교차 수를 0 으로 만들 수 없는 그래프가 있다). 그래서 목표를
「**카드·선이 잘못 놓이는 일은 0 · 교차 수는 기준선 대비 악화 금지**」로 바꿨다.
검사기는 `tools/checkflow-check.js` — 배치 코드를 건드리면 `npm run check:flow`.

| | 불변식 (랜덤 DAG + 치수 5조합으로 센다) |
|---|---|
| **P1** | 카드 쌍이 겹치지 않는다 |
| **P2** | 간선이 카드 내부를 지나지 않는다 (span > 1 인 간선은 **더미 열**로 내려온다) |
| **P3** | 간선의 y 가 단조 비감소 — 흐름이 위로 올라가 보이지 않는다 |
| **P4** | 같은 층 카드의 x 대역이 서로소 · 층끼리 y 대역이 서로소 |
| **P5** | x 는 `col * (lane + gapX)` + **반열 이동**(T자) 이산값 — 이동은 ① 반열의 정수배 ② 오른쪽으로만 ③ **그 층에 카드가 하나뿐일 때만** (들여쓰기 항이 없다) |
| **P6** | `width`·`height`·레인 폭이 실제 최대와 맞는다 |
| **P7** | 노드 수 = 박스 수 · 그릴 수 있는 간선 수 = `edges` 행 수 |
| **P8** | **부착** — 출발 = 카드 바닥 · 도착 = 카드 천장 · 꺾임은 층 사이 틈 안 · 경로는 `M·V·H` 만 |
| **P9** | 화살촉이 도착점에 있고 모양·방향이 규격대로다 |
| **P10** | **어느 카드에서 어느 카드로** 이어지는지가 `edges` 와 맞는다 |
| **P11** | 교차 수가 **기준선보다 나빠지지 않는다** (중위·최대·**합계** 셋을 함께 본다) |
| **P12** | **`flowNos` 의 층 내 순서 = `layoutDag` 의 열 순서** — 번호와 열이 한 벌이다 |
| **P13** | 조건 라벨 칩끼리 **사각형이 겹치지 않는다** (겹치면 뒤의 칩을 누를 수 없다) |

- 🔑 **개수(P7)만 세면 연결 상대가 틀려도, 끝이 카드에서 떨어져도 0건이 나온다.**
  지난 결함 두 건이 정확히 그것이었다 (`docs/AGENT_LEARNING_LOG.md`)
- 🔑 **검사기를 믿기 전에 변이로 검사기를 검증한다** (더미 열 예약 제거 · 화살촉 규격 깨기 ·
  오배선 · 라벨 자리를 옛 식으로 되돌림 → 해당 항목만 올라오는지)
- 🔑 **커버리지 카운터를 함께 읽는다** — 긴 간선·3폭 이상 층·합류·갈래·라벨이 몇 건 나왔는지
  찍는다. 0건이면 「깨끗해서 0」이 아니라 「검사 거리가 없어서 0」이다
- 🔑 **P11 기준선 키는 `건수:시드:g생성기해시`** 다. 랜덤 생성기 설정(`GEN`)을 고치면 교차 수
  분포가 달라져 옛 기준선과 비교할 수 없다. `sum` 이 없는 낡은 기준선·기준선 없음은 **실패**이고,
  다시 기록할 때는 사유를 남긴다 (`npm run check:flow -- --baseline --reason=사유`)

### 탭 3 「체크리스트 등록」

일일체크리스트에 나올 **독립 체크항목**을 만드는 곳이다. 업무프로세스 탭의 우측 설명 표와
같은 인라인 편집 규약을 쓴다 — 마지막 줄은 늘 빈 행이고, 값이 들어오면 그때 저장된다.

```
등록 기준(일별·주차별·월별)에 따라 담당자의 일일체크리스트에 나옵니다.
 구분      │ 항목                    │ 주기   │ 담당자  │ 내용            │
 [입고  ▾] │ [하차 파렛트수 대조    ] │ [일별▾]│ [김현장▾]│ [송장과 대조  ] │ ≡ ✎ ✕
 [        ] │ [항목 이름을 적으면 …  ] │ [일별▾]│ [공통 ▾]│ [            ] │      ← 빈 행
```

| 요소 | 동작 |
|---|---|
| 저장 시점 | 칸을 벗어날 때(blur). 기존 줄은 `db.updateChecklistItem`, **빈 행은 항목 이름이 있어야** `db.createChecklistItem({kind:'check', parent_id:null})` 로 등록된다 |
| 구분 | 자유 입력 + `datalist` 자동완성 (`db.checklistCategories()` — 이미 쓰인 구분값) |
| 주기 🔑 | `일별` `주차별` `월별` **3종만**. 수시(`adhoc`)는 기간이 없어 보드가 다루지 않으므로 고를 수 없다 |
| 담당자 | 정담당자 하나(비우면 `공통`). **부담당자·요일·일자·활성 여부는 `✎` 속성 모달**(탭2 와 같은 `form.js`)에서 고친다 |
| `≡` 순서 | 손잡이를 끌어 순서를 바꾼다 (`db.reorderChecklistItems(null, ids)`) |
| `✕` 삭제 | soft delete. **체크 기록은 남는다** |
| 권한 | `can(user, 'manageChecklist')` 만 편집한다. 그 밖은 입력칸이 잠긴 **읽기 전용**이고 빈 행도 없다 |

- 저장이 실패하면 적은 값을 그대로 두고 토스트만 띄운다 (다시 그리면 입력한 것이 사라진다)
- 편집 중인 칸(`.is-dirty`)이 있으면 실시간 갱신이 화면을 다시 그리지 않는다 (셸의 `guarded`)
- 비활성 항목도 흐리게 보인다 — 다시 켜려면 `✎` 에서 「활성」 을 체크한다

## 화면 구성 (앱)

### `#/checklist` 일일체크리스트 — 상단바 메뉴

웹 탭1 과 **같은 `db.checklistBoard()`** 를 읽어 카드 한 열로 편 것이다 (판정이 갈라지지 않는다).

```
[◀ 2026-09-18 ▶ 오늘]          7 / 12        ← 큰 진행 카운터 (남은 항목 5개)
일별  9/18                              3 / 5
☑ 하차 파렛트수 대조 [완료]
   송장과 대조
   입고 · 일별 · 김현장 · 2026-09-18 08:12 김현장
   [1파렛 지연                         ]      ← 특이사항 (체크 전에도 쓴다)
☐ LOT 확인 [지난 기간 미체크]
   입고 · 일별 · 공통
   [                                   ]
이번 주  9/14~9/20                      1 / 4
이번 달  9월                            0 / 3
```

- 구획 3개(`일별` · `이번 주 9/14~9/20` · `이번 달 9월`)마다 머리에 기간과 `done / total`
- **카드 전체가 터치 영역**(48px 이상)이라 장갑을 낀 채 눌러도 빗나가지 않는다.
  특이사항 입력칸을 눌렀을 때는 체크되지 않는다
- 체크해도 카드는 사라지지 않는다 — 흐리게 + 「완료」 + 체크한 시각·사람
- 담당자 필터가 없다 — **로그인 사용자 본인 담당(정·부) + 공통 항목만** 본다 (현장작업자 기준)
- 🔑 상황 발생 시트·완료 접기·`일일 | 전체` 세그먼트는 없앴다 (웹과 같다)

### `#/process` 업무프로세스 — 상단바 메뉴 · 보기 전용

현장에서 매뉴얼을 펼쳐 보는 화면이다. 업무구분·업무항목 세그먼트로 고르면 그 흐름을
**세로 스테퍼**로 그린다 — 시작 → 단계 박스(이름 · 설명 · 담당) → 박스 아래 주황 블록
`⚠ 상황명 발생 시`(어떤 때인지 · 대응 단계 1→2→3 · `↩ 처리 후 5. 다음 단계 로 이어감`)
→ … → 완료.

- 🔑 **앱은 도식을 그리지 않는다** — 좁아서 좌우로 읽기 어렵다. 같은 층에 단계가 여럿이면
  (갈래) `4.1 국내 · 수출 아닐 때` 머리가 붙은 하위 스테퍼(파란 점선 레일)로 펴고,
  번호는 머리에만 적어 동글은 가운뎃점이 된다 (번호를 두 번 적으면 줄이 길어진다)
- **합류도 캡션 한 줄**이다 — 갈래 블록 끝에 `↩ 갈래가 다시 5. 입고적치 로 모입니다`.
  모일 곳은 **갈래 멤버 모두의 다음 단계**(공통 후속)로 찾는다 (`flow.nexts` 만 본다)
- 층·번호·다음 단계는 웹과 같은 **`db.processFlow`** 를 읽는다 (좌표만 웹 전용이다)
- 🔑 **체크항목은 나오지 않는다** — 여기는 흐름 매뉴얼이고 체크는 `#/checklist` 가 맡는다
  (웹 업무프로세스 탭과 같은 기준). 설명 표도 앱에는 아직 없다
- 편집은 웹에서만 한다. 비활성 업무구분·업무항목·단계는 나오지 않는다

## 데이터 (`db.js`)

기간 판정·담당자 상속·상황 발생·권한 판정은 **`db.js` 한 곳**에만 있다. 화면은 결과만 그린다.

| 함수 | 설명 |
|---|---|
| `listChecklistItems(f)` | 항목 목록. `root`(업무항목 id → 그 아래 전체) `kind` `includeInactive` `assignee` 로 거른다 |
| `listChecklistDivisions()` | 업무구분(최상위 `division`) 목록. 비활성 포함 |
| `listChecklistGroups(divisionId?)` | 업무항목 목록. 업무구분 id 로 거른다. `null` 이면 업무구분 없는 옛 업무항목(미분류) |
| `duplicateChecklistGroup(id, user)` | 업무항목을 하위 전체와 함께 복제. `{group, count}` 반환 |
| `checklistTree(rows)` | 평평한 목록을 `{item, depth, children}` 트리로 묶는다 (순수 함수) |
| `allowedChildKinds(parentKind)` | 그 종류 아래 둘 수 있는 종류 (`CHECK_KIND_CHILDREN`) |
| `createChecklistItem(payload, user)` | 등록. 최상위는 업무항목만. 순서는 형제 맨 뒤. 종류 관계·업무항목 이름 중복을 검증한다 |
| `seedChecklistTemplate(name, divisionId, user)` | `CHECK_TEMPLATES[name]` 으로 그 업무구분 아래 업무항목 한 벌을 만든다. `{group, count}` 반환 |
| `updateChecklistItem(id, patch, user)` | 수정 (종류는 못 바꾼다). 업무항목은 `parent_id` 로 다른 업무구분으로 옮긴다. 최상위 이름을 바꾸면 하위 `category` 도 맞춘다. 부담당자는 `sub_assignee_ids` 배열로 준다 |
| `moveChecklistItem(id, dir, user)` | 형제 사이 순서 이동 (`'up'` / `'down'`) |
| `reorderChecklistItems(parentId, orderedIds, user)` | 드래그 정렬. 같은 상위 아래 항목들의 순서를 한 번에 정한다. 목록에 없는 형제(다른 종류)는 제자리를 지킨다 |
| `deleteChecklistItem(id, user)` | 하위까지 soft delete. 지운 개수를 돌려준다 |
| `checklistBoard(date, {assignee, user})` | 🔑 **일일체크리스트가 그리는 전부.** 독립 체크항목을 `{daily, weekly, monthly}` 세 묶음으로 준다. 줄 = `{item, category, title, cycle, description, assignee_eff_*, check, late, period}`. `user` 에 `manageChecklist` 권한이 없으면 **본인 담당(정·부) + 공통만** 준다 (`assignee` 는 권한자의 필터). 트리 판정을 쓰지 않는다 |
| `periodStart(cycle, date)` · `prevPeriodStart(cycle, date)` | 🔑 **기간의 시작일**(순수 함수). `daily`=그 날 · `weekly`=그 주 **월요일**(ISO) · `monthly`=그 달 1일. 「기간당 1회」 판정은 이 두 함수에만 둔다 |
| `checklistCategories()` | 독립 체크항목이 쓴 `구분` 값 (등록 탭 자동완성용 · 가나다순) |
| `listChecks(date)` | 그 날짜의 체크 기록 |
| `setCheck(itemId, date, on, memo, user)` | 체크/해제. 날짜는 항목 주기의 **기간 시작일로 정규화**한다(`periodStart`) — 같은 주·달 안에서는 기록 1건이다. 상황 노드면 **발생/해제**. 🔑 체크를 **켜는 것**은 담당자 · 상위 상황 발생을 통과해야 한다 (화면이 아니라 여기가 규칙의 출처다). 주기(`isDueOn`) 가드는 트리 항목에만 걸고 **독립 항목은 받지 않는다** — 기간 안이면 언제든 체크한다. 해제할 때 특이사항이 남아 있으면 행을 지우지 않고 `checked_at` 만 비운다 |
| `setCheckMemo(itemId, date, memo, user)` | **체크하지 않고 특이사항만** 남기거나 고친다. 없던 기록이면 `checked_at` 이 빈 메모 전용 행을 만든다 (메모까지 비우면 행을 지운다) |
| `canManageChecklist(user)` `canCheckItem(user, item)` | 권한 판정 (웹·앱 공용). 체크는 정·부 담당자 본인, 공통 업무, 관리 권한자 |

#### 흐름 · 설명 표 함수 🔑

| 함수 | 설명 |
|---|---|
| `processFlow(groupId, {includeInactive})` | 업무항목 한 벌의 흐름 — `{nodes, edges, layer, no, order, layers, nexts, preds, joinTarget, entries, exits, cyclic}`. **캡션·도식·앱·인쇄가 모두 이것만 읽는다.** 층·층 내 순서·번호는 `checkflow.flowNos` 에 맡긴다 (유일 출처). `layers` 층별 id · `joinTarget[갈래지점]` 모든 갈래의 **첫 공통 후속**(없으면 null · 「3단계 뒤 합류」도 잡는다). 비활성을 뺄 때는 간선을 이어 준다(끊으면 뒷 단계가 1층으로 튄다) |
| `addProcessEdge(fromId, toId, {label, sortOrder}, user)` | 단계를 잇는다 (`fromId` 가 null 이면 흐름의 시작). **순환·자기참조·중복·다른 업무항목을 거부** |
| `removeProcessEdge(edgeId, user)` · `setEdgeLabel(edgeId, label, user)` | 연결 끊기 · 조건 라벨 |
| `reorderEdges(fromId, orderedToIds, user)` | 같은 `from` 에서 갈라진 갈래의 좌→우 순서. 🔑 **반드시 업무항목(`group_id`) 안으로 좁힌다** — `fromId` 가 null(흐름의 시작)이면 `from_id` 만 보면 **모든 업무항목의 시작 간선**이 대상이 되어 남의 업무항목 순서까지 다시 쓴다 (`pushEdge` 의 `sort_order` 채번도 같다) |
| `reachableFrom(groupId, fromId, {reverse})` | 간선을 따라 닿는 단계. 🔑 **연결 모드에서 막을 후보 = `{reverse:true}`**(from 의 선행자들) |
| `bridgeInfo(itemId)` | 단계를 지우면 어디가 이어지는지 `{prev, next}` — 확인 문구용. 잇는 일은 `deleteChecklistItem` 이 한다 |
| `createChecklistItem({kind:'process', parent_id, from_id})` | 단계를 만들면서 **간선도 함께** 만든다. `from_id` 를 주면 그 뒤에, `null` 이면 시작, 안 주면 맨 뒤 |
| `listChecklistNotes(itemId)` · `createChecklistNote` · `updateChecklistNote` · `deleteChecklistNote` · `reorderChecklistNotes` | 설명 표(구분·내용·비고). `itemId` 는 프로세스·업무항목·상황 모두 된다. ⚠️ 삭제는 하드 삭제 |
| `noteLabels(groupId)` | 그 업무항목에서 쓴 `구분` 값 (자동완성용) |

### `checklistBoard` 뷰모델

```
{ daily: [Row], weekly: [Row], monthly: [Row] }        // 기준별 묶음 (그 안은 sort_order 순)
Row = { item,                     // 원본 항목 (id 는 item.id 다)
        category, title, cycle, description,
        assignee_eff_id, assignee_eff_name, assignee_eff_subs,   // 상속 담당자
        check: { checked_at, checked_by_name, memo } | null,     // 그 기간의 기록
        late,                     // 직전 기간에 체크 기록이 없었는가
        period }                  // 기록이 붙는 날짜 = periodStart(cycle, date)
```

- `check` 는 있는데 `checked_at` 이 `null` 이면 **특이사항만 적어 둔 줄**이다 (체크 전)
- 담당자 필터는 **상속 담당자**로 거른다. 담당자가 없는 **공통 업무는 누구의 목록에나 든다**
- `manageChecklist` 권한이 없는 사용자는 `assignee` 를 주지 않아도 본인 것으로 좁혀진다
- 웹 탭1(`daily.js`)·앱(`mobile/screens/checklist.js`)이 같은 뷰모델을 그린다

### 흐름 뷰모델

업무프로세스 탭은 `db.processFlow(groupId)` 와 트리(`db.checklistTree`)를 읽는다.
일일체크리스트와 공유하는 뷰모델은 없다 (보는 데이터가 다르다).

### 등록 기준(주기) 판정 🔑

**독립 체크항목은 「그 날짜에 나오는가」가 아니라 「어느 기간에 속하는가」로 다룬다.**
기간 계산은 `periodStart()` · `prevPeriodStart()` 두 순수 함수가 유일한 출처다.
화면에서 날짜를 다시 계산하지 않는다.

| 등록 기준 | 저장값 | 기간 | 기록이 붙는 날짜 |
|---|---|---|---|
| 일별 | `daily` | 그 날 하루 | 그 날짜 |
| 주차별 | `weekly` | 그 날짜가 속한 주 (월~일 · ISO) | **그 주 월요일** |
| 월별 | `monthly` | 그 날짜가 속한 달 | **그 달 1일** |
| 수시 | `adhoc` | — | 일일체크리스트에 나오지 않는다 |

- 🔑 **`weekday` · `monthday` 는 독립 항목에서 쓰지 않는다.** 「화요일에만」이 아니라
  「그 주 안에 한 번」이 기준이다. 값은 남아 있고 속성 모달에서 고칠 수 있지만 노출을 바꾸지 않는다
- 같은 기간 안에서는 **어느 날 눌러도 기록 1건**이다 (`unique(item_id, check_date)` + 정규화)
- `late`(지난 기간 미체크)는 `prevPeriodStart` 의 기록 유무로 본다
- 트리(프로세스 아래) 체크항목의 요일·일자 판정은 `isDueOn()` 에 남아 있다 —
  `setCheck` 의 가드가 쓸 뿐, 일일체크리스트 노출에는 관여하지 않는다
- 비활성(`active = false`) 항목과 삭제된 항목은 일일체크리스트에 나오지 않는다.
  업무프로세스 탭은 `includeInactive: true` 로 비활성까지 본다

### 테이블

| 테이블 | 주요 필드 |
|---|---|
| `checklist_items` | `category`(업무구분 이름 · 옛 컬럼. **독립 체크항목은 등록 탭의 `구분` 값**) `parent_id` `legacy_parent_id`(이행 전 부모 · 되돌리기용) **`kind`**(division/group/process/situation/check) `child_flow`(옛 모델 · **쓰지 않는다**) `title` `description` `cycle` `weekday` `monthday` `assignee_id` `assignee_name`(정담당자) **`sub_assignees`**(부담당자 `[{id,name}]` jsonb) `sort_order` `active` **`daily`**(일일체크리스트 포함) `deleted_at` |
| `checklist_checks` | `item_id` `check_date`(= 기간 시작일) `memo`(특이사항) `checked_by` `checked_by_name` **`checked_at`(nullable — 비어 있으면 특이사항만 적은 줄)** · **`unique(item_id, check_date)`** |
| **`checklist_edges`** | 업무 흐름 간선 — **단계 순서의 유일한 출처.** `group_id`(업무항목 = 흐름 경계) `from_id`(null = 흐름의 시작) `to_id` `label`(조건) `sort_order`(갈래 좌→우) `created_by` `created_at` · `unique(from_id, to_id)` + 시작 간선은 `to_id` 마다 하나 |
| **`checklist_notes`** | 단계 설명 표 — `item_id`(프로세스·업무항목·상황 모두 가능) `label`(구분) `content`(내용) `remark`(비고) `sort_order` `created_by` `created_by_name` `created_at` `updated_at` · ⚠️ 체크리스트에서 **유일한 하드 삭제** |

- 체크는 **항목·기간당 1건**이다 (`check_date` 는 기간 시작일로 정규화된다). 두 사람이 같이 눌러도 한 건만 남는다
- 상황 노드의 체크 기록 = 발생 기록. `memo` = 발생 내용
- `kind` 가 없는 옛 항목은 `db.js` 의 `normalize()` 와 스키마의 backfill 이
  **하위가 있으면 프로세스, 없으면 체크항목**으로 본다. 고정 구분 시절의 최상위 항목은
  스키마 마이그레이션이 `category` 별 업무항목(`ci_grp_<md5>`)을 만들어 그 아래로 옮기고,
  업무구분 도입 때는 최상위 업무항목마다 같은 이름의 업무구분(`ci_div_<md5>`)을 만들어 그 아래로 옮겼다
  (입고 › 입고 — 이름은 화면에서 고친다)
- 두 테이블 모두 Realtime 에 올라가 있어 다른 사람의 체크가 즉시 반영된다

## 보완 여지 (설계상 열어 둔 곳)

- **다른 견본** — `CHECK_TEMPLATES` 에 `출고` `반품` 을 더하면 「견본: 이름」 버튼이 저절로 생긴다
- **상황 아래 상황** — 허용하지 않는다(`CHECK_KIND_CHILDREN`). 필요하면 상수를 연다
- **상황 여러 번 발생** — 날짜당 1건이다. 건별 기록이 필요해지면 발생 기록을 별도 테이블로 뺀다
- **프로세스 간 조건 분기** (예: 냉장 입고면 ⑤ 대신 ⑤′) — 지금은 상황으로 표현한다
- **부분 합류 · 다른 업무항목으로의 합류** — 합류점이 늘 다음 형제라 표현할 수 없다.
  필요해지면 간선 테이블을 새로 들여야 하므로 그때 다시 설계한다

## 알려진 제약

- **인쇄에서 간선이 페이지 경계에 잘린다.** 카드와 상황 블록은 페이지 사이에서 잘리지 않게
  막아 두었지만, 카드를 잇는 선(SVG)은 페이지가 나뉘는 자리에서 끊겨 보인다. 도식은 A4 폭으로
  다시 배치해 찍으므로 가로로는 들어가지만, 갈래가 3개를 넘으면 레인이 최소폭(200px)으로 서도
  넘칠 수 있다
- **카드를 펼치면 아래가 통째로 밀린다.** 카드 높이를 재서 자리를 잡으므로 상세를 펼친 만큼

- **카드는 제목 한 줄이라 긴 이름은 잘린다** (`text-overflow`). 전체 이름은 펼치거나 ✎ 에서 본다
- **미체크 알림은 화면 안의 배지뿐이다.** 푸시·메일 알림은 서버가 필요해 넣지 않았다
- **주기가 겹치는 항목을 한 줄로 합치지 않는다.** 같은 일을 매일·매주 두 번 넣으면
  두 줄로 나온다 (등록할 때 정리한다)
