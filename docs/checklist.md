# 업무체크리스트

> 코드 `assets/js/pages/checklist.js`(웹 셸) · `assets/js/pages/checklist/*.js`(탭별 모듈) ·
> `assets/js/checkflow.js`(도식 좌표 · 순수 함수) ·
> `assets/js/mobile/screens/checklist.js`(앱 일일) ·
> `assets/js/mobile/screens/process.js`(앱 업무프로세스 · 보기 전용)
> 라우트 웹 `#/checklist` · 앱 `#/checklist` `#/process` · [공통 규약](common.md) · [CLAUDE.md](../CLAUDE.md)

담당자별 **업무 누락을 막고 담당을 분명히 하는** 화면.
사용자가 만든 **업무구분**(입고·출고·반품 …) 아래 **업무항목**(B2B출고·B2C출고 …)마다
**업무 흐름을 프로세스 순서대로** 등록하고, 프로세스마다 **체크항목**을 단다. 담당자는 날짜별로 체크항목을 중심으로 체크한다.
작업 중 **상황**(입고수량오류·제품틀림 등)이 생기면 그 자리에서 「발생」 처리해
대응 프로세스가 흐름 사이에 끼어든다.

공지사항이 *전체 대상 안내*, 이슈등록이 *개별 건의 문제 제기*라면,
업무체크리스트는 **반복 업무의 이행 확인**이다.

---

## 구조 🔑 — 트리 한 그루가 업무 흐름이다

항목(`checklist_items`)은 트리이고, 노드마다 **종류(`kind`)** 가 있다.

| 종류 | 저장값 | 역할 | 둘 수 있는 하위 |
|---|---|---|---|
| 업무구분 | `division` | **최상위 묶음.** 사용자가 「업무구분 추가」로 만든다 (입고·출고·반품 …). 이름은 겹칠 수 없다 | 업무항목 |
| 업무항목 | `group` | 업무구분 아래 흐름 한 벌 (B2B출고·B2C출고 …). 같은 업무구분 안에서 이름이 겹칠 수 없다. **복제**할 수 있고 다른 업무구분으로 **옮길** 수 있다 | 프로세스 · 체크항목(단독 업무) |
| 프로세스 | `process` | 업무 흐름의 한 단계. **형제 순서(`sort_order`)가 곧 업무 순서** | 체크항목 · 상황 · 하위 프로세스 |
| 상황 | `situation` | 그 단계에서 생길 수 있는 예외 상황. **발생 처리한 날짜에만** 하위가 끼어든다 | 대응 프로세스 · 체크항목 |
| 체크항목 | `check` | 담당자가 실제로 체크하는 항목. 주기·담당자를 가진다 | 없음 (말단) |

최상위에는 업무구분만 있다. 허용 관계는 `config.js` 의 `CHECK_KIND_CHILDREN` 이 유일한
출처이고, `db.createChecklistItem()` 이 거부한다. **종류는 수정으로 바꿀 수 없다** (지우고 다시 만든다).

### 순차 · 갈래 · 합류 (`child_flow`) 🔑

업무항목·프로세스는 **자기 하위 프로세스를 어떻게 이을지**를 가진다 (`config.js` 의 `CHECK_FLOW`).
부모에 붙는 값이고 **체크항목·상황에는 뜻이 없다.**

| 값 | 뜻 | 하위 프로세스 번호 | 도식 |
|---|---|---|---|
| `seq` (기본) | 순차 - 한 줄기로 차례대로 | ①②③ | 부모 → 첫 단계 → 다음 단계 로 이어지는 체인 |
| `fork` | 갈래 - 조건에 따라 한 갈래만 탄다 | **`4.1` `4.2`** (아래 번호 규칙) | 부모에서 갈래마다 따로 뻗는 부채꼴(파란 점선) |
| `join` | 갈래 + **합류** - 벌린 갈래들이 다시 한 단계로 모인다 | **`fork` 와 같다** | 부채꼴(파란 점선) + 갈래 말단들을 모으는 **합류 버스**(파란 실선) |

- 기본값이 `seq` 라 **예전 데이터는 지금까지와 똑같이 보인다**
- 갈래는 「냉장 입고 / 상온 입고」 처럼 **조건이 갈리는 단계**에 쓴다. 예외 상황(입고수량오류)은
  갈래가 아니라 **상황(situation)** 이다 — 갈래는 늘 있는 경로, 상황은 그날 생긴 일이다
- 갈래 아래 줄의 프로세스 캡션은 `③ 입고검수 › 4.1 냉장 › ① 냉장고 이동` 처럼 나온다
- 속성 모달의 **「하위 프로세스 연결」** 에서 고른다 (업무항목·프로세스 폼에만 있다)
- 🔑 **`isFork()` 는 `seq` 가 아닌 모든 값에 참이다.** `join` 도 벌리는 것은 갈래와 같고
  다른 것은 그린 뒤 다시 모으느냐뿐이라, 번호 규칙·채번·앱 표시가 그대로 상속된다.
  도식에서만 `isJoin()` 으로 갈라진다

#### 번호 규칙 🔑 — 갈래 줄이 **정수 슬롯 1칸**을 먹는다

갈래는 「부모 안의 하위」가 아니라 **다음 단계가 유형별로 쪼개진 것**이다. 그래서 형제 줄마다
슬롯 1,2,3… 을 매기되 **갈래 부모는 슬롯 2개를 쓴다** — 자기(N)와 갈래 줄(N+1).

| 상황 | 번호 |
|---|---|
| 순차 하위 | `①②③` (원문자) |
| 갈래 하위(`fork`·`join`) | `${N+1}.${k}` → `4.1` `4.2` (평문 + 파란 알약) |
| 갈래 부모의 다음 형제 | `N+2` — **합류점이든 아니든 같다**. `fork` ↔ `join` 을 토글해도 번호가 흔들리지 않는다 |
| 갈래 아래 순차 단계 | 다시 `①②③` (`4.1 국내 › ① 송장출력`) — 점은 한 겹만 |
| 갈래 안의 갈래 | 한 겹 더 `4.2.1` `4.2.2` |
| 업무항목·상황 자체가 갈래 | `1.1` `1.2` (앞자리가 없어 1 부터) |

```
B2B출고 (업무항목 · seq)
 ① 주문수신
 ② 피킹              ├ ① 피킹리스트 출력   └ ② 존별 피킹
 ③ WMS처리  child_flow=join
     ├ 4.1 국내 (seq)   ├ ① 국내송장 출력  └ ② 택배 인수증
     └ 4.2 해외 (fork)  ├ 4.2.1 항공      └ 4.2.2 해상
 ⑤ 출고완료          ← 합류점 = 3 + 2
 ⑥ 마감
```

캡션은 `③ WMS처리 › 4.2 해외 › 4.2.1 항공` · `4.1 국내 › ① 국내송장 출력` 처럼 읽힌다.
**원문자 = 한 줄기, 점 번호 = 갈래**라는 신호라 표기를 섞어 둔 것이다
(`common.js` 의 `circled()` 는 정수가 아니면 원문을 그대로 돌려준다).

- 🔑 **채번은 `checkflow.js` 의 순수 함수 `rowNos(children, {fork, base, isBranch})` 한 곳**이다
  (`forkBase(부모 번호)` 가 갈래 줄의 앞자리를 만든다). 좌표(`layoutFlow`)는 웹 도식 전용이지만
  **번호는 앱도 같은 것을 쓴다** — `pages/**` 와 `mobile/**` 가 공유하는 경계가 번호다
- 🔑 **불변식: `rowNos` 는 배열의 길이와 순서를 바꾸지 않는다.** 걸러내거나 섞지 않는다
- 🔑 **`no` 는 경로 캡션 전용이다** (`stepCaption` · 도식 뱃지 · 앱 캡션 2곳). 체크 대상 판정
  (`daily` · `isDueOn` · `passes` · `due`)과 집계는 번호를 보지 않는다. 그래서 그 날짜에 안 나오는
  단계가 있어도 번호가 흔들리지 않게 **걸러내기 전 원본 줄로 매긴다**
- 갈래 부모가 하위 프로세스를 아직 안 가졌으면 갈래 줄이 없으므로 슬롯도 1칸만 쓴다
  (`isBranch` 판정) — 하위를 넣는 순간 다음 형제가 `N+1` → `N+2` 로 밀린다
- **번호는 저장하지 않는다.** `sort_order` 로 정한 순서에서 그때그때 계산한다

#### 합류 (`join`) 🔑 — 모일 곳은 **언제나 다음 형제**

컬럼을 더하지 않았다. **트리 구조도 그대로다.** 합류점은 고르는 것이 아니라
합류 부모(`join`)의 **다음 형제**로 정해진다.

```
① 주문수신
② WMS처리   (child_flow = 'join')   ← 갈래 줄이 슬롯 3 을 먹는다
   ├ 3.1 국내
   └ 3.2 해외
④ 출고완료   ← ② 의 다음 형제 = 합류점 (2 + 2)
```

```
  ① 주문수신
      │
  ② WMS처리
   ┌──┴──┐            ← 갈래 버스 (파란 점선 · 틈 가운데)
 3.1 국내  3.2 해외
   └──┬──┘            ← 합류 버스 (파란 실선 · 틈 가운데)
  ④ 출고완료
```

- **합류선이 출발하는 곳은 `checkflow.js` 의 `tails(node)`** 가 정한다 (순수 함수 · 재귀).
  하위가 없으면 자기 자신, `seq` 면 마지막 하위의 말단, `fork`·`join` 이면 모든 하위의 말단이다.
  재귀라 **중첩 갈래**(국내 아래 또 갈래)도 규칙을 더하지 않고 풀리고, 말단이 여럿이면 선도 여럿이다.
  축을 모르는 트리 함수라 세로 전환에도 고치지 않고 그대로 쓴다
- **레이아웃은 y 만 민다.** 합류 노드는 **갈래 블록 전체 아래**(`앞 서브트리의 bottom + gapY`)에
  놓이고 열은 바깥 줄기 그대로다 - 다음 형제와 같은 규칙이라 합류 전용 보정이 없다.
  말단들은 각자 아래로 내려와 합류 노드 위 틈 가운데의 **가로 버스**에 모이고, 버스에서
  합류 노드로 화살촉 하나로 꽂힌다
- 🔑 **모일 곳을 사용자가 고르게 하지 않는다.** 간선 테이블·합류 전용 `kind`·부분 합류
  (일부 갈래만)·다른 업무항목으로의 합류는 모두 넣지 않기로 했다
- **다음 형제가 없으면** `fork` 와 똑같이 그리고, 카드 상세에 왜 안 모이는지를 적는다.
  두 경우를 **문구로 가른다** 🔑 — 마지막 형제라 모일 곳이 없으면 「**합류할 다음 단계가
  없습니다**」(주황 주의), **갈래로 벌린 줄 안**이면 「갈래 안이라 여기서는 모이지 않습니다」(회색 설명).
  갈래 줄은 형제끼리 이어지지 않아 **원래 모일 곳이 없는 것이 정상**인데, 다음 형제가 눈에
  보이는 탓에 주의 문구로 적으면 잘못 설정한 줄로 오해한다
- **업무항목(`group`)에는 「갈래 → 합류」 선택지를 주지 않는다** — 흐름의 맨 위라 모일 다음
  형제가 있을 수 없어, 고를 수 있으면 조용히 갈래로 동작한다 (`form.js` 의 `flowOpts`)
- 앱(`m.html#/process`)은 도식을 쓰지 않는다 — 갈래 블록 끝에
  `↩ 갈래가 다시 3. 출고완료 로 모입니다` 캡션 한 줄만 붙는다
`category` 컬럼은 최상위(업무구분) 이름을 담는 옛 컬럼이다 — 화면 로직은 쓰지 않고, 이름을
바꾸면 하위까지 함께 맞춘다.

```
입고 (업무구분)
 ├ 일반 입고 (업무항목)   ① 하차 파렛트수 확인 → ② 입고거래명세서 확인 → … 
 └ 반품 입고 (업무항목)   ① … 
출고 (업무구분)
 ├ B2B출고 (업무항목)
 └ B2C출고 (업무항목)    ← B2B출고를 「복제」한 뒤 다른 점만 고친다
```

입고 예시:

```
입고
 ① 하차 파렛트수 확인        ☐ 차량 도착 시각 기록  ☐ 하차 파렛트수 = 송장 대조
 ② 입고거래명세서 확인       ☐ 거래명세서 수령·품목 대조
     ⚠ 입고수량오류  ──발생──▶  ↳ 수량 차이 기록 → 화주 담당자 보고 → 명세서 정정본 수령
     ⚠ 제품 틀림     ──발생──▶  ↳ 오입고 제품 격리 → 반송 여부 확인
 ③ 입고검수                  ☐ LOT 확인  ☐ 유효기간 작성  ☐ 외관·파손 확인
 ④ 입고라벨 부착             ☐ 파렛트별 라벨 출력·부착
 ⑤ 입고적치                  ☐ 로케이션 지정·적치
 ⑥ WMS 입고처리              ☐ WMS 입고 확정
 ⑦ 실물 입고적치 검증        ☐ WMS 재고 = 실물 로케이션 대조
```

이 예시는 `config.js` 의 `CHECK_TEMPLATES` 에 견본으로 들어 있고, 업무프로세스 탭에서 업무구분을
고른 뒤 **「견본: 입고」** 버튼을 누르면 그 업무구분 아래에 같은 이름의 업무항목을 만들며 한 번에
등록한다(`db.seedChecklistTemplate`). 그 업무구분에 같은 이름의 업무항목이 이미 있으면 버튼이 사라진다.

### 체크 대상

**일일체크리스트에는 업무프로세스 탭에서 「일일」(`daily`)을 켠 항목만 나온다.** 🔑
켜지 않은 체크항목은 업무프로세스 보드에는 있지만 일일체크리스트에서는 빠진다 (참고용 절차).

| 노드 | 체크 대상인가 |
|---|---|
| 체크항목 (`daily` 켬) | ✅ (그 날짜에 주기가 맞을 때) |
| 체크항목·하위 프로세스가 없는 프로세스 (`daily` 켬) | ✅ 단계 자체를 체크한다 (`단계 완료`) — 상황만 달려 있어도 같다 |
| `daily` 를 끈 체크항목·프로세스 | ❌ 일일체크리스트에 나오지 않는다 |
| 체크항목이나 하위 프로세스가 있는 프로세스 | ❌ 하위 집계만 (`done / total`) |
| 상황 | ❌ 체크가 아니라 **발생 처리**다 (아래) |

### 상황 발생 🔑

- **별도 테이블이 없다.** 상황 노드에 그 날짜의 `checklist_checks` 기록이 있으면
  "그 날짜에 발생했다"는 뜻이고 `memo` 가 발생 내용이다
- 발생 처리하면 상황의 하위(대응 프로세스·체크항목)가 **그 날짜의 대상에 들어가고**
  집계(`total`)에 더해진다. 발생 안 된 상황은 프로세스 밑에 **「상황 발생 시」 후보 칩**으로만 보인다
- **발생 해제**하면 그 상황 아래 같은 날짜의 체크 기록도 함께 지운다
  (끼어들었던 단계가 통째로 빠진다). 화면은 확인 문구로 알린다
- 상위 상황이 발생 처리되지 않은 항목은 체크할 수 없다 (`db.setCheck` 가 거부)
- 상황은 **날짜당 1번**만 발생 처리된다 (unique). 같은 날 여러 건이면 발생 내용(memo)에 적는다

### 담당자 — 정 1명 + 부 여러 명 🔑

노드마다 **정담당자**(`assignee_id` · `assignee_name`) 1명과 **부담당자**(`sub_assignees` ·
`[{id, name}]`) 여러 명을 둘 수 있다. 속성 모달에서 정담당자는 선택 하나, 부담당자는
「+ 부담당자 추가」 로 줄을 늘려 고른다. 정담당자와 같은 사람·중복은 저장할 때 빠진다.

- **체크 권한은 정·부가 같다.** 부담당자도 정담당자 대신 체크·상황 발생 처리를 할 수 있다
- 일일체크리스트의 담당자 필터(`나` · 특정 담당자)는 정·부 어느 쪽이든 그 사람이면 보여 준다
- 담당 칸에는 정담당자 이름이 크게, 부담당자는 아래 작은 글씨 「부 이담당, 박용마」 로 붙는다

### 담당자 상속 🔑

체크항목의 담당자(정·부 모두)를 비우면 **가장 가까운 상위(프로세스 → 업무항목 → 업무구분)의
담당자 묶음(정 + 부)** 을 따른다. 끝까지 없으면 공통 업무(누구나 체크)다. 프로세스·업무항목·업무구분에
담당자를 한 번만 적으면 그 아래가 모두 그 팀 일이 된다. 정·부는 한 묶음이라 상위에 정만 있으면 부도
비어 있는 채로 내려온다 (부만 따로 상속하지 않는다).

```
db.js   effectiveAssignee(item)   →  rows 의 assignee_eff_id / assignee_eff_name / assignee_eff_subs
서버    checklist_can_check(item) →  checklist_checks RLS 가 이 값으로 판정 (관리자 · 공통 · 정 · 부)
```

| 요소 | 동작 |
|---|---|
| 날짜 이동 | `◀` `▶` 로 하루씩, 날짜칸 직접 선택, `오늘` 버튼 |
| `일일 \| 전체` 🔑 | 기본 `일일` — 그 날짜에 해야 하는 항목만. `전체` 면 **등록된 확인내용 전부**가 나오고, 그 날짜의 대상이 아닌 줄은 「대상 아님」 꼬리표 + 회색 **조회 전용**이다. 주기 밖 날짜에 체크 기록이 들어가면 `late`(어제 미체크)·`checklistSummary` 집계가 어긋나므로 체크박스를 잠근다. 현장이 매일 보는 화면이라 **기본값은 바꾸지 않는다** |
| `전체` 의 상황(situation) | 🔑 **`전체` 화면에서는 상황 발생 처리를 할 수 없다** (의도된 동작). 발생하지 않은 상황 아래 줄은 「대상 아님」 으로 잠긴 채 보이기만 하고, 발생 처리는 `일일` 세그먼트에서 한다 — 전체 목록은 **무엇이 등록돼 있는지 훑어보는 화면**이고, 그 날의 상황을 여는 것은 그 날짜를 보고 있는 일일 화면의 일이다 (`catalogTable` 은 `situations: []` 고정) |
| 담당자 | 기본 `나`(본인 담당 + 공통 업무). **`manageChecklist` 권한자만** `전체`·특정 담당자를 고를 수 있다. 상속 담당자로 거른다 |
| `미완료 \| 전체` | 기본 `미완료` — 완료 줄은 업무항목마다 「▸ 완료 N건 보기」 로 접힌다. `전체` 면 완료 줄도 자리에 펼친다 |
| 진행 | `남은 N · done / total` 과 막대. 100% 면 초록 |
| `상황 발생 N건` | 그 날짜에 발생 처리된 상황 수 (주황 배지) |
| `어제 미체크 N건 →` | 전날 미체크가 있을 때만 나오고, 누르면 **전날로 이동**한다 |
| **줄 안 「어제 미체크」 꼬리표** | 전날에도 대상이었는데 체크하지 않은 항목(수시 제외)에 붉은 꼬리표가 붙는다 (`row.late`) |
| 체크박스 | 켜면 기록 생성, 끄면 기록 삭제. 제목을 눌러도 된다. 체크한 **시각·사람**이 오른쪽에 남는다 |
| 프로세스 캡션 | 줄 아래 작은 글씨 `① 프로세스 › ⚠ 상황 › ① 대응 프로세스 · 주기`. 상황 아래 줄은 옅은 주황 바탕 |
| 메모 | 체크한 항목에만 남길 수 있다. 메모가 있으면 아이콘이 파랗게 표시된다 |
| 상황 칩 (발생 전) | 프로세스의 마지막 줄 뒤 「⚠ 상황」 줄. 점선 칩 + 「발생」. 누르면 발생 내용을 묻고 발생 처리한다. 권한 없으면 비활성 |
| 상황 칩 (발생) | 주황 실선. 발생 시각·사람·내용. `메모` 로 내용 수정, `✕` 로 발생 해제(확인 문구). 발생하면 대응 항목이 아래 줄로 끼어든다 |

- 줄 순서 = 업무 순서(업무구분 → 업무항목 → 프로세스 구간). 그 안에서 미완료가 먼저다
- 업무항목에 바로 둔 체크항목은 캡션 「단독 업무」 로 그 업무항목 마지막에 나온다
- 체크 권한이 없는 항목은 회색 + 체크박스 비활성 상태로 **조회만** 된다
- 화면은 `db.checklistTable(date, f)` 의 `divisions` 를 그대로 그린다. 날짜·주기·상속·지연 계산을 하지 않는다

- **읽는 규칙** 🔑: **아래로 = 다음 단계 · 오른쪽으로 벌어짐 = 갈래 · 들여쓰기 = 순차 하위**.
  카드 하나가 프로세스 한 단계이고 안에 체크항목이 줄로 놓인다. 형제 단계는 위에서 아래로
  이어지고, **잇는 선이 순차인지 갈래인지를 말해 준다** — 순차(`seq`)는 회색 실선, 갈래(`fork`)는
  부모 아래 **가로 버스**에서 갈래마다 내려가는 **파란 점선**이다.
  하위 프로세스는 **아래에 놓인 별도 카드**로 나온다 (카드 안에 넣지 않는다)
- 🔑 **줄기(main spine)는 왼쪽 첫 열에 고정한다.** 갈래 부모를 갈래 블록 가운데로 맞추면
  줄기가 지그재그로 흔들려 세로 스캔이 깨진다. 순차 하위는 **같은 열에서 24px 들여쓰고**
  (2단계 48px 에서 멈춘다) 왼쪽 레일(회색 세로선)로 「같은 줄기의 하위」임을 알린다
- **합류(`join`)** 는 갈래 말단들이 합류 노드 위 **가로 버스**(파란 실선)에 모여 화살촉 하나로
  꽂힌다. 합류 노드는 갈래 블록 **전체 아래**에 놓이고 열은 바깥 줄기 그대로다.
  카드를 펼치면 「↩ 갈래가 다시 ④ 출고완료 로 모입니다」 가 보인다
- 🔑 **다시 모이지 않는 갈래(`fork` 만)** 뒤에도 다음 형제는 온다. 이때는 말단을 끌어오지 않고
  **다음 형제로 내려가는 회색 선 하나**만 그린다 (`checkflow.blockNextEdge`).
  합류(말단 여럿 → 버스 → 화살촉 1개)와 생김새가 달라야 「다시 모인다 / 안 모인다」 가 구분된다.
  출발은 **부모와 같은 열에서 가장 아래 카드의 바닥**(`colTail`)이다 — 갈래 첫 하위는 언제나
  부모와 같은 열이라 이 열에는 카드가 반드시 있고, 그 아래로는 같은 열에 카드가 없다.
  ⚠️ **부모 카드에서 곧장 내리면 안 된다** — 갈래 첫 카드를 관통해 「부모 → 갈래 첫 카드 →
  다음 형제」 로 잘못 읽힌다 (선 SVG 가 카드 뒤에 깔려 겹친 자리가 눈에 띄지도 않는다).
  ⚠️ **서브트리 바닥(`bottomOf`)에서 출발해서도 안 된다** — 바닥 카드가 다른 열(갈래로 벌어진
  쪽)이면 부모 열의 그 높이에는 아무것도 없어 **선이 허공에서 시작한다**
- **치수** — `gapY 56` · `gapX 56` · 들여쓰기 `24`(2단계 `48` 에서 캡) · 레인 폭 `200~260` 가변.
  레인 폭은 **열 수에 맞춰 정한다** (`checkflow.laneWidth`) — 열이 화면에 들어오면 꽉 채우고,
  안 들어오면 200px 에서 멈추고 가로 스크롤한다. 갈래 수에 따라 폭을 다르게 주지 않는다.
  🔑 **`gapX` 는 들여쓰기 상한보다 넓어야 한다** — 카드 폭은 들여쓰기와 상관없이 레인 폭
  그대로라 2단 들여쓴 카드가 열 밖으로 `48px` 삐져나오기 때문이다. 두 상수를 따로 두었다가
  `gapX 40` < 들여쓰기 `48` 이 되어 옆 열 카드와 8px 겹친 적이 있다. 지금은
  `checkflow.colGap()` 이 `max(gapX, 들여쓰기*2 + 8)` 로 **간격을 코드에서 보장하고**,
  레인 폭 계산과 좌표 계산이 그 한 값을 같이 쓴다. 🔑 치수를 바꿔 부를 때는
  `laneWidth(폭, 열수, opts)` 에 **`layoutFlow` 와 같은 `gapX`·들여쓰기를 넘긴다** —
  둘이 다른 간격을 쓰면 카드가 계산한 자리에서 밀려 선이 카드에서 떨어진다
- 상황이 달린 단계는 카드 안에 **주황 블록**(「X 발생 시」 → 대응 체크항목 · 대응 단계 ①→②→③)이
  붙는다. **상황은 도식 노드가 아니다** — 늘 있는 경로가 아니라 그날 생긴 일이라 카드 안에 둔다.
  상황 아래 대응 프로세스도 블록 안 작은 사슬(`pm-chain`)이다
- **선만 SVG 다.** 카드는 지금까지의 HTML 그대로라 드래그 정렬·접힘·✎ 모달이 모두 살아 있다.
  좌표는 순수 함수 `checkflow.js` 의 `layoutFlow()` 가 계산한다 — 카드 높이는 접힘·체크항목 수로
  달라져 계산식이 없으므로 **먼저 붙여 재고(1-pass) 그 값으로 자리를 잡는다(2-pass)**
- 🔑 **순서가 있다**: 열 수(`flowCols`)는 측정 없이 셀 수 있으므로 → 레인 폭(`laneWidth`)을 정해
  `--pm-lane` 으로 내려주고 → **그다음에** 높이를 잰다. 어기면 다른 폭으로 줄바꿈된 높이를 쓰게 되어
  선이 카드에서 떨어진다. 레인 폭의 유일한 출처는 `checkflow.js` 이고 CSS 는 변수만 읽는다
- **다시 배치하는 때** — 창 리사이즈(디바운스 1회) · 우측 구역 **드래그 종료 시 1회**(끄는 동안
  매 프레임은 하지 않는다 · 높이를 다시 재는 일이라 무겁다) · 서랍 여닫기 · 세그먼트 전환
  (뒤 둘은 화면을 통째로 다시 그리므로 저절로 따라온다). 창 리사이즈 구독은 화면을 떠날 때 끊는다
  (`disposeManage()` — `checklist.js` 의 정리 함수가 부른다)

#### 선이 엉키지 않는 근거 (세로판) 🔑

이 일곱 가지를 깨는 변경은 하지 않는다.

| | 불변식 |
|---|---|
| **V1** | **진행축 단조** — 모든 카드는 `y = 부모.bottom + gapY` 또는 `앞 서브트리.bottom + gapY` 로만 놓인다. 모든 간선은 y 가 늘어나는 방향뿐이다 |
| **V2** | **열 독점** — 갈래 형제 `k` 의 열 구간 `[c, c+cols(k))` 는 서로소다. 들여쓴 카드까지 포함해 **x 대역이 겹치지 않는다** (`colGap()` 이 `gapX > 들여쓰기 상한` 을 강제한다) |
| **V3** | **순차 줄 단일 열** — 순차 형제·하위는 같은 열에 있고 y 대역이 서로소다 |
| **V4** | **버스는 gap 안에만** — 버스의 y 는 언제나 카드 bottom 과 다음 카드 top 사이다 |
| **V5** | **두 버스는 같은 gap 을 쓰지 않는다** — 사이에 최소 카드 1개(갈래 카드)가 있다 |
| **V6** | **x 는 이산값** — 모든 x 는 `colX(정수) + 들여쓰기(0·24·48)` 다 |
| **V7** | **간선 부착** — 모든 간선은 **카드 경계**(출발=바닥 · 도착=천장)나 **버스 접점**(앞 간선이 끝난 점)에서 시작·끝난다. 허공에서 시작하는 선은 없다 |

- 형제 사슬은 **앞 서브트리의 끝 카드**(`spineTail`)에서 출발한다 — 부모 카드에서 곧장 내리면
  사이에 있는 순차 하위 카드들을 지나간다. 🔑 **끝 카드가 없을 때**(앞 형제가 갈래거나,
  순차인데 **마지막 하위가 갈래**라 끝이 여럿일 때)는 부모로 되돌아가지 말고
  합류면 `joinEdges`, 아니면 `blockNextEdge` 로 잇는다. `blockNextEdge` 는 **같은 열의
  가장 아래 카드 바닥**(`colTail`)에서 출발한다 — 다음 형제는 `bottomOf + gapY` 에 놓이고
  출발 카드 아래로는 이 열에 카드가 없으므로 선은 틈 안에만 있다 (V7)
- 🔑 **「선이 허공에서 시작한」 결함(F1)은 이 한 간선만 규칙에서 벗어나 있었기 때문이다** —
  다른 간선은 모두 카드 바닥에서 출발하는데 `blockNextEdge` 만 **서브트리 바닥**이라는 다른
  기준을 썼고(바닥 카드가 다른 열이면 부모 열에는 아무것도 없다), 검사기가 그 규칙(V7)을
  모르니 통과했다. **간선 규칙은 하나로 통일하고 그 규칙을 검사기에 넣는다**
- 🔑 **이 일곱 가지는 손으로 만든 예시로 확인되지 않는다.** 실제로 카드 겹침(V2)과 간선
  관통(V1·V4), 간선 미부착(V7)을 예시 트리로는 못 잡고 넘어간 적이 있다. 배치 코드를 건드리면
  **`npm run check:flow`** (= `node tools/checkflow-check.js [트리수] [시드]`) 로 랜덤 트리
  수천 그루를 돌려 `P1`~`P10` 이 모두 0건인지 본다.

  | | 보는 것 |
  |---|---|
  | P1~P3 | 카드 쌍 교차 · 간선의 카드 관통 · 간선 y 단조 |
  | P4~P6 | 갈래 x 대역 서로소 · x 이산값 · 치수(width/height·레인 폭) 일치 |
  | P7 | 노드/간선 **개수** |
  | **P8** | **간선 부착**(V7) — 양 끝이 카드 경계이거나 버스 접점이다. 경로는 `M·V·H` 만 쓴다 (**모르는 명령은 실패** — 예전에는 `C`·`l` 을 조용히 `H` 로 읽어 통과했다) |
  | **P9** | **화살촉** — 카드에 닿는 간선만 갖고, 꼭짓점이 도착점과 같고 모양이 규격이다 |
  | **P10** | **연결 상대** — 어느 카드에서 어느 카드로 가는지가 트리와 맞는다 (개수만 세는 P7 로는 오배선이 안 잡힌다) |

  치수는 **5조합**(`gapX`·`gapY`·들여쓰기)을 돌려가며 넣는다 — 기본값으로만 돌리면
  `colGap()` 파생(들여쓰기가 `gapX` 보다 큰 경우)이 검사되지 않는다.
  `layoutFlow` 가 순수 함수라 브라우저 없이 돌아가고, 테스트 러너를 들이지 않으려고
  의존성 없는 스크립트 하나로 두었다
- 🔑 **검사기를 믿기 전에 검사기를 검증한다.** 배치 코드에 일부러 결함을 넣어(곡선 명령 ·
  화살촉 규격·위치 · 부모에서 곧장 내리기 · 부모→첫 하위 간선을 둘째에 붙이기) 해당 항목이
  올라오는지 보고 나서 「0건」 을 신뢰한다
- **가운데에서 프로세스 카드를 누르면** 그 단계가 파랗게 표시되고 **우측 표의 해당 구간으로 옮겨 준다**
- **접힘 / 펼침** 🔑: 카드는 기본으로 **핵심만** 보인다 — 순번 · 프로세스명 · 체크항목 이름 · 「X 발생 시」.
  설명문구는 넣지 않는다. **카드 머리(또는 상황 머리)를 누르면** 그 카드의 상세가 펼쳐진다 — 설명 ·
  담당(정·부) · 체크항목의 설명·주기·담당·「일일 제외」 · 「체크항목 없음 · 단계 자체를 체크」 ·
  「처리가 끝나면 ③ 다음 단계 로 이어집니다」. 펼침 상태(`state.open`)는 다른 화면에 다녀와도 유지되고,
  인쇄할 때는 모두 펼친 뒤 찍고 원래대로 돌린다. 버튼·토글·손잡이를 누른 것은 펼침으로 치지 않는다
- **왼쪽 트리** (`pm-nav`): 업무구분(굵게, 업무항목 수) › 업무항목(들여쓰기). 누르면 오른쪽 흐름이 바뀐다.
  편집 모드에서 업무구분 옆 `✎`, 업무항목 목록 끝 「+ 업무항목」, 트리 머리 「+ 업무구분」.
  업무구분이 없는 옛 업무항목은 「미분류」 로 마지막에 붙는다 (수정 폼에서 업무구분을 고르면 옮겨진다)
- **머리** (`pm-head`): `업무구분 › 업무항목` · 설명 · 담당. 편집 모드에서 `✎`(수정) 「복제」. 오른쪽에
  견본(`CHECK_TEMPLATES`, 그 업무구분에 같은 이름이 없을 때만) · 「편집 / 편집 끝」 · 「인쇄」 ·
  좁은 화면용 「체크리스트」 버튼 / `구성 | 흐름 | 체크리스트` 세그먼트
- **우측 체크리스트 표** (`pm-side`) 🔑: 왼쪽에서 고른 **업무항목 하나**의 체크항목 전부를
  `프로세스 · 체크리스트 · 담당자` 세 칸으로 편다. **새 데이터가 아니라 `kind='check'` 노드의 표
  편집기**다 — 이름은 칸에서 바로 고치고(포커스를 벗어나면 저장), 담당자는 고르면 저장된다
  (`db.createChecklistItem` · `db.updateChecklistItem` — 전용 함수를 따로 두지 않는다).
  체크항목이 아직 없는 프로세스도 「아직 없습니다」 줄로 표에 남아 어디가 비었는지 보인다.
- 🔑 **추가는 표 아래 폼 하나에서 한다** (`pm-side__add`) — **어느 프로세스에 달지 고른 뒤**
  이름을 넣고 Enter 또는 「추가」. 구간마다 입력칸을 두던 방식을 대신한다(표가 길어지고 어느 칸이
  어느 단계인지 헷갈렸다). 고른 프로세스는 `state.pick` 에 담기므로 **중앙 도식의 파란 강조와 같이
  움직이고**, 실시간 갱신으로 다시 그려도 선택이 풀리지 않는다. 가운데에서 카드를 누르면 그 단계가
  폼에 잡히므로 **도식에서 고르고 → 표 아래에서 적는** 흐름이 된다.
  「단독 업무」 를 고르면 업무항목 직속 체크항목이 된다.
  주기·부담당자·삭제는 줄 끝 `✎`(속성 모달)로 한다. **이 표의 `✎` 는 편집 모드와 상관없이 늘 보인다**
- **너비 조절** 🔑: 우측 구역 **왼쪽 경계를 끌면** 너비가 바뀐다 (손잡이에 초점을 두고 `←` `→` 로도
  16px 씩). 값은 `--pm-side-w` CSS 변수로 들어가고 `state.sideW` 에 남아 **다른 화면에 다녀와도
  유지된다**(새로고침하면 320px 로 돌아온다 — 화면 코드에 localStorage 를 쓰지 않는다).
  범위는 240~640px 이되 **가운데 도식이 쓸모를 잃지 않도록** `전체폭 − 좌측 230 − 도식 최소 420`
  으로 한 번 더 자른다 (`SIDE_W`). 서랍으로 접힌 뒤에는 끌 경계가 없어 손잡이를 숨기지만,
  정해 둔 너비는 서랍 폭에도 그대로 쓴다.
  포인터를 손잡이에 가둬(`setPointerCapture`) **window 리스너를 남기지 않는다**
- **반응형**: 1280px 이하면 **우측부터 접어** 「체크리스트」 버튼으로 여는 서랍이 되고,
  1024px 이하면 `구성 | 흐름 | 체크리스트` 세그먼트로 한 칸씩 본다
- **편집 모드**: 「편집」 을 켜야 도구(`pm-tools`)가 보인다. 도구는 노드마다 셋뿐이다 —
  | 도구 | 하는 일 |
  |---|---|
  | `≡` 손잡이 | **끌어서 순서 바꾸기.** 같은 상위·같은 종류(프로세스끼리, 체크항목끼리, 상황끼리) 사이에서만 놓인다. 손잡이를 잡아야 끌리므로 입력칸 글자 선택과 부딪히지 않는다 (`db.reorderChecklistItems`) |
  | `✎` | **속성 모달** — 이름·설명·담당자·주기·하위 연결(순차/갈래)·일일 포함·활성. 아래에 「삭제」 와 순서 `↑` `↓`(드래그 대신) |
  | `[일일]` 토글 | 체크항목(잎 프로세스는 카드 머리)의 일일체크리스트 포함 여부 (`daily`). 편집 모드가 아니면 꺼진 항목에 「일일 제외」 꼬리표만 보인다 |
  **추가는 「+ 체크항목」 「+ 상황」 「+ 하위 프로세스」 (상황 안에서는 「+ 대응 프로세스」, 흐름 끝에서는
  「+ 다음 프로세스」 「+ 단독 체크항목」) — 누르면 그 자리에 이름 입력칸이 열리고 Enter 로 바로 등록된다.**
  등록 뒤에도 입력칸이 열린 채라 연달아 넣을 수 있다 (Esc 또는 ✕ 로 닫는다). 담당자·주기 같은 나머지는
  기본값(상위 담당 따름 · 매일 · 체크항목은 일일 포함)이며 필요하면 `✎` 로 고친다.
  업무구분·업무항목 추가는 모달 폼으로 한다 (업무구분 선택이 필요해서)
- **인쇄**: 업무항목 하나를 매뉴얼로 인쇄한다(`window.print`). 사이드바·탭·왼쪽 트리·도구를 숨긴다
  (`body.cl-printing` + `@media print`). 상세를 모두 펼친 뒤 **가용폭을 A4 기준(≈680px)으로 넣어
  다시 배치**하고 찍는다 — 순차만 있는 업무항목은 열이 1개라 여유롭게 들어간다.
  카드와 상황 블록은 페이지 사이에서 잘리지 않는다
- **복제**(`db.duplicateChecklistGroup`): 프로세스·상황·체크항목·포함 여부까지 통째로 복사해 같은 업무구분
  맨 뒤에 「이름 복사」로 만든다. 체크 기록은 복사하지 않는다. B2B출고 → B2C출고처럼 비슷한 흐름을 짤 때 쓴다
- 실시간 갱신은 모달이 열려 있거나 빠른 추가 입력칸이 있는 동안 멈춘다 (입력하던 값이 사라지지 않게)

| 종류 | 폼 필드 (속성 모달) |
|---|---|
| 업무구분 | 이름(전체에서 겹치면 거부) · 설명 · 정담당자 · 부담당자(여러 명) · 활성 |
| 업무항목 | 이름(같은 업무구분 안에서 겹치면 거부) · **업무구분**(바꾸면 옮겨진다) · 설명 · **하위 프로세스 연결(순차/갈래)** · 정담당자 · 부담당자 · 활성 |
| 프로세스 | 프로세스명 · 설명 · **하위 프로세스 연결(순차/갈래)** · 정담당자 · 부담당자(하위가 따른다) · 일일체크리스트 포함(잎 프로세스일 때만 뜻이 있다) · 활성 |
| 상황 | 상황명 · 어떤 때인지(대응 요령) · 정담당자 · 부담당자 · 활성 |
| 체크항목 | 항목명 · 설명 · 주기(+요일/일자) · 정담당자 · 부담당자(모두 비우면 상위 담당 따름) · **일일체크리스트 포함** · 활성 |

- 부담당자 줄은 「+ 부담당자 추가」 로 늘리고 ✕ 로 뺀다. 「선택」 인 채 둔 줄은 저장할 때 무시된다

- 삭제는 **하위 항목까지 함께** 지운다(확인 문구로 개수를 알린다). 체크 기록을 남기려고
  행을 지우지 않고 `deleted_at` 만 찍는다(soft delete)
- 비활성 항목은 업무프로세스 탭에서만 흐리게 보이고 일일체크리스트에는 나오지 않는다

## 화면 구성 (앱)

### `#/checklist` 일일체크리스트 — 상단바 메뉴

웹의 목록을 **한 열**로 편 것이다. 업무구분은 굵은 머리, 업무항목은 소제목, 그 아래 체크 줄.
미완료가 먼저이고 완료 줄은 「▸ 완료 N건 보기」 로 접힌다(업무항목마다).

```
입고  1 / 8                                 ← 업무구분 머리
일반 입고  1 / 8                            ← 업무항목 소제목
☐ 하차 파렛트수 = 송장 대조  [어제 미체크]
  ① 하차 파렛트수 확인 · 일 · 김현장
☐ 거래명세서 수령·품목 대조
  ② 입고거래명세서 확인 · 일 · 김현장
  [⚠ 입고수량오류 발생 · 3박스 부족 ···] [⚠ 제품 틀림 ·발생·]
☐ 품목별 차이 수량 사진 촬영
  ② 입고거래명세서 확인 › ⚠ 입고수량오류 › ① 수량 차이 기록 · 일
▸ 완료 3건 보기
```

- 날짜 이동(`◀ 날짜 ▶ 오늘`) · **`일일 | 전체` 세그먼트**(웹과 같다 — 전체에서 그 날짜의 대상이
  아닌 줄은 「대상 아님」 + 눌리지 않는다) · 큰 진행 카운터(아래 한 줄에
  `남은 항목 N개 · 상황 발생 N건`) · `어제 미체크 N건 보기` 버튼(전날로 이동)
- 체크 줄 전체가 터치 영역(48px 이상)이라 장갑을 낀 채 눌러도 빗나가지 않는다
- 담당자 필터가 없다 — **로그인 사용자 본인 담당(상속 포함) + 공통 항목만** 본다
- 상황 칩: 발생 전은 점선 「발생」 → **시트**에 어떤 때인지·대응 절차가 보이고 발생 내용을 적어 「발생 처리」.
  발생한 칩(주황 실선)을 누르면 시트에서 내용 수정 · 「발생 해제」(빨간 버튼)
- 메모는 체크한 항목의 메모 아이콘을 눌러 시트에서 입력한다

### `#/process` 업무프로세스 — 상단바 메뉴 · 보기 전용

현장에서 매뉴얼을 펼쳐 보는 화면이다. 업무구분·업무항목 세그먼트로 고르면 그 흐름을 **세로 스테퍼**로
그린다 — 시작 → 프로세스 박스(체크항목 목록 포함) → 박스 아래 주황 블록 `⚠ 상황명 발생 시`
(어떤 때인지 · 대응 체크항목 · 대응 단계 1→2→3 · `↩ 처리 후 3. 다음 단계 로 이어감`) → … → 완료.
하위 프로세스는 박스 안 작은 사슬. **앱은 좌우 도식을 쓰지 않는다** — 좁아서 읽기 어렵다.
**갈래(`fork`)는 `4.1 국내` 머리가 붙은 하위 스테퍼**(파란 점선 레일)로 편다 — 번호는 머리에만
적고 동글은 가운뎃점이라 좁은 화면에서 줄이 길어지지 않는다.
**합류(`join`)도 앱에서는 도식으로 그리지 않는다** — 갈래 블록 끝에
`↩ 갈래가 다시 ④ 출고완료 로 모입니다` 캡션 한 줄만 붙는다.
앱도 번호는 웹과 같은 `checkflow.rowNos` 로 매긴다 (좌표만 웹 전용이다).
편집은 웹에서만 한다. 비활성 업무구분·업무항목·항목은 나오지 않는다.

## 데이터 (`db.js`)

주기 판정·담당자 상속·상황 발생·권한 판정은 **`db.js` 한 곳**에만 있다. 화면은 결과만 그린다.

| `canManageChecklist(user)` `canCheckItem(user, item)` | 권한 판정 (웹·앱 공용). 체크는 정·부 담당자 본인, 공통 업무, 관리 권한자 |

### `dailyTable` 뷰모델

```
{ date, done, total, raised,
  divisions: [ { item, name, done, total, groups: [Group] } ],   // 업무구분 순서
  groups:    [Group] }                                            // 평평하게 (집계·호환)
Group   = { item, name, division, done, total, sections: [Section] }
Section = { key, path: [{title, no, sit}], sit: item|null, rows: Row[](+late,+due), situations: SituationVM[] }
  path        프로세스 경로 (하위·대응 프로세스는 상위부터, 상황 아래면 상황명도 든다)
              🔑 `no` 는 순차면 정수(①②③), **갈래 줄이면 `'4.1'` 꼴 문자열**이다 (번호 규칙 절 참고).
              상황 노드만 `no: null` 이다
  sit         이 구간이 발생한 상황 아래면 그 상황 (화면이 주황으로 표시)
  rows        그 구간에서 체크할 항목 (단계 자체 체크 포함). `due` 는 그 날짜의 대상인지
  situations  그 프로세스에 직접 달린 상황 (발생 전 후보 + 발생한 것)
```

구간 순서 = 업무 순서. 발생 안 된 상황의 하위 구간은 나오지 않는다.
`dailyTable` 의 줄은 모두 `due: true` 다. `checklistTable(date, {scope:'all'})` 만 `due: false`
(그 날짜의 대상이 아닌 줄)를 함께 준다 — 화면이 회색 조회 전용으로 그린다.

### `dailyFlow` 뷰모델

```
{ date, done, total, raised, groups: [
    { item, name, done, total, loose: Row[],      // loose = 업무항목에 바로 둔 단독 체크항목
      processes: [ProcessVM] } ] }
ProcessVM   = { item, no, done, total, rows: Row[], subs: ProcessVM[],
                situations: SituationVM[], self: Row|null }   // self = 하위 없는 단계 자체
SituationVM = { item(+assignee_eff_*), active: check|null, rows: Row[], subs: ProcessVM[], done, total }
Row         = 항목 + { path, check, assignee_eff_id, assignee_eff_name, process_id }
```

- 담당자 필터는 **상속 담당자**로 거른다. 담당자가 없는 **공통 업무는 누구의 목록에나 든다.**
  내 일이 하나도 없는 프로세스·상황은 나오지 않는다
- 발생 안 된 상황은 `active: null` 이고 `done/total` 이 0 이다 (후보 칩용)
- 웹 업무프로세스 탭은 이 뷰모델이 아니라 트리(`checklistTree`)를 같은 모양으로 바꿔 흐름을 그린다

### 주기 판정 🔑

`dailyFlow()` 안의 `isDueOn()` 이 유일한 출처다. 화면에서 날짜를 다시 계산하지 않는다.
**주기는 체크항목에만 있다.** 프로세스·상황은 `daily` 로 저장되고 화면에 보이지 않는다.

| 주기 | 저장값 | 나오는 날 |
|---|---|---|
| 일 | `daily` | 매일 |
| 주 | `weekly` + `weekday`(0=일 ~ 6=토) | 지정 요일 |
| 월 | `monthly` + `monthday`(1~31) | 지정 일자. **말일 보정** — `31` 이면 그 달 말일(2월은 28·29일) |
| 수시 | `adhoc` | 날짜와 무관하게 항상 |

- **수시는 `어제 미체크` 집계에서 뺀다.** 날짜 개념이 없어 "밀렸다"고 볼 수 없다
- 비활성(`active = false`) 항목과 삭제된 항목은 일일체크리스트에 나오지 않는다.
  업무프로세스 탭은 `includeInactive: true` 로 비활성까지 본다

### 테이블

| 테이블 | 주요 필드 |
|---|---|
| `checklist_items` | `category`(업무구분 이름 · 옛 컬럼) `parent_id` **`kind`**(division/group/process/situation/check) **`child_flow`**(seq/fork/join · 기본 seq) `title` `description` `cycle` `weekday` `monthday` `assignee_id` `assignee_name`(정담당자) **`sub_assignees`**(부담당자 `[{id,name}]` jsonb) `sort_order` `active` **`daily`**(일일체크리스트 포함) `deleted_at` |
| `checklist_checks` | `item_id` `check_date` `memo` `checked_by` `checked_by_name` `checked_at` · **`unique(item_id, check_date)`** |

- 체크는 **항목·날짜당 1건**이다. 두 사람이 같이 눌러도 한 건만 남는다
- 상황 노드의 체크 기록 = 발생 기록. `memo` = 발생 내용
- `kind` 가 없는 옛 항목은 `db.js` 의 `normalize()` 와 스키마의 backfill 이
  **하위가 있으면 프로세스, 없으면 체크항목**으로 본다. 고정 구분 시절의 최상위 항목은
  스키마 마이그레이션이 `category` 별 업무항목(`ci_grp_<md5>`)을 만들어 그 아래로 옮기고,
  업무구분 도입 때는 최상위 업무항목마다 같은 이름의 업무구분(`ci_div_<md5>`)을 만들어 그 아래로 옮겼다
  (입고 › 입고 — 이름은 화면에서 고친다)
- 두 테이블 모두 Realtime 에 올라가 있어 다른 사람의 체크가 즉시 반영된다

## 상수 (`config.js`)

| 상수 | 값 |
|---|---|
| `CHECK_KIND` / `CHECK_KINDS` | `division` `group` `process` `situation` `check` (저장값) / 표시 문구 `업무구분` `업무항목` `프로세스` `상황` `체크항목` |
| `CHECK_KIND_CHILDREN` | 종류별 허용 하위 종류. `root` 키는 최상위(업무구분만) |
| `CHECK_FLOW` / `CHECK_FLOWS` | `seq` `fork` `join` (저장값 · `child_flow`) / 표시 문구 `순차 ①②③` `갈래 (조건 분기)` `갈래 → 합류 (다시 한 단계로)` |
| `isFork(item)` | 그 노드가 하위 프로세스를 **벌리는지** (`seq` 가 아닌 모든 값 · 웹·앱 공용) |
| `checkflow.rowNos` / `forkBase` | 형제 프로세스 줄의 번호 채번 (순수 함수 · 웹·앱 공용 · 위 번호 규칙) |
| `isJoin(item)` | 벌린 갈래를 **다음 형제 한 단계로 모으는지**. 도식 렌더에서만 갈라진다 |
| `CHECK_TEMPLATES` | 업무항목 이름별 견본 (현재 `입고`). 「견본: 이름」 버튼이 쓴다 |
| `CHECK_CYCLE` | `daily` `weekly` `monthly` `adhoc` (저장값) |
| `CHECK_CYCLES` | 표시 문구 `일` `주` `월` `수시` |
| `WEEKDAYS` | `['일','월','화','수','목','금','토']` — 배열 순서가 `Date.getDay()` 와 같다 |
| `cycleLabel(item)` | `주(화)` `월(25일)` 처럼 한 줄로 만든다 (웹·앱 공용) |

## 보완 여지 (설계상 열어 둔 곳)

- **다른 견본** — `CHECK_TEMPLATES` 에 `출고` `반품` 을 더하면 「견본: 이름」 버튼이 저절로 생긴다
- **상황 아래 상황** — 허용하지 않는다(`CHECK_KIND_CHILDREN`). 필요하면 상수만 열면 되지만
  `dailyFlow` 의 `buildSituation` 이 상황 하위 상황을 무시하므로 함께 고쳐야 한다
- **상황 여러 번 발생** — 날짜당 1건이다. 건별 기록이 필요해지면 발생 기록을 별도 테이블로 뺀다
- **프로세스 간 조건 분기** (예: 냉장 입고면 ⑤ 대신 ⑤′) — 지금은 상황으로 표현한다
- **부분 합류 · 다른 업무항목으로의 합류** — 합류점이 늘 다음 형제라 표현할 수 없다.
  필요해지면 간선 테이블을 새로 들여야 하므로 그때 다시 설계한다

## 알려진 제약

- **인쇄에서 간선이 페이지 경계에 잘린다.** 카드와 상황 블록은 페이지 사이에서 잘리지 않게
  막아 두었지만, 카드를 잇는 선(SVG)은 페이지가 나뉘는 자리에서 끊겨 보인다. 도식은 A4 폭으로
  다시 배치해 찍으므로 가로로는 들어가지만, 갈래가 3개를 넘으면 레인이 최소폭(200px)으로 서도
  넘칠 수 있다
- **카드를 펼치면 아래가 통째로 밀린다.** 카드 높이를 재서 자리를 잡으므로 상세를 펼친 만큼
  다음 단계들이 아래로 내려간다 (스크롤 위치는 그대로다)
- **카드 너비가 200~260px 이라 편집 모드에서는 체크항목 줄이 접힌다** (이름 아래로 `일일`·`✎`).
  체크항목을 많이 손볼 때는 우측 체크리스트 표를 쓴다
- **미체크 알림은 화면 안의 배지뿐이다.** 푸시·메일 알림은 서버가 필요해 넣지 않았다
- **주기가 겹치는 항목을 한 줄로 합치지 않는다.** 같은 일을 매일·매주 두 번 넣으면
  두 줄로 나온다 (등록할 때 정리한다)
