# 출고주문처리

> 코드 `assets/js/pages/shipping.js` · 라우트 `#/shipping` · [공통 규약](common.md) · [CLAUDE.md](../CLAUDE.md)
> 단계 계산은 `assets/js/steps.js`, 정의는 `config.js` 의 `WORK_STEPS`

**출고작업 → 검수작업 → 추가작업**을 처리하는 화면.
처리한 결과가 [주문처리현황](status.md)의 단계에 그대로 반영된다.

## 웹과 모바일이 다르다 🔑

| | 웹 (861px 이상) | 모바일 (860px 이하) |
|---|---|---|
| 역할 | **진행중 목록 확인만** | **스캔해서 직접 처리** |
| 스캔 패널 | 없음 | 있음 |
| 처리 버튼 | 없음 | 있음 |

**실제 작업은 현장에서 모바일로 한다.** 웹은 각 탭에서 처리해야 할 건이
얼마나 남았는지 확인하는 용도다.

```js
const MOBILE_QUERY = '(max-width: 860px)';   // CSS 반응형 기준점과 같은 값
function isMobile() { return window.matchMedia(MOBILE_QUERY).matches; }
```

창 크기가 기준점을 넘나들면 `matchMedia` 의 `change` 이벤트로 **화면을 다시 그린다.**
(브라우저 창을 줄여 모바일 화면을 확인할 수 있다)

## 접근 권한

| 역할 | 조회 | 처리 (작업시작/완료/취소) |
|---|:---:|:---:|
| 관리자 | ✅ | ✅ |
| 용마담당자 | ✅ | ✅ |
| 화주관리자 | ✅ | ❌ 조회만 |
| 화주영업팀 | ✅ | ❌ 조회만 |

```js
const editable = can(user, 'updateStatus');
```

처리 권한이 없으면 버튼 대신 "처리 권한이 없어 조회만 가능합니다"를 표시한다.
(주문정보등록과 달리 이 화면은 소속이 아니라 **역할**로만 판정한다)

---

## 전체 처리 흐름 🔑

```
주문처리    출고작업      요청작업     검수작업     출고적치      추가작업     상차작업
(접수)  →  (출고작업) → (검수작업) → (검수작업) → (출고적치) → (조정요청) → (상차완료)
주문정보등록  출고주문처리   출고주문처리  출고주문처리  출고주문처리  출고주문처리  당일상차리스트
```

- **요청작업**은 주문에 추가작업(`extra_works`)이 등록된 경우에만 나타난다
- **추가작업**은 추가작업 요청이 등록된 경우에만 나타난다
- 단계 완료는 주문의 시각 필드에 저장된다 (`ship_done_at` 등). 값이 있으면 완료다
- 단계 정의는 `config.js` 의 `WORK_STEPS` 가 유일한 출처다

## 화면 구성

상단에 **출고작업 / 검수작업 / 출고적치 / 상차대기 / 조정요청** 탭이 있다.
선택한 탭은 모듈 스코프에 기억되어, 다른 메뉴에 갔다 돌아와도 유지된다.

---

## 웹 화면 - 진행중 목록

`renderPendingList()` 가 탭별로 **아직 처리되지 않은 건**만 보여준다. 처리 버튼은 없다.

| 탭 | 대상 |
|---|---|
| 출고작업 | 취소되지 않았고 `ship_done_at` 이 비어 있는 주문 |
| 검수작업 | `ship_done_at` 이 있고 `inspect_done_at` 이 비어 있는 주문 |
| 출고적치 | 검수까지 끝났고 아직 상차 전인 주문 — **적치완료 건도 함께 보인다** |
| 상차대기 | 적치까지 끝나고 아직 완료처리되지 않은 주문 — **상차완료 건도 함께 보인다** |
| 조정요청 | 접수된 요청이 있고 `extra_done_at` 이 비어 있으며 아직 상차 전인 주문 |

- ⚠️ **출고적치·상차대기 탭만 완료된 건까지 보여준다** (`showsDone()`).
  나머지 탭은 처리할 건(미완료)만 나온다
- 출고요청일 → 주문번호 순으로 정렬한다
- 출고작업 목록의 `작업상태` 는 `미접수` / `대기` / `작업중` 으로 구분한다
- **검수작업 목록에만 `파렛트수` · `박스수` 컬럼이 있다.** 진행중(검수 전) 건이라
  박스수는 대개 비어 있고(`-`), 값이 채워진 뒤에는 당일상차리스트에서 확인한다
- 조회 범위는 역할을 따른다 (화주영업팀은 본인 등록건만)
- 5초 폴링으로 갱신된다

### 요약 카드와 검색 🔑

목록 위에 **요약 카드 4개와 검색창이 한 행**으로 놓인다 (`drawSummary`).

| 항목 | 뜻 |
|---|---|
| 총건수 | 그 탭의 집계 대상(모수) 전체 — 완료된 건도 포함한다 |
| 완료건수 | 탭의 완료 시각 필드가 채워진 건 |
| 미완료 | 총건수 − 완료건수. 아래 표에 나오는 건수와 같다 |
| 완료율 | 완료건수 ÷ 총건수 (막대로도 표시) |

탭별 모수와 완료 판정은 다음과 같다 (`tabRows` · `DONE_FIELD`).

| 탭 | 모수 | 완료 판정 |
|---|---|---|
| 출고작업 | 취소되지 않은 주문 전체 | `ship_done_at` |
| 검수작업 | 출고작업이 완료된 주문 | `inspect_done_at` |
| 조정요청 | 접수된 요청이 있고 아직 상차 전인 주문 | `extra_done_at` |

- 검색은 **주문번호 · 거래처명** 부분 일치다 (대소문자 구분 없음)
- **요약도 검색 결과 기준으로 다시 집계된다.** 표만 걸러지는 것이 아니다
- 검색어는 탭별로 따로 기억되고, 다른 메뉴에 갔다 돌아와도 유지된다
- 5초 폴링으로 갱신될 때도 검색어는 그대로 유지된다
- 요약·검색은 **웹 화면에만** 있다. 모바일은 스캔으로 1건을 처리하는 화면이다

### 작업자 컬럼 🔑

각 탭에 **누가 그 작업을 하고 있는지** 표시한다. 단계별로 값이 따로 저장된다.

| 탭 | 필드 |
|---|---|
| 출고작업 | `ship_worker` |
| 검수작업 | `inspect_worker` |
| 조정요청 | `extra_worker` |

**입력하지 않는다. 모바일에서 주문번호를 스캔해 작업을 연 사람이 자동으로 기록된다.**

```js
// 각 탭에서 주문을 여는 순간 호출된다
if (editable) await db.recordWorker(orderId, mode, user);
```

- 조회 권한만 있는 사용자(화주 측)가 열어보는 것으로는 기록되지 않는다
  (`can(user, 'updateStatus')` 인 경우에만 기록)
- 다른 사람이 다시 스캔하면 **최신 스캔자로 갱신된다.** 지금 그 작업을 잡고 있는 사람을 뜻한다
- ⚠️ **완료된 단계는 바꾸지 않는다.** 실제로 작업한 사람 기록이 지워지면 안 되기 때문이다
  (`db.js` 의 `recordWorker()` 가 `STEP_DONE_FIELD` 로 판단한다)
- 스캔 없이 API 로 바로 완료 처리한 경우를 대비해, 값이 비어 있으면 완료 시점에
  처리자 이름으로 채운다 (`fillWorker()`)
- 웹 목록에서는 표시만 한다. 수정 수단은 없다

## 모바일 화면 - 스캔 처리

아래 내용은 모바일(860px 이하)에서만 나타난다.

### 스캔 패널 (`mountScanBox`)

| 방법 | 설명 |
|---|---|
| 카메라 스캔 | `📷 스캔` 버튼. 다시 누르면 정지 |
| 직접 입력 | 주문번호 입력 후 `조회` 또는 Enter |

- `assets/js/scanner.js` 의 `createScanner()` 를 쓴다 (BarcodeDetector 기반)
- 미지원 브라우저에서는 안내 문구를 띄우고 **직접 입력으로 처리한다**.
  블루투스 스캐너(키보드 입력 방식)도 그대로 동작한다
- **탭을 바꾸거나 화면을 떠나면 카메라를 반드시 정지한다** (각 탭이 정리 함수를 반환)

### 여러 차수 처리

같은 주문번호에 차수가 여러 건이면 **선택 목록**을 보여준다 (`pickOrder`).
1건이면 바로 열린다. 취소된 주문은 조회되지 않는다.

### 주문 요약 (`orderSummary`)

선택한 주문의 주문번호·차수·거래처·출고요청일·차량·파렛트수와
**현재 단계 흐름**을 남색 헤더에 보여준다. 완료된 단계는 초록으로 채워지고,
🔑 **지금 진행중인 단계(아직 끝나지 않은 첫 단계)는 노란색**으로 표시한다
(`.step.is-current`, 판단은 `visibleSteps()` 의 `current` 값).

#### 접기 / 펼치기 🔑

출고작업 · 검수작업 · 출고적치 탭의 요약 카드는 **카드 하단의 손잡이**로 접을 수 있다.
접으면 **주문번호와 거래처명만 한 줄로** 남아 아래 작업 영역이 화면 위로 올라온다.

```
펼침 (208px)                        접힘 (79px)
┌───────────────────────────┐       ┌───────────────────────────┐
│ PO-24080103  1차수         │       │ PO-24080103 이마트 김포센터 │
│ 이마트 김포센터             │   ⇄   │         ∨ 펼치기           │
│ 출고요청일 · 차량 · 파렛트   │       └───────────────────────────┘
│ 주문처리 → [출고작업] → …   │
│         ∧ 접기             │
└───────────────────────────┘
```

- `orderSummary(o, opt, { fold: true })` 로 손잡이를 붙이고
  `bindOrderHead(root)` 로 동작을 연결한다
- 접힘 상태는 `headFolded` 에 남아 **탭을 옮기거나 다른 주문을 스캔해도 유지된다**
- 조정요청 탭과 웹 팝업의 요약 카드에는 손잡이를 붙이지 않는다

## 출고작업 탭

작업자·작업시작·작업완료 시각을 보여주고, 상태에 따라 버튼이 달라진다.

| 상태 | 버튼 |
|---|---|
| 미착수 | `작업시작` |
| 작업중 | `작업완료` · `시작 취소` |
| 완료 | `완료 취소` |

- `db.startShipWork()` 가 `ship_started_at`, `db.setShipWorkDone()` 이 `ship_done_at` 을 기록한다
- **작업시작을 거치지 않고 바로 완료할 수 없다.** 시작 시각을 반드시 남기기 위해
  미착수 상태에는 `작업시작` 버튼만 둔다
- **검수작업이 완료된 주문은 출고작업을 취소할 수 없다.** 검수를 먼저 취소해야 한다
- 접수(주문처리)가 안 된 주문도 작업할 수 있지만 경고 문구를 띄운다.
  현장 작업을 막지 않기 위한 선택이며, 주문처리 단계는 비어 있는 채로 표시된다

## 검수작업 탭

**출고작업이 완료된 주문만 진행할 수 있다.** 아니면 안내만 나온다.

시작/완료 개념이 없고 **완료만** 처리한다.

### 완료 조건

| 항목 | 언제 나오나 | 필수 |
|---|---|:---:|
| 요청작업 완료 확인 (체크) | 주문에 `extra_works` 가 있을 때 | ✅ |
| 패킹리스트 작성 확인 (체크) | 항상 | ✅ |
| **총 파렛트수** (숫자 입력) | 항상 | ✅ |
| **총 박스수** (숫자 입력) | 항상 | ✅ |

- 요청작업 체크 아래에 등록된 작업(라벨작업·박스교체·LOT지정)을 태그로 보여준다
- **하나라도 빠지면 검수완료가 거부된다** (`db.setInspectDone()` 이 막는다)
- 요청작업 체크는 `req_work_at` 을, 패킹리스트 체크는 `packing_at` 을 채운다.
  두 값과 `inspect_done_at` 이 한 번에 기록된다

검수작업 탭도 출고작업 탭과 같이 **상단에 진행현황(단계 흐름)을 표시한다.**

### 검수 실측값 입력 🔑

검수하면서 센 **총 파렛트수(`pallet_count`)와 총 박스수(`box_count`)를 수기로 입력**해야
검수를 완료할 수 있다. 1 이상의 정수가 아니면 거부된다.

- 🔑 **추가건(2차수 이상)은 `0파렛트` 로 둘 수 있다.** 기존 차수 파렛트에 함께 싣는
  혼적이라 파렛트가 늘지 않는 경우다. 1차수는 여전히 1 이상이어야 한다
  (`db.setInspectDone()` 이 `seq > 1` 일 때만 0을 받는다)
- ⚠️ **0파렛트로 검수완료하면 출고적치도 함께 끝난 것으로 처리한다.**
  적치할 파렛트가 없는데 출고적치 탭에 영원히 남지 않게 하기 위해서다
  (검수를 취소하면 적치도 함께 풀린다)
- 0파렛트로 검수완료하면 **확인 대화상자**가 한 번 더 뜬다 —
  "0파렛트로 처리됩니다. 기존 차수 파렛트에 함께 적재(혼적)하여 파렛트수가 늘지 않는 것이 맞습니까?"
- 파렛트수는 주문의 `pallet_count` 를 **덮어쓴다.** 주문 등록 시에는 입력하지 않으므로
  이 화면이 값을 채우는 유일한 경로다 (CLAUDE.md 열린 이슈 1 참고)
- ⚠️ **입력한 파렛트수만큼 상차 검수용 바코드가 다시 만들어진다**
  (`{주문번호}-P01…`). 값이 바뀌면 이미 진행한 상차 검수는 초기화되고
  상차 상태가 `대기` 로 돌아간다
- 완료 후에는 입력칸이 사라지고 표에 값만 보인다. `완료 취소` 를 하면 다시 입력할 수 있고,
  **입력값 자체는 지워지지 않는다** (마지막 실측 기록을 남기기 위해서다)
- 값은 웹의 **당일상차리스트 · 검수(바코드) 화면**에서 확인한다

`완료 취소` 를 누르면 검수·요청작업·패킹리스트가 함께 풀린다.
**상차완료된 주문은 취소할 수 없다.**

## 출고적치 탭 🔑

검수가 끝난 파렛트를 창고 로케이션에 넣고 **파렛트마다 위치를 기록**하는 단계다.
파렛트 전량에 로케이션이 들어가면 `stow_done_at` 이 자동으로 채워진다
(`db.setPalletLocation()` 안의 `syncStowDone`).

### 대상

**검수작업(`inspect_done_at`)이 끝나고 아직 상차되지 않은 주문.**
검수 전 주문을 스캔하면 안내만 나온다. 파렛트 수는 검수작업에서 입력한
`pallet_count` 를 따르므로, 그 값이 0이면 적치할 파렛트도 없다.

### 상태 (`config.js` 의 `STOW_STATUS`)

저장하지 않고 **로케이션이 입력된 파렛트 수로 계산한다.**

| 상태 | 조건 | 색 |
|---|---|---|
| `적치대기` | 로케이션이 하나도 없음 | 회색 |
| `적치중` | 일부만 입력 | 파랑 |
| `적치완료` | 전량 입력 (`stow_done_at` 기록) | 초록 |

### 모바일 - 로케이션 입력 🔑

주문번호를 스캔하면 **입력 패널과 파렛트 목록**이 함께 나온다.
입력 패널은 화면 위에 **고정(sticky)** 되어 목록을 훑는 동안에도 계속 보인다.
현장에서 스캐너를 들고 연속으로 찍는 화면이라 **한 손 조작·연속 입력**을 우선한다.

```
┌ 연속이동 | 건별이동 ───────── 적치중 2/6 ┐   ← 화면 위에 고정
│ 구역코드  [자동|수기]  [IF]              │
│ 다음 대상  PO-24080105-03      남은 4건   │
│ [ 010203            ]  [ 저장 ]          │
│         IF-01-02-03                     │   ← 미리보기 (입력 중일 때만)
│ [지우기]             [📷 카메라] [⌨ 자판] │
└─────────────────────────────────────────┘
  파렛트 목록 (▶ 다음 차례 · ✅ 입력 완료)
```

### 이동 방식 (`STOW_MODES`)

| 방식 | 대상 | 쓰는 상황 |
|---|---|---|
| **연속이동** (기본) | 목록에서 **로케이션이 없는 첫 파렛트** | 스캐너로 순서대로 쭉 찍을 때 |
| **건별이동** | 목록에서 **직접 고른 파렛트** | 특정 파렛트만 고치거나 건너뛸 때 |

- 목록의 파렛트를 누르면 **자동으로 건별이동으로 바뀌고** 그 파렛트가 대상이 된다
- 입력 패널이 고정되어 있어 **목록에서 고르는 동안에도 입력칸이 계속 보인다.**
  예전처럼 화면 아래 입력창으로 이동하지 않는다
- 저장하면 두 방식 모두 **다음 미지정 파렛트로 대상이 넘어간다**

#### 목록 정렬 🔑

| 방식 | 목록 순서 |
|---|---|
| **연속이동** | **방금 이동한 것이 맨 위** (최근순) → 나머지는 파렛트 번호순 |
| **건별이동** | 파렛트 번호순 (골라야 하므로 순서를 흔들지 않는다) |

찍으면서 바로 눈으로 확인하기 위한 순서다. 이동 순서는 **화면에 머무는 동안만** 기억하므로
(`moved`), 주문을 다시 스캔하면 파렛트 번호순으로 돌아간다.
로케이션을 지우면 그 파렛트는 최근 목록에서 빠지고, 이미 넣은 건을 다시 넣으면 맨 위로 올라온다.

### 구역코드 (`ZONE_MODES`) 🔑

| 방식 | 동작 |
|---|---|
| **자동** (기본) | 미리 넣어둔 구역코드가 **이후 입력에 계속 따라붙는다.** `010203` → `IF-01-02-03` |
| **수기** | **넣은 값을 그대로 쓴다.** 로케이션 바코드를 스캔해 넣을 때 쓴다 |

- 구역코드는 영문 2자리다 (소문자로 넣어도 대문자로 바뀐다)
- 자동이라도 **영문이 섞여 들어오면 그대로 쓴다.** 로케이션 전체를 스캔한 경우다
- 자동 + 구역코드가 정해지면 입력칸이 숫자 자판(`inputmode=numeric`)으로 바뀐다
- 설정은 `stowPrefs` 에 남아 **다른 주문을 스캔해도 유지된다**

### 입력 방법

| 방법 | 설명 |
|---|---|
| **외부 스캐너** | 입력칸에 값을 치고 Enter 를 보낸다. **저장 후 커서가 입력칸으로 돌아와** 연속으로 찍을 수 있다 |
| **카메라 스캔** | `📷 카메라` — 읽은 값을 그대로 입력한다. 연속 입력을 위해 켜둔 채로 유지된다 |
| **수기 입력** | 입력칸에 직접 치거나 `⌨ 자판` 으로 계산기 배열 숫자 자판을 펼친다 |

- 카메라·자판 버튼은 **오른쪽에 모아** 크게 두고, 구분선으로 입력칸과 나눈다.
  `지우기` 는 잘못 누르지 않도록 반대쪽 끝에 떨어뜨린다
- 자판을 펼치면 패널이 화면을 다 덮으므로 **고정이 풀린다** (`.stow-bar.is-tall`)
- 자판 배열은 계산기와 같다 — `7 8 9 / 4 5 6 / 1 2 3 / C 0 ←`
  (`C` 는 전체 지우기, `←` 는 한 자리 지우기)

### 연속 입력 규칙 🔑

| 상황 | 처리 |
|---|---|
| 저장 성공 | 토스트 + 진동, 입력칸을 비우고 **커서를 되돌린다** |
| 같은 값이 **2.5초 안에** 다시 들어옴 | 스캐너 이중 발사로 보고 **조용히 무시**한다 (`STOW_REPEAT_MS`) |
| 같은 주문의 **다른 파렛트에 이미 쓴 로케이션** | 알림 + 진동 3회, 저장하지 않고 **다시 받는다** |
| 형식이 덜 채워진 값 | 알림 후 입력칸을 비운다 |

- 중복 검사는 **같은 주문 안에서만** 한다 (다른 주문의 로케이션은 보지 않는다)
- 잘못 넣었으면 건별이동으로 그 파렛트를 고른 뒤 `지우기` 를 누른다.
  **상차완료된 주문은 되돌릴 수 없다**

### 로케이션 형식 🔑

**영문 2자리 구역코드 + 2자리 숫자 3묶음** 이다 (`config.js` 의 `LOCATION_FORMAT`).

```
IF-01-03-01
```

- 숫자는 **6자리**까지 받고 `formatLocation()` 이 2자리씩 끊는다. 7자리째부터는 무시한다
- **형식이 다 채워지면 미리보기 테두리가 초록으로 바뀐다** (`.loc-preview.is-ready`)
- 형식이 덜 채워졌으면 저장이 거부된다 (`isValidLocation()`).
  **화면과 `db.setPalletLocation()` 양쪽에서 검사한다**
- 화면에 보여줄 때도 `formatLocation()` 을 거치므로 예전 형식으로 저장된 값도
  같은 모양으로 정리되어 보인다
- 값은 저장할 때 대문자로 바꾼다

### 웹 - 목록

```
출고일자 · 주문번호 · 차수 · 거래처명 · 파렛트수 · 출고적치(상태 + 진행 수)
```

**주문번호를 누르면 파렛트별 로케이션 목록이 팝업으로 열린다** (`openLocationView`).
웹에서는 입력하지 않는다.

- 적치가 끝난 건도 목록에 남는다. **상차완료되면 이 탭에서 빠진다**

## 상차대기 탭

적치까지 끝나 상차를 기다리는 주문을 본다. 처리 기능은 없고 확인용이다.

```
출고일자 · 주문번호 · 차수 · 거래처명 · 파렛트수 · 적치로케이션 · 상태
```

| 항목 | 내용 |
|---|---|
| 대상 | `stow_done_at` 이 있고 아직 완료처리(`closed_at`)되지 않은 주문 |
| 묶음 | **같은 주문번호의 차수를 하나로 묶어 대표(가장 낮은 차수)만 보여준다** |
| 적치로케이션 | `로케이션 보기` 버튼 → **차수 전체**의 로케이션 팝업. **상차완료 건은 버튼 없이 `-`** |
| 상태 | `loaded_at` 이 있으면 `상차완료`(초록), 없으면 `상차대기`(회색) |

### 차수 묶음 🔑

추가주문은 1차수와 **함께 한 거래처로 배송**되므로 상차 단위로 묶는다 (`db.getLoadGroup()`).

- 목록에는 **대표(가장 낮은 차수)만** 나오고, 주문번호 옆에 `+2건` 주황 배지가 붙는다
- 주문번호·거래처명은 **1차수 정보**를 쓴다. 파렛트수는 차수 합계다
- `로케이션 보기` 는 **모든 차수의 파렛트**를 보여주고, 맨 앞에 `1차` `2차` 차수 컬럼이 있다
- 검수·상차완료도 그룹 전체에 적용된다 ([당일상차리스트](loading.md) 참고)

실제 상차 처리는 [당일상차리스트](loading.md)에서 한다.

### 모바일 - 상차대기 목록

모바일도 스캔이 아니라 목록에서 고른다 (`renderLoadWaitTab`).

```
주문번호 · 거래처명 · 파렛트 · 적치로케이션(대표 1개 + 외 N)
```

- 대상은 **적치완료 + 상차 전** 이다. ⚠️ **상차완료되면 목록에서 빠진다**
  (웹은 상태 컬럼으로 상차완료까지 보여주지만, 모바일은 처리할 건만 남긴다)
- 행을 누르면 위쪽에 **상세(거래처·출고요청일·차량·박스수·검수)와
  파렛트별 로케이션 목록**이 펼쳐진다
- 이 화면에서 상차 처리는 하지 않는다. 파렛트 내리기와 상차완료는 당일상차리스트에서 한다

### 재고실사표 🔑

목록 우측 상단의 `재고실사표` 버튼으로 연다 (`openStockSheet`).
**적치가 끝나고 아직 상차되지 않은 파렛트 전체**를 로케이션 순으로 모아 보여준다.

```
로케이션 · 주문번호 · 거래처명 · 적치확인 · 비고
```

- `적치확인` 과 `비고` 는 **현장에서 손으로 적는 칸이라 빈 값으로 둔다**
- `엑셀 다운로드` — CSV 로 받는다 (`downloadCsv`). 엑셀에서 바로 열리도록 BOM 이 붙는다.
  xlsx 라이브러리는 쓰지 않는다
- `인쇄` — 새 창에 A4 세로로 그리고 인쇄 대화상자를 띄운다 (`printStockSheet`)
- ⚠️ **인쇄용 문서는 `body { width: 186mm }` 로 폭을 고정한다.**
  고정하지 않으면 브라우저 레이아웃 폭을 따라가 표가 오른쪽 여백을 넘는다.
  여러 장이 되면 `thead { display: table-header-group }` 로 머리글이 반복된다

## 조정요청 탭

### 대상

**두 조건을 모두 만족하는 주문만** 목록에 나온다.

1. 접수된 조정요청 또는 작업요청이 있다
2. 아직 상차되지 않았고 취소되지 않았다

⚠️ **출고작업·검수작업이 끝나지 않은 주문도 목록에 나온다.** 요청이 들어온 것을
현장에서 미리 알 수 있어야 하기 때문이다. 다만 **완료 처리는 검수작업을 마친 뒤에만**
가능하다 (`db.setExtraWorkDone()` 이 막는다). 검수 전인 주문을 열면 그 안내가 뜬다.

### 요청의 출처 🔑

`db.listRequestTasks()` 가 **두 갈래를 합쳐서** 돌려준다.

| 구분 | 출처 | 목록에 나오는 조건 |
|---|---|---|
| **조정요청** | 주문 상세 팝업의 조정요청 탭에서 등록 | **용마담당자가 `접수` 처리한 건만** |
| **작업요청** | 이슈등록의 `작업요청` 유형 (주문번호로 연결) | 주문번호가 일치하면 바로 |

- 조정요청은 접수 전에는 나오지 않는다. 접수를 해제하면 목록에서 빠진다
- 목록의 `구분` 컬럼에 **요청항목**(전체취소·부분취소·전체보류·부분보류·기타요청)이
  주황 태그로 표시된다. 이슈 기반 건은 `작업요청` 회색 태그다
- ⚠️ 이슈의 `order_no` 는 자유 입력이라 오타가 나면 연결되지 않는다

### 목록 컬럼

⚠️ **모바일에서는 스캔 패널이 없다.** 조정요청은 스캔할 대상이 아니라
**접수된 요청 목록에서 골라 처리하는 화면**이다.

**모바일(이 화면의 목록)** — 좁은 화면에 맞춰 4개만 보여준다.

```
등록일자(월/일) · 구분 · 주문번호 · 거래처명
```

- 등록일자는 `08/30` 형식으로 줄인다 (`monthDay()`)
- **행을 누르면 위쪽에 상세가 펼쳐지고 그 위치로 스크롤된다.** 주문번호뿐 아니라
  행 어디를 눌러도 열린다 (`tr.is-clickable`)
- 요청 내용·완료요청일·차수·상태는 상세에서 확인한다
- 표 밀도는 CSS 의 `table.grid--mobile` 이 낮춘다 (주문처리현황 모바일 표와 공유)

**웹(진행중 목록)** — 컬럼이 더 많다.

등록일자 · **구분** · 주문번호 · **차수** · 거래처명 · 요청 내용 · 완료요청일 · 작업자

같은 주문번호의 차수마다 요청이 따로 걸리므로 **차수를 함께 표시한다.**
(이슈의 `작업요청` 은 주문번호로만 연결되어 여러 차수에 동시에 붙는다)

- 조정요청은 완료요청일이 없어 `-` 로 표시한다
- 탭 이름 옆에 **미처리 건수 배지**가 붙어 새 요청이 들어온 것을 알린다
- 주문번호를 누르면 상세가 열린다. 스캔으로도 같은 화면을 연다
- `작업완료` / `완료 취소` 로 `extra_done_at` 을 기록한다
- **검수작업이 완료되지 않았으면 완료할 수 없다**

## 수정 시 주의

- **단계를 추가·변경할 때는 `config.js` 의 `WORK_STEPS` 만 고친다.**
  주문처리현황·당일상차리스트가 같은 정의를 쓰므로 자동으로 따라온다
- ⚠️ **출고적치는 필수 단계다.** 적치가 끝나지 않으면 `readyToLoad` 가 false 라
  당일상차리스트에 나오지 않는다 ([docs/loading.md](loading.md) 참고)
- **각 탭은 정리 함수를 반드시 반환한다.** 카메라가 계속 켜져 있게 된다
- 단계 완료 여부는 `stage` 같은 숫자가 아니라 **시각 필드의 유무**로 판단한다.
  숫자 단계로 되돌리면 조건부 단계(요청작업·추가작업)를 표현할 수 없다
- 취소 처리(완료 취소)는 뒤 단계가 진행됐으면 막는다. 새 단계를 넣을 때도 같은 규칙을 지킨다
- **웹과 모바일 두 화면을 모두 확인한다.** 브라우저 창을 줄이면 바로 전환된다
- 웹 화면에는 처리 버튼을 넣지 않는다. 현장 처리는 모바일에서만 한다
- `#scan-video` 는 `hidden` 속성으로 감춘다.
  CSS 의 `display: block` 이 이를 덮지 않도록 `#scan-video[hidden]` 규칙을 유지한다
